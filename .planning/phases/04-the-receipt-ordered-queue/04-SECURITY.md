# Security Report — Phase 4: the-receipt-ordered-queue

**Mode:** verify
**Audited:** 2026-09-15
**Verdict:** SECURED
**Confirmed HIGH/CRITICAL:** 0

## Summary
Verified all 9 declared STRIDE threats (T-04-01 through T-04-09) from the four Phase 4 PLAN.md `<threat_model>` blocks against the shipped code, not just the plan prose. Every claimed mitigation was found genuinely present: `resolveCaseIdentifier` binds the caller-supplied identifier as `$1` in every branch (never concatenated); the route validates identifier FORM via `UUID_RE`/`CASE_REF_RE` before any DB call; the blanket `Object.keys(req.query).length > 0` query-parameter rejection is untargetable (confirmed with `qs` parsing edge cases — even a bare `?foo` or `?=x` produces a non-empty key set); the `CASE_READ_INVARIANT:` internal-error prefix is a plain `Error` that only `errorMapper`'s generic-500 fallback branch (case 4, "anything else") can reach, with no internal detail in the response; the 500-row truncation is a fixed literal with no request-derived input reaching it; `Queue.tsx` renders all three server strings as plain JSX text children (verified against the project-wide `dangerouslySetInnerHTML` source-scan in `headers.spec.ts`, which returned zero offenders); and the case-reference link is built with `react-router`'s `Link` to a same-origin relative path, with the format constrained server-side by `cargo_entries_case_reference_fmt_chk`. The two "accept" dispositions (T-04-02, T-04-07 — no per-user scoping) were independently confirmed accurate: `specialists` (migration 0001) has no `role`/`is_supervisor`/`permissions`/`scope` column, and no application-layer role check exists anywhere in the auth chain (`requireApiAuth`, `sessionMiddleware`) or in any repository — every specialist genuinely sees every case identically. Beyond the declared 9, I additionally confirmed `requireApiAuth()` runs before route registration in `app.ts` and is data-driven from the full `API_ROUTE_TABLE` in `guard.spec.ts`'s unauthenticated matrix (so the two new GET routes are provably gated, not gated "by claim"), and that CSRF middleware correctly excludes GET so no CSRF bypass is introduced on these read-only routes. No HIGH/CRITICAL finding survived adversarial refutation. Ship.
