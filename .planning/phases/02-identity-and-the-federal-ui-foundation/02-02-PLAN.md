<objective>
Build the four cross-cutting HTTP concerns every route in the product will inherit: the
security headers (including the one header that must never be sent), request correlation, the
redacting logger, and the single error-translation point.

Purpose: these are the pieces whose failure modes are invisible until they matter. An
`X-Frame-Options` header makes the running application unreachable in the only environment
the walkthrough happens in. A `HITL_VIOLATION` leaked verbatim tells an attacker the shape of
the governance layer. A cookie in a log line is a session handed over. Each is cheap to build
once, here, and expensive to retrofit across ten routes later.

Output: `server/src/http/{logger,requestId,cookies,headers,errorMapper}.ts` and their unit
suites. No route, no middleware chain, no server — plan 02-04 assembles these.
</objective>

<never_send_this_header_rule>
`X-Frame-Options` MUST NOT be emitted on any route, in any configuration, with any value
(FR-Y3.9a, TechArch D-1). The application is demonstrated inside a sandbox preview IFRAME and
the header has no allowlist form, so `DENY` and `SAMEORIGIN` are equally fatal. helmet sends
`X-Frame-Options: SAMEORIGIN` **by default** — `frameguard: false` is therefore not optional
polish, it is the whole point. The literal string `X-Frame-Options` must not appear anywhere
under `server/src/` except, if you wish, inside a comment explaining this rule; plan 02-09
adds an architecture assertion that fails the build if a value is ever set.

Equally prohibited: CSP `frame-ancestors 'none'`, a bare `frame-ancestors 'self'`, and
`Cross-Origin-Embedder-Policy`. `loadConfig` already refuses to start on the first two.
</never_send_this_header_rule>

<no_orm_rule>
No module in this plan touches the database. If a later reader adds SQL here, it is
hand-written and parameterised — no template-literal interpolation of any value, no ORM, no
query builder (R-L8, TechArch §6.3).
</no_orm_rule>

```typescript
pino({
  level: config.logLevel,
  redact: {
    paths: [
      'req.headers.cookie',
      'req.headers["x-csrf-token"]',
      'req.headers.authorization',
      'password',
      '*.password',
      'token',
      '*.token',

      return { ...base, headers: req.headers };

  },
});
```

**`server/src/http/headers.ts`** — `securityHeaders(config: AppConfig): RequestHandler[]`
returning an ordered array of handlers (helmet first, then the hand-written CSP and the
per-path cache header).

Configure helmet with **both** of its framing/CSP features disabled so nothing is emitted
behind your back:

```typescript
helmet({
  frameguard: false,              // D-1: X-Frame-Options is NEVER sent
  contentSecurityPolicy: false,   // the CSP below is hand-written (§4.5)
  crossOriginEmbedderPolicy: false, // would break framing for no benefit here
  hsts: config.originIsHttps ? { maxAge: 31536000 } : false,
  referrerPolicy: { policy: 'same-origin' },
  // noSniff stays on -> X-Content-Type-Options: nosniff
})
```

Then a handler that sets, on **every** response, the CSP of TechArch §4.5 assembled from
these directives in this order:

```
default-src 'self';
script-src 'self';
style-src 'self';
img-src 'self' data:;
font-src 'self';
connect-src 'self';
form-action 'self';
base-uri 'self';
object-src 'none';
frame-src 'none';
[frame-ancestors <FRAME_ANCESTORS>;]      ← emitted ONLY when configured
```

`frame-ancestors` is appended **only** when `config.frameAncestors !== null`. Unset is the
demonstration default and means the directive is omitted entirely — the app is embeddable and
no frame-blocking exists. `loadConfig` has already refused `'none'` and `'self'`, so no
defensive re-check is needed here; add a one-line comment pointing at that self-check so the
next reader does not add a redundant one.

No `unsafe-inline` and no nonce machinery: there is no inline script anywhere (§4.5), and the
USWDS stylesheet is a compiled file served from the same origin and referenced by a
`<link rel="stylesheet">` in `web/index.html` (plan 02-05) — **not** imported from JavaScript.
Record that dependency here as a comment: a JS-injected `<style>` element would violate
`style-src 'self'` and the stylesheet would silently not apply.

Finally, cache policy (§3.2, §4.5):
- `Cache-Control: no-store` on every response whose path starts with `/api`.
- `Cache-Control: no-store` on the SPA document (`index.html` / any HTML document response),
  so a stale shell never renders against a new API.
- Static hashed assets are left to `express.static`'s defaults.

**`server/src/http/errorMapper.ts`** — the only place a failure becomes a response body
(TechArch §1A.3). Two exports.

`class ApiError extends Error` — what handlers throw deliberately:
```typescript
export class ApiError extends Error {
  constructor(
    readonly status: number,
    readonly code: ErrorCode,
    message?: string,                          // defaults to ERROR_MESSAGES[code]
    readonly details?: readonly ApiErrorDetail[],
  ) { super(message ?? ERROR_MESSAGES[code] ?? 'Request failed.'); }
}
```
Because the message defaults from `ERROR_MESSAGES`, a handler writing `new ApiError(401,
'AUTH_FAILED')` produces exactly the Y2 §1 text, and no handler can drift it.

`errorMapper(): ErrorRequestHandler` — the Express error middleware, registered last. It maps,
per TechArch §3.7:

| Source | Surfaces as |
|---|---|
| `ApiError` | its own status + code + message + details |
| `ZodError` | `422 REQUEST_MALFORMED` with `details[]` — one entry per issue, `field` = the dot path, `code` = the zod issue code, `message` = plain language |
| PG `23505` on `cargo_entries.entry_number` | `409 ENTRY_NUMBER_DUPLICATE` |
| PG `23505` on `decisions.exception_id` | `409 EXCEPTION_ALREADY_DECIDED` |
| PG `23505` on `decisions (exception_id, idempotency_key)` | `409 IDEMPOTENCY_KEY_REUSED` |
| PG `23514` `decisions_reason_required_chk` | `422 REASON_REQUIRED` |
| PG `23503` `exceptions_basis_fk` | internal `EXCEPTION_WITHOUT_BASIS` → `500 RECEIPT_FAILED` |
| PG `P0001` whose message begins with one of `INTERNAL_INVARIANT_CODES` | internal → `500 RECEIPT_FAILED` or `500 DECISION_FAILED` |
| PG `42501` | internal `AUDIT_IMMUTABLE` → `500 RECEIPT_FAILED` |
| anything else | `500` with a generic message |

The 23505/23514/23503 rows name tables that do not have routes until phases 3 and 6. Implement
the mapping table now anyway — it is one data structure, it is the documented contract, and
splitting it across four phases guarantees drift. Add a comment naming the owning phase beside
the rows that are not yet reachable; **do not** write a skipped test for them.

Three rules the mapper enforces, each with a test:

1. **An internal invariant code never reaches the client.** When the underlying error's message
   starts with a member of `INTERNAL_INVARIANT_CODES`, the response body contains the generic
   code only, and the internal code is written to `req.log.error({ internal_code, request_id })`.
   Assert both halves: the body does NOT contain e.g. `HITL_VIOLATION`, and a captured log line
   DOES (Y2 §7, FR-Y2.5).
2. **No message discloses SQL, a stack trace, provider text, configuration, or account
   existence.** Assert the serialised body of a mapped PG error contains none of `SELECT `,
   `INSERT `, `at Object.`, `pg`, `password`.
3. **Every envelope carries `request_id`**, taken from `res.locals.requestId`, matching the
   `X-Request-Id` header (FR-Y2.6, FR-Y1.4).

Envelope shape (`ApiErrorBody`, §3.10): `{"error":{"code","message","details"?,"request_id"}}`
with `details` **omitted when empty** — not `[]`, omitted.
