<objective>
Stand up the USWDS asset pipeline and the application shell every screen in the product will
inherit — landmarks, skip link, the two-destination navigation, focus and title management,
the two live regions, and the five shared state components — and prove it in a real browser.

Purpose: F2 exists so that accessibility is a property of the delivered interface rather than
a per-screen aspiration. Landmarks, the error pattern, focus management and the provenance
badge are built **once** here; a screen cannot accidentally have a different heading structure
because it does not own one. This plan is also where the phase's exclusion criterion becomes
real: the navigation set is data with exactly two members, and nothing in the DOM implies a
dashboard, a report, a metric or a second role.

Output: the Vite + dart-sass build, `web/src/shell/*`, the shared state components, the router,
and `e2e/shell.spec.ts` driving a real browser against the real server.
</objective>

<exactly_two_destinations_rule>
UX 00-overview §2 is the authority and FR-2.7 is the requirement: primary navigation contains
**exactly two** destinations —

| Screen | Route | Nav element |
|---|---|---|
| Review queue | `/queue` | header `usa-nav` link **"Review queue"** (`aria-current="page"` when active) |
| Cargo entry form | `/entries/new` | header `usa-nav` link **"New cargo entry"** |

"**A third navigation item does not exist anywhere in the DOM** — no dashboard, reports,
metrics, settings, administration or export item." Not disabled, not hidden, not commented
out: absent. Express the set as the exported `NAV_ITEMS` array so its cardinality is a value
a test can read, and render it with `.map` so the DOM cannot disagree with the data. Plan
02-09 adds the architecture assertion; `e2e/shell.spec.ts` in this plan adds the browser one.

Equally absent: a user menu, a settings gear, a notifications bell, a search box, a theme
toggle, a language switcher, a version string and an environment badge. Each would imply a
capability this product does not have.
</exactly_two_destinations_rule>

<excluded_affordance_scan>
**The canonical definition of criterion 5's exclusion scan. Plan 02-09 Task 1 item 4
implements the durable version of exactly this; keep the two identical.**

The thing being excluded is an **affordance** — a destination a specialist can reach or a
control she can operate — not a source token. Scanning source text for these words does not
work and must not be attempted: `export` appears in every TypeScript module, `filter` and
`sort` are `Array.prototype` methods, and `report` is a substring of `reporter`. A gate that
cannot pass on a conformant tree is a gate that gets weakened by whoever hits it, and
criterion 5 is the one assertion standing against PRD R-2's named scope risk.

**Surfaces to scan** (and only these):
1. **destinations** — the values of `to`, `href` and `path`, in both the JSX attribute form
   (`href="…"`) and the object-literal form (`{ to: '…' }`, `{ path: '…' }`), across
   `web/src/**/*.{ts,tsx}`. Both forms matter: `NAV_ITEMS` is a `.ts` file using `to:`, and
   the router uses `path:`, so an attribute-only scan would miss a third nav item entirely;
2. `NAV_ITEMS` labels;
3. in a browser, the accessible name and `href` of every `a`, `button`, `[role="link"]` and
   `[role="button"]` inside `nav[aria-label="Primary"]`, `header[role="banner"]` and
   `main#main-content`.

**Surface deliberately excluded:** the `footer[role="contentinfo"]` subtree. The USWDS
`usa-identifier` required-links row is federal conformance markup whose link set is fixed by
USWDS (it includes "Performance reports"), not a product capability. Excluding it is why the
Footer's link set is pinned explicitly in Task 2 — so the exclusion is auditable rather than
a convenient blind spot.

**Terms** (case-insensitive, word-boundary where the word is also ordinary English):
`dashboard`, `\breports?\b`, `\bmetrics?\b`, `analytics`, `settings`, `preferences`,
`\badmin(istration)?\b`, `user management`, `\bexport\b`, `download`, `\bsearch\b`,
`\bfilter\b`, `sort by`, `assign`, `priority`.

Note `\breports?\b` does not match `reporter`, and the four English words only appear in these
surfaces if someone has actually added the affordance.
</excluded_affordance_scan>

<no_accessibility_gate_rule>
There is **no automated accessibility gate** and there must never be one (NFR-2, FR-2.25,
TechArch §7.8). Do not add `axe-core`, `@axe-core/*`, `jest-axe`, `pa11y` or `lighthouse-ci`;
`server/test/architecture/absence.spec.ts` fails the build if one appears. Do not create a
`.github/` directory.

The Playwright suite in this plan tests **keyboard operability and functional structure** —
landmark counts, focus destinations, tab order, nav cardinality. §7.8 sanctions exactly that:
"a functional test of SM-11's task completability, not an accessibility conformance gate", and
it asserts no WCAG rule. The enforcement mechanism for conformance is the signed per-screen
review of §7.7, which plan 02-09 delivers.
</no_accessibility_gate_rule>

<placeholder_screens_are_transitional>
The two navigation destinations are owned by later phases: `/entries/new` is F6 (Phase 3) and
`/queue` is F8 (Phase 4). A nav link to a route that 404s would be a broken shell and would
fail the no-orphan-screen invariant of UX §2, so this plan registers both routes with a
`NotBuiltYet` screen that renders inside the shell: the correct `h1` for that screen ("Review
queue" / "New cargo entry"), the correct document title, and one `usa-alert--info` reading
"This screen is not available in this build." with a link to the other destination.

Constraints on it, so it does not become scope:
- It renders **no** disabled control, no "coming soon" chip, no greyed-out table and no
  tooltip explaining a missing capability (UX Pattern 7, FR-12.11).
- It is a transitional build artefact. Phase 3 replaces `/entries/new` and Phase 4 replaces
  `/queue`; `NotBuiltYet.tsx` is **deleted** when the second of them lands. Put that sentence
  in the file header naming both phases.
</placeholder_screens_are_transitional>

icon sprite**, not as a wrapper component library, so the project owns the rendered DOM that
manual review certifies (§7.2). Structure:

```scss

  $theme-show-notifications: false

```
(the exact module names for USWDS 3.11 are `uswds-core` and `uswds`; if the package layout
differs, read `node_modules/@uswds/uswds/packages/` and follow the shipped
`uswds-theme`/`uswds` entry points rather than inventing paths.)

appear in any screen-level style** (FR-2.2) — every colour, space and type step comes from a
token. Keep this file the only `.scss` in the project for now; screens use USWDS utility and
component classes.

`npm run build:css` (declared in plan 02-01) compiles this to `web/public/assets/uswds.css`
with `--load-path=node_modules` and `--load-path=node_modules/@uswds/uswds/packages`.

**`web/scripts/copy-uswds-assets.mjs`** — copies `@uswds/uswds/dist/img` (including
`sprite.svg`), `dist/fonts`, and `dist/js/uswds.min.js` into `web/public/assets/{img,fonts,js}`.
FR-2.3: the demonstration must render correctly with **no external network access**, so
nothing may be fetched from a CDN at runtime. Use `node:fs.cp` recursively; make it idempotent.

**`web/index.html`** — the SPA document:
```html
<!doctype html>
<html lang="en">
  <head>
    <meta charset="utf-8" />
    <meta name="viewport" content="width=device-width, initial-scale=1" />
    <title>CargoExec</title>
    <link rel="stylesheet" href="/assets/uswds.css" />
  </head>
  <body>
    <div id="root"></div>
    <script type="module" src="/src/main.tsx"></script>
    <script type="module" src="/assets/js/uswds.min.js"></script>
  </body>
</html>
```

**Two things here are load-bearing, not stylistic:**

1. **The stylesheet is a `<link>`, never a JS `import './uswds.scss'`.** CSP is `style-src
   'self'` with no `unsafe-inline` (§4.5). A bundler that injects CSS by creating a `<style>`
   element at runtime would be blocked by that directive and the application would render
   unstyled with only a console warning. A linked file from the same origin satisfies the
   directive in both dev and production.
2. **No inline script anywhere** (§4.5: "No inline script is used anywhere, so `script-src
   'self'` needs no `unsafe-inline` and no nonce machinery"). `<html lang="en">` is FR-2.24.

⚠️ **The `env` block is load-bearing and was the defect this plan was revised to fix.**
`npm start` is `node server/dist/index.js` with **no** `--env-file` (deliberately — the
container has no `.env`, and Node 22's `--env-file` errors on a missing file). `loadConfig`

base and deviation D-1's iframe proof. Pass the complete `E2E_ENV`.

**Ordering: this configuration deliberately does not depend on whether Playwright runs
`globalSetup` before or after `webServer`.** Playwright's ordering here has changed between
releases and is not worth betting a gate on. Two design choices remove the dependency
entirely:

  is ready whenever the server is ready, regardless of what `globalSetup` did or when;
- the specs read credentials from `e2e/env.ts`, **not** from `process.env` keys that
