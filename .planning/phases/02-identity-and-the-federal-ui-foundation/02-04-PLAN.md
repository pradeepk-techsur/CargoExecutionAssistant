<middleware_order_is_normative>
TechArch §1A.3 fixes the order and explains the one ordering that carries a security
consequence:

```
requestId → headers → bodyLimit(64 KB) → cookieParse → staticAssets
          → session → csrf → routes → htmlRouteGuard → errorMapper
```

**CSRF runs after session because it compares against the session's stored token.** Reversing
them makes the comparison meaningless. `errorMapper` is registered last, as Express's error
middleware. `htmlRouteGuard` runs after the API routes so `GET /api/unknown` produces a JSON
`404` envelope rather than the SPA document (§6.5 "Route order").
</middleware_order_is_normative>

**`server/src/http/session.middleware.ts`** — `sessionMiddleware({ pool, clock })`. Per
request:

1. `parseCookies(req.headers.cookie)[SESSION_COOKIE_NAME]`. Absent ⇒ leave `req.principal`
   undefined and call `next()`. **The middleware never rejects** — rejection is the job of the
   route (`401`) and of `htmlRouteGuard` (`302`), because the two need different responses for
   the same condition (§4.2).
2. `loadSessionByToken(pool, rawToken, clock)`:
   - `VALID` ⇒ attach `req.principal = session.specialist`, `req.sessionId`,
     `req.csrfTokenHash`.
   - `EXPIRED` ⇒ call `expireSession(pool, sessionId, clock)` **at the moment it is rejected**
     so the `sessions` row records what happened (`revoked_at` + `'EXPIRED'`, FR-1.5, §4.2),
     then leave the principal unset.
   - `REVOKED` / `INACTIVE` / `ABSENT` ⇒ leave the principal unset. Do not re-revoke an
     already-revoked session.
3. `last_seen_at` write throttling: when the session is `VALID` and
   `clock.now() - lastSeenAt >= LAST_SEEN_THROTTLE_MS` (60 s), call `touchSession`. Otherwise
   write nothing — §4.2 bounds write amplification to once per 60 s per session.
4. A database error while resolving the session must not 500 the whole origin on a public
   path; log it at `error` with the `request_id` and continue with no principal, so the caller
   gets the normal `401`/`302` rather than a stack-trace-shaped `500`.

`req.principal` is the **sole** source of actor identity in the product (FR-1.6). Add a file
header saying so, and saying that no handler may read an actor from a body, a header or a
query value. Plan 02-09 adds an architecture assertion that greps for exactly that.

**`server/src/http/csrf.middleware.ts`** — `csrfMiddleware()`:
- Applies to `POST`, `PUT`, `PATCH`, `DELETE`. `GET` and `HEAD` are **never** CSRF-checked and
  never change state — an invariant, not a convention (§4.4).
- **Exempt `POST /api/session`**: it creates the session, so there is no session token to
  compare against yet (§4.4, §3.1 shows CSRF "no" for that row).
- For every other state-changing request: read `X-CSRF-Token`, SHA-256 it, and compare the
  32-byte digest against `req.csrfTokenHash` with `crypto.timingSafeEqual`. Guard the length
  first — `timingSafeEqual` throws on unequal lengths — and treat a length mismatch as a
  failure.
- Missing header, no session, or mismatch ⇒ `throw new ApiError(403, 'CSRF_INVALID')`. The
  request never reaches a service, so **no audit entry is written** (§4.4, US-1.2 AC-5).
- Note in the header that this protection is independent of the cookie's `SameSite` value,
  which is what makes deviation D-2 acceptable (§4.4).

**`server/src/http/htmlRouteGuard.ts`** — registered **after** the API routes:

```typescript
export const NEXT_PATH_RE = /^\/[A-Za-z0-9/_\-]*$/;
export function validateNextPath(raw: string | undefined): string;
```
`validateNextPath` returns `raw` when it matches `NEXT_PATH_RE`, otherwise `/queue`. This is
open-redirect prevention (FR-1.7): `//evil.example`, `https://evil.example`,
`/queue?x=1`, `/%2F%2Fevil`, a path with `.` or `:` — all discarded in favour of `/queue`.
Validate the **raw, undecoded** value and reject anything containing `%`, so a
double-encoded escape cannot slip a scheme past the character class.

`htmlRouteGuard()` handles requests that are HTML document requests — i.e. the path does not
start with `/api/`, the method is `GET`, and `Accept` includes `text/html`:

| Condition | Response |
|---|---|
| Protected route, no principal | `302` to `/sign-in?next=` + `encodeURIComponent(validateNextPath(req.path))` |
| `/sign-in`, with a valid principal | `302` to `/queue` |
| `/sign-in`, no principal | pass through to the SPA document |
| static asset path | pass through |
| otherwise, with a principal | pass through to the SPA document |

Requests whose path starts `/api/` or whose `Accept` is `application/json` are **not** handled
here at all — they must have already been answered by a route, or fall through to a JSON `404`
envelope (§4.2's table, §3.7).

**`server/src/http/routes/session.ts`** — the three endpoints, copied from TechArch §3.3 and
FRD Y1 §1. Do not reshape a field name.

```
POST /api/session      — sign in. No auth, no CSRF.
Request   { email, password }
201       { specialist: {id, email, display_name},
            csrf_token, session: {absolute_expires_at} }
          Set-Cookie: cargoexec_sid=<opaque>; HttpOnly; Path=/; SameSite=<profile>; [Secure]
Errors    401 AUTH_FAILED        (unknown email and wrong password are byte-identical)
          403 ACCOUNT_INACTIVE
          422 REQUEST_MALFORMED  (request shape, not credentials)
          429 TOO_MANY_ATTEMPTS  (+ Retry-After)

GET /api/session       — current principal and CSRF token.
200       the same body shape;  401 UNAUTHENTICATED if absent/expired

DELETE /api/session    — sign out. Session + CSRF.
204       cookie cleared, revoked_at/'SIGNED_OUT' recorded
```

Request validation with zod, `.strict()` (§3.2, §4.6):
```typescript
const SignInBody = z.object({
  email:    z.string().trim().max(254),
  password: z.string().min(12).max(256),   // NEVER trimmed (F1 Inputs)
}).strict();
```
`.strict()` is what rejects a client-supplied `specialist_id`, `actor`, `decided_by` or
`on_behalf_of` as an unknown property with `422 REQUEST_MALFORMED` — it is the mechanism
behind criterion 3, not incidental hygiene. Let the `ZodError` propagate; `errorMapper`
already turns it into the envelope with `details[]`.

Two subtleties from the FRD, both of which a naive implementation gets wrong:
- **A present-but-short password must still return the generic `401 AUTH_FAILED`, not a
  length error** (F1 Validation) — otherwise the response describes the stored credential
  policy of an existing account. So `password` is validated for *presence and type* by zod,
  but a length violation is caught and converted to `AUTH_FAILED` rather than
  `REQUEST_MALFORMED`. Implement it by parsing `password: z.string()` in the schema and
  applying the 12–256 bound inside the handler, returning `AUTH_FAILED`.
- **A malformed email is a `422`** (request shape), while an unknown email is a `401`. Validate
  structure — ≤ 254 chars, exactly one `@`, non-empty local part, dot-containing domain — as
  shape; anything that parses is a credential question.

`GET /api/session` returns the same `SessionDto` shape, reading the CSRF token from… nothing:
only its hash is stored. Re-issuing a token on every `GET` would invalidate the one the open
tab holds. Instead, `POST /api/session` returns the CSRF token once and the SPA keeps it for
the life of the page; `GET /api/session` re-issues a **fresh** CSRF token and updates
`sessions.csrf_token_hash` in the same request, so the token the caller receives is the one
that will verify. Document this in the handler: it is the only way to satisfy §3.3's
"re-readable from `GET /api/session`" against a store that holds only hashes, and it is safe
because the token is bound to the session the cookie already proves.

⚠️ **Rotate-on-GET is load-bearing and has a client half. Do not change either without the
other.** §3.3 makes this `GET` the SPA's load-time call ("The SPA calls this on load to choose
between the sign-in screen and the application shell"), so **every page load rotates the
stored hash**. Any token a client held from a previous page is dead the moment the new page
bootstraps. The client half is therefore mandatory: `api.getSession()` must store the returned
`csrf_token` (plan 02-07 Task 1 specifies it inside the client so no caller can forget). If
this rotation is ever "simplified" away — or if the client stops re-storing — a reload
followed by any `POST`/`DELETE` returns `403 CSRF_INVALID` while every in-session test still
passes. State this pairing in the handler comment and in this plan's SUMMARY.

`DELETE /api/session` ⇒ `signOut(pool, req.sessionId)`, set the cleared cookie, `204` with no
body. Revokes only the requesting session (FR-1.11).

`Retry-After` on `429` is the whole-seconds remainder of the throttle window.
