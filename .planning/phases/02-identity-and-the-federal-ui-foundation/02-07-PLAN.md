<objective>
Ship the screen the whole phase is named for: an accessible USWDS sign-in that establishes the
identity every later decision is attributed to — together with the two form components every
later screen inherits, the typed API client, and a browser suite that walks the whole path
with the keyboard alone and inside an IFRAME.

Purpose: Screen-00 states the point plainly — this is "an **accountability** gate, not merely
a security perimeter". Two of its details are counter-intuitive and both are deliberate: the
failure never says which field was wrong, because the server does not distinguish them and the
UI must not imply it does; and neither input receives `aria-invalid`, because marking a field
would leak account information to a screen-reader user that a sighted user does not get.

Output: `SignIn.tsx` on the reduced shell, the inherited `UswdsForm`/`ErrorSummary` pattern,
`api/client.ts`, the header's sign-out wiring, and `e2e/sign-in.spec.ts`.
</objective>

<sign_in_is_the_exception_to_the_error_pattern>
The inherited pattern (§7.6, UX Pattern 2) lists one error-summary item per server finding and
marks each affected control `aria-invalid="true"`. **Sign-in deviates, deliberately, in two
ways** (UX Y2 §4.8, Screen-00 "Accessibility", US-1.1):

1. The summary lists **exactly one** generic item — "Email or password is incorrect." — because
   the server returns one generic credential error.
2. **No input receives `aria-invalid`** and no field-level error styling appears on either
   input. "Announcing an invalid field would leak which one was wrong."

Also per Screen-00's States table: on any failure the **password field is cleared and the email
value is retained**. A failed submission must never cost the specialist the email she typed,
and must never leave her password in the DOM.
</sign_in_is_the_exception_to_the_error_pattern>

<deliberately_absent_on_this_screen>
Screen-00 names each of these and why a reviewer might look for it. **Do not add any of them:**
a "Remember me" checkbox (session lifetime is server-authoritative and non-extendable —
FR-1.3/FR-1.5); a "Forgot password?" link and a "Create account" link (there is no self-service
provisioning and no administrative role — FR-1.13); third-party / PIV / SSO buttons (out of
scope, FR-Y3.8); a "show password" toggle (not required by any story and would be a bespoke
control); a role selector (there is exactly one role — US-1.2). Also absent: product marketing,
screenshots, a "what is CargoExec" blurb, version strings and environment badges — "nothing on
this screen but the accountability gate".

The screen also **never shows a countdown timer**: the 8-hour absolute and 30-minute idle
expiries are server-side, and expiry is explained in words when the specialist arrives here
(Screen-00 "Timing", US-1.4).
</deliberately_absent_on_this_screen>

**`web/src/api/client.ts`** — a typed `fetch` wrapper, per TechArch §1A.4:
- `Accept: application/json` on every request; `Content-Type: application/json` on bodies.
- `credentials: 'same-origin'` so the cookie is sent (and only ever to this origin).
- Attaches `X-CSRF-Token` from the in-memory token to every `POST` and `DELETE`. The token is
  held in a module variable set by `setCsrfToken` — **never** in `localStorage` or
  `sessionStorage`, which are readable by any script and survive the tab.
- Parses the response into the `contract` DTOs. On a non-2xx, parses `ApiErrorBody` and throws
  `ApiClientError` carrying `status`, `code`, `details` and `request_id`. On a network failure
  or unparseable body, throws `ApiClientError` with `code: 'NETWORK'`.
- **On `401 UNAUTHENTICATED`** (FR-1.8, §1A.4): discard in-memory state and navigate to
  `/sign-in?next={current path}` with the announced message "Your session expired. Sign in
  again to continue." Exempt the sign-in call itself — a `401` there is `AUTH_FAILED` and
  belongs to the screen.
- **No retry logic on a mutating request.** An unknown submit outcome advises the specialist to
  reload rather than risking a second submission (§1A.4, UX Pattern 9). Say so in the header;
  later phases rely on it.
- Import request/response types from `@cargoexec/contract` with `import type` and **never**
  re-declare a DTO shape locally (R-L9).

**`web/src/session/SessionProvider.tsx`** — React context over the client:
- On mount, call `GET /api/session`; while it is unresolved the status is `loading` and **no
  protected screen content renders** (FR-2.4 validation: no flash of protected content).
- `signIn(email, password)` → `POST /api/session`, `setCsrfToken(body.csrf_token)`, store the
  specialist, and navigate to the validated `next` or `/queue` (FR-1.21).
- `signOut()` → `DELETE /api/session`, clear the token and the specialist, navigate to
  `/sign-in`, and `announceStatus('You are signed out.')` in the polite region (F1 Process —
  Sign-out step 4, Screen-00 "Signed out" state).
- In-progress form input is **never** retained across re-authentication and never resubmitted
  (FR-1.8) — the provider holds no draft state at all, which is the simplest way to guarantee it.

**`web/src/components/ErrorSummary.tsx`** — the pattern every later screen inherits verbatim
(§7.6, UX Pattern 2, Y2 §4):
- `usa-alert usa-alert--error` composition with `role="alert"` and `tabIndex={-1}`, rendered as
  the **first child of the form region**.
- **Receives focus when it appears** — a `useEffect` on transition-to-visible calling
  `.focus()`. Focus must move *to the summary*, not merely scroll to it.
- One item per error, **in the exact order the server returned them** — the client never
  re-orders, merges, re-words or suppresses.
- Each item is an in-page link; activating it moves focus to the offending control by `id`.
  When an item has no `controlId` (the sign-in case), render it as plain text rather than a
  link that goes nowhere.
- The assertive region announces "{n} problems with your submission" for a multi-item summary;
  for the single generic sign-in item the announcement is "There is a problem with your
  sign-in." (Screen-00 States table). Pass the announcement text in as a prop so each screen
  supplies the right sentence, and announcements never duplicate what focus movement reads.

**`web/src/components/UswdsForm.tsx`**:
- `Field` — `usa-form-group`, `<label class="usa-label" for={id}>` bound to the control's `id`,
  optional hint in `usa-hint` associated via `aria-describedby`, `usa-input`. **Placeholder
  text is never a label and never the only hint** (FR-2.10). Required fields get the USWDS
  required marking (visible `*` plus `required` on the control) and the form states the
  convention above the first field: "A star (*) marks required information." (FR-2.11,
  Screen-00).
- When `invalid` is set, render `usa-error-message` inside `usa-form-group--error`, bound by
  `aria-describedby`, with `aria-invalid="true"` (FR-2.13). SignIn will simply never set it.
- `SubmitButton` — `usa-button`; while `busy`, the visible text changes (e.g. "Signing in…")
  and `aria-disabled="true"` is set. **A second activation is ignored** (FR-1.19, UX Pattern 9).
  Use `aria-disabled` plus a guard in the handler rather than the `disabled` attribute: a
  `disabled` button loses focus and drops out of the tab order mid-interaction, which strands
  a keyboard user.
- The form element carries `noValidate` so native constraint validation can never pre-empt the
  server (FR-1.16, F2 process step 3, Y2 §10). The browser may hint; **the server decides**.
- No colour-only signalling anywhere: an error is carried by the alert's heading text, its icon
  and its position (FR-2.17, Screen-00 "Colour independence").

Tokens only — no raw hex colour and no raw `px` in any of these components (FR-2.2).
