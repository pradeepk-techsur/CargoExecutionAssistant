<the_bootstrap_account_is_not_seed_data>
PRD §10 #7 excludes a **seeded demonstration dataset** — demo cargo entries, cases,
recommendations, decisions, audit history. The repository has no `seeds/` or `fixtures/`
directory and `server/test/architecture/absence.spec.ts` fails the build if one appears or if
any migration gains an `INSERT INTO`.

A specialist account is a different thing. TechArch §8.7 step 5 lists it explicitly as part of
the **deployment sequence**, not the dataset: "create-specialist --email … --display-name …
(password entered interactively). This is the ONLY insert performed operationally; no seed data
is created (§10 #7)."

So this plan runs **that** command — the FR-1.13 operational provisioning path built in plan
02-03 — from the container command in its non-interactive form
(`--from-env --if-absent`), because a human cannot type a password into a `docker compose up`.
It inserts **one row in `specialists`** and touches no other table. When the bootstrap
environment keys are absent it exits 0 and creates nothing.

State this distinction in the README and in the compose file's comment, so a later reader does
not delete it as scope leakage, and does not extend it into one.
</the_bootstrap_account_is_not_seed_data>

<the_compose_file_is_how_the_app_runs>
The compose file in this repository is not documentation of a topology — it is the way the
product is started, for the demonstration and for every later phase's UAT. It must therefore
satisfy the runtime contract, all four points:

1. Every datastore service carries a **pinned image version** (`postgres:16.4` — already
   correct) and a **healthcheck**.
2. The app service declares `depends_on: { db: { condition: service_healthy } }`, publishes
   `ports: ["3000:3000"]`, and takes its connection strings from `environment:` addressing the
   **service name** `db:5432` — never `localhost`, which inside the container is the container
   itself.
3. The app `command` runs **migrate → bootstrap account → serve**, in that order, using the
   project's own tooling, and both of the first two steps are idempotent because the volume
   persists and the command re-runs on every boot.
4. Nothing else is added: **no** message broker, cache, object store, search index, scheduler,
   sidecar or second replica (FR-Y3.12, §8.5). The AI worker of Phase 5 is in-process by
   design, precisely so "an asynchronous actor with more capability than intended" cannot come
   into existence as a separate deployable.
</the_compose_file_is_how_the_app_runs>

<no_health_endpoint_rule>
Do **not** add an HTTP liveness route. §8.6: an HTTP liveness endpoint would be an eleventh
route, and the endpoint inventory is exhaustive at ten by requirement (FR-Y1.1) with an
architecture test pinning it. Liveness is checked **out of band** by
`node server/dist/cli/ping.js`, which opens and closes a database connection and exits
non-zero on failure. §8.6 records this explicitly "so a future reader does not 'fix' the
omission" — keep that sentence in the file.
</no_health_endpoint_rule>

```dockerfile
# prebuild miss compiles rather than failing the image (TechArch §6.2).
RUN apt-get update && apt-get install -y --no-install-recommends \
      python3 make g++ ca-certificates \
 && rm -rf /var/lib/apt/lists/*
COPY package.json package-lock.json ./
COPY contract/package.json contract/
COPY server/package.json server/
COPY web/package.json web/
RUN npm ci
COPY . .
RUN npm run build            # build:server (tsc -b contract server) + build:web

# ---- stage 2: runtime -------------------------------------------------------
FROM node:22.11-bookworm-slim AS runtime
WORKDIR /app
ENV NODE_ENV=production
COPY package.json package-lock.json ./
COPY contract/package.json contract/
COPY server/package.json server/
COPY web/package.json web/
RUN npm ci --omit=dev
COPY --from=build /app/contract/dist  contract/dist
COPY --from=build /app/server/dist    server/dist
COPY --from=build /app/web/dist       web/dist
COPY server/migrations                server/migrations
COPY server/scripts                   server/scripts
EXPOSE 3000
CMD ["node", "server/dist/index.js"]
```

  image; if that fails in this environment, the acceptable fallback is to copy
  `/app/node_modules` from the build stage instead — record which you did in the SUMMARY.
- `server/migrations` and `server/scripts` are copied because the container command runs the
  migration set on boot (§8.7 step 3).
- `web/dist` is copied because Express serves it statically in production (§6.5).
- Keep the base image at `node:22.11-bookworm-slim` and the database at `postgres:16.4` —
  §6.2 pins both, and the database version matters because the governance guarantees rest on
  PostgreSQL 16 features.

Every part of that `command` must be **idempotent**, because the volume persists and the
command re-runs on every boot: `migrate.mjs` is forward-only and records applied migrations in
`schema_migrations`; `create-specialist --from-env --if-absent` uses
`ON CONFLICT (email) DO NOTHING`. A second `docker compose up` must neither fail nor duplicate.

`.env.example` — append the three bootstrap keys with placeholder values and a comment
repeating the not-seed-data distinction. `.env` remains git-ignored.

**The cookie profile, and the one thing most likely to go wrong in the preview.** The default
is `governed` (`SameSite=Lax`, `Secure` only on HTTPS), which is correct when the preview proxy
serves the application **same-origin under a path** — TechArch §4.3's explicit recommendation,
so the D-2 deviation stays documented-but-unused. If the proxy instead embeds the application
from a **different origin**, a `Lax` cookie is not sent at all on the framed navigation and
sign-in becomes impossible with no visible cause. The remedy is
`SESSION_COOKIE_PROFILE=demo-iframe`, which requires an HTTPS origin — and `loadConfig` refuses
to start if it is combined with plain HTTP, precisely so the failure is loud rather than a
silently dropped cookie. Record both facts in the README and in a comment beside the variable.
CSRF protection does not depend on `SameSite` (§4.4), so neither profile weakens it.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| host→container | Environment values (connection strings, bootstrap credentials, cookie profile) crossing into the running application |
| container→db | The application's connection to the database over the compose network |
| internet/proxy→app | The published port 3000 and the preview proxy's framed requests |
| build→image | Repository content crossing into the shipped image |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-51 | Information disclosure | `.dockerignore` / image contents | mitigate | `.env`, `.git`, `node_modules` and local build output are excluded from the build context, so no local secret or stale artefact is baked into the image; secrets reach the container only through `environment:` (§4.7, FR-Y3.13) |
| T-02-52 | Information disclosure | `server/src/cli/ping.ts` failure output | mitigate | The failure path logs the error class and exits 1 without printing `DATABASE_URL_APP` or any connection string, matching the rule established for `config.ts` (§4.7) |

| T-02-54 | Spoofing | A well-known bootstrap password in `.env.example` and the compose default | accept | Owned by the demonstration posture: the stack is a local/sandbox demonstration with no public exposure, and the README names the variable to change. The alternative — refusing to boot without a supplied password — would leave a sign-in screen nobody can sign into, which fails the walkthrough outright.
