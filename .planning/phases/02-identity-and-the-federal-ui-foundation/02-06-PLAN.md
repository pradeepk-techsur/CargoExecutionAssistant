<objective>
Prove the three governance properties this phase exists to establish, as permanent regression
assets: that nothing reaches case data without identification (criterion 2), that the actor on
a request is the server-resolved specialist and cannot be renamed by the caller (criterion 3),
and that a session ends on its own terms and the record says how (criterion 1).

Purpose: this is the Phase 2 analogue of Phase 1's refusal suites. Phase 1 did not merely
build an append-only store — it deliberately mis-wrote transactions and watched the database
refuse them. The same standard applies here. It is not enough that the middleware is written
correctly today; the attempt must be made, in a test, and observed to fail. These three files
are the executable form of three of the phase's five success criteria, and every later phase
re-runs them.

Output: three supertest suites on the plan 02-04 harness — no production code changes.
</objective>

This is the Phase 2 analogue of Phase 1's HITL refusal tests: the attempt to name a different
actor is **made**, and observed to be refused or ignored. State that in the file header.

Phase 2's HTTP surface is three endpoints, so enumerate the actor-naming vectors that are
actually reachable on it and close every one. Set up two specialists — **A** (who signs in)
and **B** (whom the request tries to name) — once per suite.

**Vector 1 — a body property.** `POST /api/session` with a body containing, one at a time:
`specialist_id: B.id`, `actor: B.id`, `decided_by: B.id`, `on_behalf_of: B.id`, `origin: 'AI'`,
`applied: true`. Each ⇒ `422 REQUEST_MALFORMED` with a `details[]` entry naming the offending
property, and **no session created** (assert `SELECT count(*) FROM sessions` is unchanged).
This is zod `.strict()` doing exactly the job §3.2 assigns it: "This is the mechanism that
blocks a client-supplied `origin`, `decided_by`, or `applied`." Silent ignoring never occurs.

**Vector 2 — a request header.** Sign in as A, then call `GET /api/session` with
`X-Actor-Id: B.id`, and separately with `X-Specialist-Id: B.id`, `X-On-Behalf-Of: B.id` and
`X-User: B.email`. Each ⇒ `200` whose body names **A**, not B. The header is ignored, because
nothing reads it.

**Vector 3 — a second cookie.** Call `GET /api/session` with A's valid `cargoexec_sid` plus a
forged `specialist_id=<B.id>` cookie, and separately with a `cargoexec_sid` for A followed by
a second `cargoexec_sid=<B's token>` in the same header. Assert the resolved principal is
deterministic and is A in the first case; in the second, assert it is one of the two real
sessions and never a blend — the point being that a session token is opaque and resolves to
exactly the specialist its row references, so a token belonging to A can never resolve to B.

**Vector 4 — a query parameter.** `GET /api/session?specialist_id=<B.id>` ⇒ `200` naming A.
(The whole API accepts zero query parameters — FR-Y1.2 — and the endpoints that reject them
outright arrive in Phase 4; here the assertion is simply that the parameter cannot influence
identity.)

**Vector 5 — B's own valid session is not A's.** Sign in as B in a second context; `GET
/api/session` with B's cookie names B. This is the positive control that makes the four
negative assertions meaningful: the resolution works, and it works *from the cookie*.

**Structural assertion — no code path reads a client-supplied actor.** A source scan over
`server/src/**/*.ts` asserting that none of the strings
`req.body.actor`, `req.body.decided_by`, `req.body.specialist_id`, `req.body.on_behalf_of`,
`req.headers['x-actor`, `req.headers['x-specialist`, `req.query.specialist`
appears outside a comment. TechArch §4.9 pairs the API test with exactly this
"schema/grep test", because a behavioural test proves today's routes and a source assertion
proves the next one added.

**The forward contract.** Add a comment block, not a skipped test, recording what this suite
will be extended with when the audited endpoints exist: F13's `audit_entries.actor_specialist_id`
must equal the signed-in specialist, and `decisions.decided_by` likewise (Phase 3 for the
receipt path, Phase 6 for the decision path). Name both phases. Phase 1's convention is that
a deferred assertion is a comment naming its owning phase, never a skipped test, because a
skipped test reads as coverage it does not have.

  <feature_dependencies>Implements: F1 FR-1.5, FR-1.8, FR-1.9, FR-1.11, FR-1.12, acceptance 4, 5, 6; TechArch §4.9 rows 3–5, §8.3 test:api "Auth"; US-1.4 · Depends on: 02-04 · Enables: the phase criterion-1 evidence</feature_dependencies>

Every time-dependent assertion uses the harness's `fixedClock`. **No test in this file waits
in real time**; §8.2 requires an injected clock precisely so a 31-minute idle expiry costs
milliseconds. Where a scenario is easier to express by writing the row directly (e.g. forcing
`last_seen_at` into the past), do that instead and say which mechanism each test uses — both
are legitimate, and stating it keeps the suite readable.

1. **Idle expiry** (FR-1.5, acceptance 5, §4.9 row 3). Sign in; advance the clock 30 minutes
   and 1 millisecond; call `GET /api/session`. Assert `401 UNAUTHENTICATED`, **and** read the
   row back: `revoked_at IS NOT NULL` and `revocation_reason = 'EXPIRED'`. Recording the
   expiry is as much of the requirement as refusing the request — §4.2: "so the `sessions`
   table records what happened".

2. **Idle expiry does not fire early.** Advance 29 minutes; the request still returns `200` and
   the row is **not** revoked. Without this, a test that always expires would pass for the
   wrong reason.

3. **`last_seen_at` throttling** (§4.2). Make two requests 10 seconds apart (clock-advanced);
   assert `last_seen_at` was written at most once — the second request inside the 60-second
   window does not write. Then advance past 60 seconds, make a third request, and assert it
   did write. This is the write-amplification bound, and it is also why idle expiry is measured
   from `last_seen_at` rather than from the last request.

4. **Idle expiry is measured from activity.** Make a request every 20 minutes (clock-advanced)
   four times; the session is still valid after 80 minutes, because each request refreshed
   `last_seen_at`.

5. **Absolute expiry** (FR-1.5, acceptance 4 of US-1.4). With continuous activity — a request
   every 20 minutes — advance past 8 hours from `created_at`. The next request returns `401`
   **regardless of activity**, and the row is marked `'EXPIRED'`. The absolute limit is not
   extendable; this is the test that distinguishes it from the idle limit.

6. **Sign-out** (acceptance 6). `DELETE /api/session` with cookie and `X-CSRF-Token` ⇒ `204`;
   the row carries `revocation_reason = 'SIGNED_OUT'`; the `Set-Cookie` clears the cookie.
   Replaying the same cookie on `GET /api/session` ⇒ `401` (§4.9 row 5).

7. **Sign-out revokes only the requesting session** (FR-1.11). Two sign-ins for one specialist;
   sign out of the first; the second still returns `200`. Two rows exist and only one is
   revoked.

8. **An expired session's reason is not overwritten.** Let a session expire (recorded
   `'EXPIRED'`), then attempt `DELETE /api/session` with the stale cookie ⇒ `401`, and the row
   still reads `'EXPIRED'`. The record should say what actually happened first.

9. **CSRF refusal writes nothing** (FR-1.9, acceptance 4, §4.9 row 2). `DELETE /api/session`
   **without** `X-CSRF-Token` ⇒ `403 CSRF_INVALID` with the Y2 §1 message verbatim; the session
   is **still valid** afterwards (`GET /api/session` ⇒ `200`); and `SELECT count(*) FROM
   audit_entries` is `0`. Repeat with a **wrong** `X-CSRF-Token` and with a token belonging to
   a *different* session — both `403`.

10. **`GET` is never CSRF-checked** (§4.4). `GET /api/session` with no `X-CSRF-Token` ⇒ `200`.
    This is an invariant, not a convention: there is no `GET` endpoint that writes.

11. **Session events write no audit entry** (FR-1.12). After the whole suite has signed in,
    expired, signed out and been refused, assert `audit_entries` and `audit_entry_values` are
    both still empty. Session history lives on `sessions`; this is a boundary, not a gap.
  </action>
