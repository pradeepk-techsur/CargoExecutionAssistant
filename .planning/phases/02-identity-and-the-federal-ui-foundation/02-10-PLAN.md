<objective>
Close UAT gap ref 1: the shipped runtime posture issues an iframe-hostile session
cookie, so sign-in succeeds server-side (201) and then appears to fail inside the
Pivota Preview panel with no visible cause.

The application code is already correct — `cookies.ts` emits `SameSite=None;
Secure` under `demo-iframe`, and `config.ts` correctly refuses that profile over
plain HTTP. The defect is entirely the shipped *default*: `docker-compose.yml`
ships `SESSION_COOKIE_PROFILE=governed` with `PUBLIC_ORIGIN=http://localhost:3000`,
so the deployed stack takes the `Lax`/no-`Secure` branch, and a browser drops that
cookie on a cross-site framed navigation.

This plan does NOT simply flip the default to `demo-iframe`. That would make
`loadConfig` throw at boot for anyone running the documented plain-HTTP
`http://localhost:3000` path (config.ts self-check 4), trading one broken
environment for another. Instead it adds a third, self-resolving profile —
`auto` — that decides `SameSite`/`Secure` from the scheme the request actually
arrived on, and makes that the shipped default. Both environments then work from
one unchanged compose file, and the residual misconfiguration (an HTTPS proxy
that forwards no `X-Forwarded-Proto`) is named in a log line instead of vanishing
into a silently dropped cookie.

Purpose: criterion 1 of this phase — "a specialist signs in … and reaches the
application" — is currently false in the only environment the walkthrough
actually happens in.
Output: a three-valued `SESSION_COOKIE_PROFILE`, per-request cookie posture
resolution, a permanent regression suite reproducing both postures, and a
compose/README/.env default that no longer takes the iframe-hostile branch.
</objective>

**`server/src/http/cookies.ts`** — replace the private `sameSiteAndSecure(config)`
with an exported, request-aware resolver. Keep `SESSION_COOKIE_NAME`,
`parseCookies` and the always-fixed attribute set (HttpOnly, Path=/, no Domain,
no Max-Age/Expires on the set cookie) exactly as they are.

```ts
/** The minimal request shape the posture needs. Structural, so unit tests need no Express. */
export interface CookieRequest {
  /** Express's req.secure — true when the request arrived over TLS, including
   *  via X-Forwarded-Proto because app.ts sets `trust proxy`. */
  secure?: boolean;
  header?(name: string): string | undefined;
}

export interface CookiePosture {
  sameSite: 'Lax' | 'None';
  secure: boolean;
  /** True when a browser will DROP this cookie inside a cross-site frame. */
  iframeHostile: boolean;
}

export function resolveCookiePosture(
  config: AppConfig,
  req?: CookieRequest,
): CookiePosture;
```

Resolution rule — implement exactly this, no other branches:

| profile | posture |
|---|---|
| `demo-iframe` | `{ sameSite: 'None', secure: true, iframeHostile: false }` — unchanged; `loadConfig` already refused a non-HTTPS origin |
| `governed` | `{ sameSite: 'Lax', secure: config.originIsHttps, iframeHostile: true }` — byte-identical to today's behaviour |
| `auto` | `overHttps = req?.secure === true \|\| config.originIsHttps`; `overHttps ? { sameSite: 'None', secure: true, iframeHostile: false } : { sameSite: 'Lax', secure: false, iframeHostile: true }` |

`iframeHostile` is definitionally `sameSite === 'Lax'`.

Read the scheme ONLY from `req.secure` — never from a raw `X-Forwarded-Proto`
header read here. `req.secure` is the value Express derives under the
`trust proxy` setting established in `app.ts`; reading the header directly would
bypass that policy.

Under `auto` over plain HTTP the emitted bytes are IDENTICAL to today's
`governed`-over-http output. That is deliberate: it is what keeps the existing
e2e suite, `server/test/api/session.spec.ts` test 1 and the documented local demo
unchanged.

Add an exported predicate for the diagnostic:

```ts
/** True when the request looks like it came from a cross-site or framed context
 *  (Sec-Fetch-Site / Sec-Fetch-Dest, set by the browser and not settable by page
 *  script). Used ONLY to log a warning — never to decide cookie attributes. */
export function looksCrossSite(req?: CookieRequest): boolean;
```

Return true when `sec-fetch-site` is `cross-site` or `same-site`, or when
`sec-fetch-dest` is `iframe`.

Widen both builders to take the request:

```ts
export function buildSessionCookie(token: string, config: AppConfig, req?: CookieRequest): string
export function buildClearedSessionCookie(config: AppConfig, req?: CookieRequest): string
```

`req` is OPTIONAL so every existing two-argument call site and unit test keeps
compiling and keeps asserting the same contract. Both builders call
`resolveCookiePosture` — the CLEARED cookie must carry the same SameSite/Secure
as the cookie it replaces, or a browser on an HTTPS origin will refuse the
non-Secure clear and the session cookie will linger.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API | Sign-in and sign-out request data (`POST`/`DELETE /api/session`) crossing into the session handlers, which mint and clear the credential cookie |
| proxy→API | `X-Forwarded-Proto`, `Sec-Fetch-Site` and `Sec-Fetch-Dest` — headers set by an intermediary or a browser, now consulted when shaping a security-relevant response header |
| API→client | The `Set-Cookie` response header itself: the one place the session credential leaves the server |
| API→logs | The new boot-posture and cross-site warning lines, written by a logger that also handles credentials |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-40 | Tampering (cross-site request forgery) | `server/src/http/cookies.ts::resolveCookiePosture` emitting `SameSite=None` under `auto` over HTTPS — the cookie is now sent on cross-site requests, removing the SameSite brace | mitigate | The double-submit token in `server/src/http/csrf.middleware.ts` is the actual CSRF control and is independent of `SameSite` (§4.4, deviation D-2): every state-changing method bar `POST /api/session` must present `X-CSRF-Token` whose SHA-256 equals `sessions.csrf_token_hash`, compared with `crypto.timingSafeEqual`. This plan changes nothing in that middleware; Task 2's `cookiePosture.spec.ts` assertion 3 exercises `DELETE /api/session` WITH the rotated token under the `None` posture, so a regression that broke the pairing fails there. |
| T-02-41 | Information disclosure | The session cookie transmitted without `Secure` on a plain-HTTP origin (`auto`/`governed` over http) — readable by a network observer | accept | §4.8 explicitly permits plain HTTP for a local demonstration, and the alternative is worse: a `Secure` cookie on an `http:` origin is silently discarded by the browser, making sign-in impossible with no diagnosable cause. Residual risk is owned by the demonstration operator and is stated out loud at boot by the `logger.warn` in `server/src/index.ts` (Task 1) naming the reduced posture. Not carried into any HTTPS deployment: over HTTPS `auto` emits `Secure`. |
| T-02-42 | Spoofing | A direct client forging `X-Forwarded-Proto: https` on a plain-HTTP connection, since `server/src/http/app.ts` sets `trust proxy: true` for all peers, causing `Secure` to be emitted on a non-TLS connection | mitigate | `resolveCookiePosture` reads the scheme ONLY from `req.secure` — the value Express derives under the app's `trust proxy` policy — and never from a raw header read in `cookies.ts`, so the trust decision stays in one place. The effect of a successful forge is confined to the forging client: their own browser drops the `Secure` cookie on the non-TLS connection. No other user's session, cookie value or session binding is affected, and the token remains server-generated and session-bound in `services/session.service.ts`. |

The pre-existing per-email throttle in `server/src/services/session.service.ts` continues to bound sign-in attempts independently. |
