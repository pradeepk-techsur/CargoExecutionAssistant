<objective>
Build the identity half of F1 below the HTTP layer: the two repositories, the session service
that verifies a credential and mints a session, and the operational CLI that is the only way
an account comes into existence.

Purpose: this is where the phase's central claim is made good — that every decision taken
from here on names a real accountable person. It is made good by three specific properties,
each of which is a design decision rather than a coding detail: the raw session token exists
only in the client's cookie, an unknown email is indistinguishable from a wrong password, and
there is no self-registration, no password reset and no user-administration surface because
each of those would be an administrative role the product deliberately does not have.

Output: `clock.ts`, `db/repositories/{specialists,sessions}.ts`, `services/session.service.ts`,
`cli/create-specialist.ts`, a reusable specialist fixture, and a database-backed suite that
proves sign-in, sign-out, expiry recording and throttling against a real PostgreSQL.
</objective>

<schema_is_already_built_rule>
`specialists` and `sessions` were created by migration `0001_identity.sql` in phase 1. **Do
not write a migration in this plan.** The DDL below is the shipped schema, reproduced here so
every column name and constraint in your SQL is exact:

```sql
CREATE TABLE specialists (
  id               uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  email            text NOT NULL,
  display_name     text NOT NULL,
  password_hash    text NOT NULL,
  is_active        boolean NOT NULL DEFAULT true,
  created_at       timestamptz NOT NULL DEFAULT now(),
  last_sign_in_at  timestamptz,
  CONSTRAINT specialists_email_lower_chk CHECK (email = lower(email)),
  CONSTRAINT specialists_email_len_chk   CHECK (char_length(email) BETWEEN 3 AND 254),
  CONSTRAINT specialists_name_len_chk    CHECK (char_length(btrim(display_name)) BETWEEN 1 AND 120)
);
CREATE UNIQUE INDEX uq_specialists_email ON specialists (email);

CREATE TABLE sessions (
  id                  uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  specialist_id       uuid NOT NULL REFERENCES specialists (id),
  token_hash          bytea NOT NULL,
  csrf_token_hash     bytea NOT NULL,
  created_at          timestamptz NOT NULL DEFAULT now(),
  absolute_expires_at timestamptz NOT NULL,
  last_seen_at        timestamptz NOT NULL DEFAULT now(),
  revoked_at          timestamptz,
  revocation_reason   text,
  user_agent          text,
  CONSTRAINT sessions_token_hash_len_chk CHECK (octet_length(token_hash) = 32),
  CONSTRAINT sessions_csrf_hash_len_chk  CHECK (octet_length(csrf_token_hash) = 32),
  CONSTRAINT sessions_revocation_chk CHECK (
    (revoked_at IS NULL AND revocation_reason IS NULL) OR
    (revoked_at IS NOT NULL AND revocation_reason IN ('SIGNED_OUT','EXPIRED'))
  ),
  CONSTRAINT sessions_expiry_after_creation_chk CHECK (absolute_expires_at > created_at)
);
CREATE UNIQUE INDEX uq_sessions_token_hash ON sessions (token_hash);
CREATE INDEX idx_sessions_specialist ON sessions (specialist_id);
```

Note what the schema dictates and your code must match: `token_hash` and `csrf_token_hash` are
`bytea` of **exactly 32 bytes** (raw SHA-256 digests, not hex strings — pass a `Buffer`);
`revocation_reason` accepts only `'SIGNED_OUT'` or `'EXPIRED'` and only together with
`revoked_at`; there is **no** `role`, `is_supervisor`, `permissions` or `scope` column and
none may be added (FR-1.1, and `server/test/architecture/schema.spec.ts` fails the build on
any of the twenty-five forbidden column names).

Privileges (migration 0008): `cargoexec_app` holds `SELECT, INSERT, UPDATE` on `specialists`
and `sessions`; `cargoexec_ai` holds **nothing at all** on either — the worker cannot read a
specialist identity. Use the **app** pool for everything in this plan; the CLI uses the
**owner** connection string because it runs operationally, outside the request path.
</schema_is_already_built_rule>

<no_orm_rule>
Hand-written parameterised SQL only. Every value is a `$n` placeholder; no template-literal
interpolation of any value anywhere under `server/src/`. Do not add `prisma`, `typeorm`,
`sequelize`, `knex`, `drizzle-orm` or `mikro-orm` — an ORM's dirty-flush is exactly the
mechanism that would emit an `UPDATE` against an append-only table (R-L8, PRD R-4).
Transactions, where needed, go through `withTransaction` from `server/src/db/tx.ts`: it is the
only place a `BEGIN` may appear (R-L2, asserted by `test:arch`).
</no_orm_rule>

<no_audit_entry_rule>
Sign-in, sign-out and expiry write **no** `audit_entries` row (F1 FR-1.12, F13 §Boundary,
TechArch §3.3). `audit_entries.case_id` is `NOT NULL` and no case state changes at
authentication; session history lives on `sessions`. This is a boundary, not a gap — do not
"improve" it by calling `append()`. A test in this plan asserts the audit tables are still
empty after a full sign-in / sign-out / expire cycle.
</no_audit_entry_rule>

**`server/src/services/session.service.ts`** — the only module in the product that verifies a
credential. It imports `express` nowhere (R-L1: a service never imports `express`).

**Constants**, named and exported so the middleware and the tests share one definition:

export const SESSION_ABSOLUTE_MS   = 8 * 60 * 60 * 1000;   // FR-1.5
export const SESSION_IDLE_MS       = 30 * 60 * 1000;       // FR-1.5
export const LAST_SEEN_THROTTLE_MS = 60 * 1000;            // §4.2

**`signIn(pool, { email, password, userAgent }, clock = systemClock)`** — implement the F1
"Process — Sign-in" steps in this exact order:

1. Normalise the email: `email.trim().toLowerCase()`.
2. **Throttle check first.** Look up the in-process counter keyed by
   `sha256(normalisedEmail)` (never the email itself — §4.2: "keyed by a hash of the email").
   If ≥ 5 failures inside the rolling 15-minute window, return
   `{ ok:false, reason:'TOO_MANY_ATTEMPTS', retryAfterSeconds }` **without** touching the
   database, identically whether or not that email exists (FR-1.10, US-1.5).
3. `findSpecialistByEmail`.
4. **Verify the password with Argon2id in both branches.** When no row was found, verify
   against a module-level `DUMMY_HASH` — a real Argon2id hash of a fixed throwaway string,
   computed once lazily at module init at the same parameters. The comparison result is
   discarded; the point is that the elapsed time is the same (FR step 4, §4.2, T-6).
   Parameters: `type: argon2.argon2id, memoryCost: 19456 (19 MiB), timeCost: 2,
   parallelism: 1` — FR-1.4's floor. Wrap `argon2.verify` in try/catch and treat a throw as a
   failed verification: a corrupt stored hash must be a generic `401`, not a `500` that
   discloses the row exists.
5. On verification failure: increment the throttle counter and return
   `{ ok:false, reason:'AUTH_FAILED' }`. **Unknown email and wrong password return the same
   value** — the route turns both into a byte-identical body (US-1.1, AC-3).
6. `is_active === false` ⇒ `{ ok:false, reason:'ACCOUNT_INACTIVE' }`. Note the ordering: the
   password is verified *before* the activity check, so a deactivated account cannot be probed
   by response timing either.
7. Mint the session:
   - `token = randomBytes(32)` → the raw value returned to the caller as
     `token.toString('base64url')`; `token_hash = sha256(rawTokenString)` as a 32-byte `Buffer`.
   - `csrfToken` the same way, independently; store `csrf_token_hash`.
   - `created_at = clock.now()`, `absolute_expires_at = created_at + SESSION_ABSOLUTE_MS`,
     `last_seen_at = created_at`, `user_agent` truncated to 512 chars (or `null`).
   - **Hash the string form, not the buffer**, and do the same on the lookup path — a mismatch
     between "hash of bytes" and "hash of the base64url text" would make every session lookup
     miss, and the failure mode (silent sign-out on the next request) is hard to diagnose.
8. Reset the throttle counter for that key and `touchLastSignIn`.
9. Return `{ ok:true, specialist: {id,email,display_name}, sessionId, token, csrfToken,
   absoluteExpiresAt }`. The raw `token` and `csrfToken` leave this function **once** and are
   never stored, logged or returned again (FR-1.2, FR-1.14).

**`loadSessionByToken(pool, rawToken, clock)`** — the resolution the middleware calls:
- `findSessionByTokenHash(sha256(rawToken))`; `null` ⇒ `{ state:'ABSENT' }`.
- `revoked_at !== null` ⇒ `{ state:'REVOKED' }`.
- `now > absolute_expires_at` **or** `now > last_seen_at + SESSION_IDLE_MS` ⇒ `{ state:'EXPIRED' }`.
- `specialist.is_active === false` ⇒ `{ state:'INACTIVE' }`.
- otherwise `{ state:'VALID', session: { sessionId, specialist, lastSeenAt,
  absoluteExpiresAt, csrfTokenHash } }`.

It does **not** write. Recording the expiry is `expireSession`, called by the middleware, so
this function stays safe to call from a read path.

**`expireSession(pool, sessionId, clock)`** ⇒ `revokeSession(..., 'EXPIRED', clock.now())`.
**`signOut(pool, sessionId, clock)`** ⇒ `revokeSession(..., 'SIGNED_OUT', clock.now())`.
**`touchSession(pool, sessionId, at)`** ⇒ `updateLastSeen`; the caller decides whether the
60-second throttle has elapsed.

**Throttle store** — an in-process `Map<string, { failures: number[]; }>` holding failure
timestamps, pruned on read. §4.2 is explicit that this is "**not** a table, **not** account
state: there is no lockout flag and no unlock surface, because there is no administrative
role". Do not add a `specialists.locked_until` column; `schema.spec.ts` would fail the build
and the requirement forbids it anyway. Export `__resetThrottle()` for tests and a
`throttleState(emailHash)` reader; keep the map module-local otherwise.

**`server/test/unit/throttle.spec.ts`** — pure unit test of the throttle with an injected

- 4 failures then a 5th all return a count below the limit; the 6th attempt is throttled.

- A successful sign-in resets the counter (test the reset function directly).
- Two different emails have independent counters.
- The map key is a hash: assert that no key in the exported state reader equals a plaintext
  email string.
