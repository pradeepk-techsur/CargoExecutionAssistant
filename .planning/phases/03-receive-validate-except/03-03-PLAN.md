<objective>
Close the Phase 2 carry-forward: add `requireApiAuth` after `sessionMiddleware`
and before `csrfMiddleware`, so any `/api/*` request except `POST /api/session`
with no principal answers `401 UNAUTHENTICATED` — then tighten `guard.spec`'s
four weakened assertions back to 401.

Purpose: STATE.md records Phase 2 criterion 2 as only PARTIALLY evidenced. Today
only `GET /api/session` answers 401 unauthenticated; `DELETE /api/session`
answers `403 CSRF_INVALID` (CSRF runs first) and the seven unimplemented pairs
answer `404 ENTRY_NOT_FOUND` (no handler). **This matters to Phase 3 directly:**
plan 03-06 implements `POST /api/entries` — the first `/api` route that writes
case data — and this phase's own criterion 4 requires that *no API shape* can
author an exception. Shipping a cargo-entry POST behind no auth gate would create
exactly the hole Phase 2 left open, so closing it is in-scope here and must land
in Wave 1, **before** any route flips to `implemented: true`.

Output: one small middleware, one wiring line in `app.ts`, and a `guard.spec`
that now proves the uniform 401 the phase-2 must_have asked for.

This plan is deliberately independent of every other Phase 3 plan: it touches
`app.ts` and `guard.spec.ts`, which no other Phase 3 plan touches.
</objective>

Create `server/src/http/requireApiAuth.ts`:

```typescript
/**
 * The API authentication gate (F1 FR-1.7, TechArch §4.2).
 *
 * `sessionMiddleware` deliberately NEVER rejects — it only attaches
 * `req.principal`, because the same condition needs two different answers: a
 * protected API route answers 401 UNAUTHENTICATED, an HTML document request
 * answers 302 to /sign-in. This middleware is the API half of that split, and
 * `htmlRouteGuard` is the document half.
 *
 * ORDER IS LOAD-BEARING: this runs AFTER sessionMiddleware (it reads the
 * principal that middleware attached) and BEFORE csrfMiddleware. Running it
 * after CSRF would answer `403 CSRF_INVALID` to a caller whose real problem is
 * that they have no session — which is what plan 02-04 shipped and what plan
 * 02-06 recorded as the phase-2 carry-forward.
 *
 * POST /api/session is the sole exemption: it CREATES the session, so requiring
 * one would make sign-in unreachable.
 *
 * Refusal is UNIFORM across every /api path — implemented, not-yet-implemented,
 * and unknown alike. That is deliberate: an anonymous caller must not be able to
 * probe which /api paths exist by comparing a 404 against a 401 (information
 * disclosure). The 404/405 distinction is for AUTHENTICATED callers, where it is
 * useful and discloses nothing.
 */
import type { RequestHandler } from 'express';
import { ApiError } from './errorMapper.js';

export function requireApiAuth(): RequestHandler {
  return (req, _res, next) => {
    if (!req.path.startsWith('/api/') && req.path !== '/api') {
      return next();
    }
    if (req.method.toUpperCase() === 'POST' && req.path === '/api/session') {
      return next();
    }
    if (req.principal !== undefined) {
      return next();
    }
    return next(new ApiError(401, 'UNAUTHENTICATED'));
  };
}
```

Notes for the implementer:
- Read the exact `req.principal` property name and its type from
  `server/src/http/session.middleware.ts` (it augments the Express `Request`);
  use that declaration, do not re-augment.
- `ApiError(401, 'UNAUTHENTICATED')` routes the refusal through `errorMapper`,
  the single §3.7 translation point, so the envelope, the `request_id`, the
  `Cache-Control: no-store` and the absence of `Location` /
  `WWW-Authenticate` all come from the code already in place. Do **not** write
  a `res.status(401).json(...)` here — that would be a second translation point.
- Match on `req.path`, not `req.originalUrl`, and compare the method
  case-insensitively.
- The gate MUST NOT read an actor identifier from a header, a body property or a
  query value. `req.principal` is the sole source of actor identity in the
  product (FR-1.6), and plan 02-09's architecture scan fails the build on the
  forging shape.

Then wire it into `server/src/http/app.ts`. The normative order becomes:

```
requestId → headers → bodyLimit(64KB) → [static] → session → requireApiAuth
          → csrf → routes (+ /api 404, +405) → htmlRouteGuard → [SPA fallback]
          → errorMapper
```

Insert `app.use(requireApiAuth());` immediately after
`app.use(sessionMiddleware({ pool, clock }));` and immediately before
`app.use(csrfMiddleware());`, renumber the step comments (the new step 5a or a
renumber to 6, whichever keeps the block readable), and update the ASCII order
diagram in the file header **and** the `@param`-style order comment on
`createApp` so the normative order documented in the file matches the code. A
future reader must not have to diff the comment against the calls.

Static asset serving stays BEFORE the gate: `/assets/*.js` is not under `/api`,
so the SPA bundle is still served to an unauthenticated browser — which it must
be, because the sign-in screen is part of that bundle.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| client→API | Every `/api/*` request from an unauthenticated or forged caller crossing into the handler chain. This plan is the gate on that boundary. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-11 | Elevation of privilege | `http/requireApiAuth.ts` mounted in `http/app.ts` — an anonymous caller reaching a protected handler | mitigate | The gate refuses every `/api/*` request with `req.principal === undefined` before route matching, exempting only `POST /api/session`. It is positioned after `sessionMiddleware` (which attaches the principal) and before `csrfMiddleware` and the router; Task 1's verify asserts that index ordering in `app.ts`, and `guard.spec` case 6 fails if a refactor moves it after CSRF. |
| T-03-12 | Spoofing | `http/requireApiAuth.ts` — forging identity to satisfy the gate | mitigate | The gate reads `req.principal` and nothing else — no header, no body property, no query value. `req.principal` is resolved from the `cargoexec_sid` cookie alone by `session.middleware.ts` (FR-1.6), and plan 02-09's architecture scan over `server/src` already fails the build on an actor identifier read from caller-controlled input. |
| T-03-13 | Information disclosure | `http/requireApiAuth.ts` — path-existence probing by an anonymous caller | mitigate | The refusal is uniform across implemented, unimplemented and unknown `/api` paths, so a `401` never distinguishes them. Asserted by `guard.spec` case 4 (all nine non-sign-in pairs) and case 5 (`/api/unknown-path`). The 404/405 distinction survives only for authenticated callers, to whom it discloses nothing. |
| T-03-14 | Information disclosure | `http/errorMapper.ts` — the 401 envelope | mitigate | The refusal is raised as `ApiError(401, 'UNAUTHENTICATED')` and formatted by `errorMapper`, the single §3.7 translation point, so the body is exactly `{code, message, request_id}` with no `details`, no stack, no SQL. `guard.spec` case 4 asserts the exact key sets on both the body and the error object. |
| T-03-15 | Denial of service | `http/requireApiAuth.ts` | accept | The gate performs no I/O — it is a synchronous property read, and it runs *before* CSRF's constant-time compare and before any route handler, so it strictly reduces work done for an anonymous request. Residual risk owned by the phase: rate limiting on `POST /api/session` already exists (F1 throttle) and no other endpoint is anonymously reachable. |
</threat_model>
