<objective>
Implement the two F3 endpoints and register them: `POST /api/entries` (receive one
manually authored entry) and `GET /api/entries/{entryId}` (retrieve one entry with
its derived state). Flip exactly those two rows of `API_ROUTE_TABLE` to
`implemented: true`, and prove the contract with supertest.

Purpose: this is where the receipt becomes reachable, and where the line between
*structural* validation (a client error) and *required-information* validation (a
business outcome) is drawn. The FRD is emphatic: **no error code in F3's table is
produced by a required-information failure.** A validation failure is a `201`
with `receipt_outcome: "EXCEPTION_OPENED"` — a successful receipt with a business
outcome, not an error. The screen (plans 03-09/03-10) depends entirely on that.
Output: `routes/entries.ts`, the updated route registry, an api-tier spec, and
`boot.spec.ts` updated from three registered routes to five.

**Do not add an eleventh route.** `API_ROUTE_TABLE` stays at exactly ten rows —
`guard.spec.ts` case 1 and plan 03-04's `validation.spec.ts` both assert that,
and "anything not on this list does not exist" is the §3.1 contract. This plan
changes two `implemented` flags and adds two handlers, nothing else.
</objective>

**The structural schema — zod `.strict()`.** Every one of the fourteen fields is
**optional at the transport layer**; this is deliberate and central, not lax. The
schema's job is shape only:

```typescript
const numericish = z.union([z.string(), z.number()]);

const EntryBody = z
  .object({
    entry_number: z.string().max(20).nullish(),
    importer_of_record_id: z.string().max(20).nullish(),
    port_of_entry_code: z.string().max(8).nullish(),
    mode_of_transport: z.string().max(16).nullish(),
    carrier_code: z.string().max(8).nullish(),
    conveyance_name: z.string().max(100).nullish(),
    bill_of_lading_number: z.string().max(40).nullish(),
    air_waybill_number: z.string().max(20).nullish(),
    country_of_origin_code: z.string().max(4).nullish(),
    goods_description: z.string().max(2000).nullish(),
    quantity: numericish.nullish(),
    quantity_uom: z.string().max(8).nullish(),
    declared_value_usd: numericish.nullish(),
    arrival_date: z.string().max(10).nullish(),
  })
  .strict();
```

The structural limits are copied from F3 §The Entry Field Set and match the
`cargo_entries_len_chk` CHECK exactly — 20 / 20 / 8 / 16 / 8 / 100 / 40 / 20 / 4
/ 2000 / — / 8 / — / 10. `.strict()` is what rejects an unknown property with
`422 REQUEST_MALFORMED` naming it; that is the mechanism behind FR-3.7 (*silent
ignoring is prohibited, because a silently dropped value would be absent from the
audit record the specialist believes they created*) **and** behind the guarantee
that a client cannot supply `created_by`, `origin`, `receipt_outcome`,
`case_reference`, `validation`, `findings`, `exception`, `skip_validation` or
`force` — each of those is simply an unknown property.

Then apply the structural rules the schema cannot express, each mapping to a
`422` with a per-field detail (`{ field, code, message }`):
- Body MUST be a JSON object — not an array, not a scalar. Reject
  `Array.isArray(req.body)` and a non-object body **before** the schema so an
  array does not produce a confusing zod path. Code `wrong_type`.
- `quantity` / `declared_value_usd`: must parse as a decimal within scale —
  ≤ 14 digits total and ≤ 3 (quantity) / ≤ 2 (declared value) decimals. Codes
  `not_numeric` / `too_many_decimals`. **A value that parses but is zero,
  negative or otherwise implausible is NOT a structural error** — it is F4's
  business, via `RIV-101` and `RIV-121` (clarification C-3). Only unparseable or
  over-scale values are 422s.
- `arrival_date`: must be a string within 10 characters. If it is present and
  **not** a syntactically valid ISO calendar date, that is **NOT a 422** — it is
  stored as `NULL` and reported by F4 as `RIV-130` and/or `RIV-131`, because "the
  specialist typed the date wrongly" is exactly a required-information finding.
  An over-length date string IS still a 422.
- `mode_of_transport`: length only. Presence is `RIV-040` and code-list
  membership is `RIV-041` — do **not** validate the value against the domain list
  here.
- Use `z.number()` acceptance for the two numeric fields (JSON number or numeric
  string) and convert to the submitted **string** form for storage. For a JSON
  number, use a fixed-notation string, never exponential: reject anything whose
  `String(n)` contains `e` or `E` as `not_numeric` rather than silently
  reformatting.

Let the `ZodError` propagate to `errorMapper`, which already detects it
structurally and emits `422 REQUEST_MALFORMED` with `details` (and omits
`details` when empty). Do not format a zod error by hand — `errorMapper` is the
single §3.7 translation point.

**Canonicalisation (F3 FR-3.8, §1.5 step 5).** After the schema, build the
`CanonicalEntryRecord`: for each of the fourteen fields, take the submitted
value, coerce a number to its fixed-notation string, `trim()` leading/trailing
whitespace, and map `''` / whitespace-only / `undefined` / `null` to `null`. An
empty string, a whitespace-only string and an absent property MUST be treated
**identically** — all are "not provided". Alongside it build
`provided: EntryFieldName[]` — the fields whose canonical value is non-null, in
`ENTRY_FIELDS` order — which is what drives the field-origin rows.

⚠️ **Trim only.** Do not uppercase a code, strip a hyphen, reformat a date, round
a number, or normalise internal whitespace. Normalisation for rule evaluation
happens inside F4 and applies to the *comparison*, never to the stored value: the
audit record must show what the specialist actually typed (F3 §The Entry Field
Set, F6 acceptance 6).

**`POST /api/entries` handler:**
1. Content type: `app.ts`'s `express.json({ type: 'application/json' })` leaves a
   non-JSON body unparsed and its `bodyErrorGuard` maps the parser failures to
   `413` / `415` / `422`. Add the belt: if the request has a body and
   `req.is('application/json')` is false, raise
   `ApiError(415, 'UNSUPPORTED_MEDIA_TYPE')`. There is no multipart parser
   installed anywhere and this endpoint MUST NOT accept an array, a file,
   `text/csv` or any batch wrapper (FR-3.2).
2. `req.principal` is guaranteed by `requireApiAuth` (plan 03-03) and CSRF by
   `csrfMiddleware` — which now guards this route automatically, because it
   derives its set from `API_ROUTE_TABLE`'s `implemented` state-changing pairs.
   Still assert `req.principal !== undefined` and raise
   `ApiError(401, 'UNAUTHENTICATED')` if absent, so the handler is correct in
   isolation and a middleware regression fails loudly rather than reaching the
   service with no actor.
3. Parse → canonicalise → `receiveEntry({ pool: deps.pool, principal:
   { id: req.principal.id, display_name: req.principal.display_name }, requestId:
   req.requestId }, canonical, provided)`. Read the exact principal property
   names from `session.middleware.ts`.
4. `201` with the `ReceiptResponse` the service returns, verbatim. Do not reshape
   it, do not add a field, do not omit `validation` on a clean pass — the
   response MUST state the outcome as a discriminated value, the case reference,
   the full validation result with findings, and the exception when one was
   opened, because *the specialist must never have to infer what happened to
   their entry* (FR-3.10).
5. `EntryNumberDuplicateError` → `ApiError(409, 'ENTRY_NUMBER_DUPLICATE')` with
   the message `Entry number {n} already exists on case {ref}.` and a `details`
   entry `{ field: 'entry_number', code: 'ENTRY_NUMBER_DUPLICATE', message }`
   carrying the existing `case_reference` so the SPA can link to it (F6 FR-6.15).
   Interpolate the **submitted** entry number.
6. Every other failure propagates unchanged so `errorMapper` maps it — a P0001
   coupling/chain violation, an `AuditWriteError`, a `ValidationEngineError`, a
   pool failure — all become `500 RECEIPT_FAILED` with *"The entry could not be
   received. Nothing was saved. Try again."* Do **not** catch-and-rewrite them
   here; `errorMapper` already logs the internal code against the `request_id`
   and returns the generic envelope.
7. There is **no** idempotency key on this endpoint. Receipt is deliberately not
   idempotent — two identical submissions are two distinct entries (FR-3.16) —
   so reject `Idempotency-Key` handling entirely by simply not implementing it
   (and note in a comment that the header is ignored by design, with the
   double-submit prevention living client-side in F6 FR-6.9).

**`GET /api/entries/{entryId}` handler:**
1. Validate `req.params.entryId` as a uuid. A non-uuid value ⇒
   `ApiError(400, 'INVALID_IDENTIFIER')` — a 400, not a 404, per F3's error
   table. Use a uuid regex or `z.string().uuid()`; do not pass an unvalidated
   string into the query (it is bound, but a 400 is the specified answer).
2. `loadEntryDetail(pool, entryId)` → `null` ⇒
   `ApiError(404, 'ENTRY_NOT_FOUND')`.
3. Assemble `EntryDetailResponse`: `entry` (values + `field_origins` from
   `loadFieldOrigins`, `created_by` from the join), `receipt_outcome`,
   `validation` from `loadValidationByEntry` (findings ascending `rule_id`), and
   `exception` from `loadExceptionRefByEntry` or `null`. The entry's "current
   state" is **derived** — `receipt_outcome` plus the exception's state — and
   there is no separate mutable status column to drift out of sync (FR-3.11).
4. There is deliberately **no** listing endpoint: no `GET /api/entries`, no
   query parameter of any kind on this route. The only list surface in the
   product is the receipt-ordered open-exception queue (F7, Phase 4). Reject any
   query string on this path with `ApiError(400, 'UNSUPPORTED_QUERY_PARAMETER')`
   if `Object.keys(req.query).length > 0`, matching the §3.1 no-query-parameters
   convention.

Export exactly `entryRoutes` and nothing else. Add no `PUT`, `PATCH` or `DELETE`
handler for an entry, and no service method that updates one (FR-3.6).

9. `entry_number` of 21 characters ⇒ `422` (`too_long`); of 20 ⇒ accepted

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-30 | Spoofing | `http/routes/entries.ts` POST handler — a client supplying its own actor | mitigate | The `EntryBody` zod schema is `.strict()`, so `created_by`, `origin`, `actor`, `specialist_id`, `on_behalf_of` and `decided_by` are unknown properties rejected `422 REQUEST_MALFORMED`. The handler passes `req.principal.id` — resolved from the `cargoexec_sid` cookie alone by `session.middleware.ts` — to `receiveEntry`, and reads no actor identifier from the body, a header or the query. Cases 7 and 17 of `server/test/api/entries.spec.ts` assert both halves. |
| T-03-31 | Tampering | `http/routes/entries.ts` POST handler — forcing the receipt outcome or bypassing validation | mitigate | `.strict()` rejects `receipt_outcome`, `case_reference`, `validation`, `findings`, `exception`, `skip_validation` and `force` as unknown properties (cases 6, 7); the handler passes no flag to `receiveEntry`, whose signature accepts none; and plan 03-04's `server/test/architecture/validation.spec.ts` fails the build on any skip/force/bypass identifier or `VALIDAT*` env key in `server/src`. |
| T-03-32 | Elevation of privilege | `http/routes/entries.ts` registered via `http/routes/index.ts` — an unauthenticated or cross-site write | mitigate | `requireApiAuth` (plan 03-03) refuses the request before route matching when `req.principal` is absent, and `csrf.middleware.ts` derives its guarded set from `API_ROUTE_TABLE`'s `implemented` state-changing pairs — so flipping the `POST /api/entries` flag turns on the constant-time `X-CSRF-Token` comparison with no code change. The handler additionally re-checks `req.principal`. Cases 17–19 assert 401 without a cookie and 403 without/with a wrong CSRF token, in each case with nothing persisted. |
| T-03-33 | Tampering | `db/repositories/entries.ts` via the `entryId` path parameter | mitigate | `entryId` is validated as a uuid in the GET handler (`400 INVALID_IDENTIFIER` otherwise, case 22) and then passed as a bind parameter to the repository's static SQL — it never enters query text. |
| T-03-34 | Information disclosure | `http/routes/entries.ts` GET handler — reading another specialist's entry | accept | CargoExec has exactly one role and no per-specialist ownership model: authorisation is binary (a request carries a valid session or it does not — F1 FR-1.1, PRD §10 #3), and every authenticated cargo specialist is entitled to read every case. There is therefore deliberately no ownership check, and `navigation.spec.ts`'s RBAC-identifier scan fails the build if one is introduced. | T-03-35 | Information disclosure | `http/errorMapper.ts` — internal failure detail in the receipt response | transfer | Every non-409 failure propagates unchanged to `errorMapper`, the single §3.7 translation point, which logs the internal invariant code (`AUDIT_COUPLING_VIOLATION`, `AUDIT_CHAIN_BROKEN`, `VALIDATION_ENGINE_FAILURE`, …) against the `request_id` and returns the generic `500 RECEIPT_FAILED` with "Nothing was saved." | T-03-36 | Information disclosure | `http/routes/entries.ts` — the 409 response | mitigate | The `409` body carries only the submitted `entry_number` and the existing `case_reference`, which F3 FR-3.9 and F6 FR-6.15 require the specialist to receive; no specialist identity, entry value or internal id is included. |
