<objective>
Build `server/src/services/receipt.service.ts`: the single atomic receipt
transaction that persists the entry, validates it, opens an exception on failure,
writes all three audit entries, and returns the receipt response.

Purpose: this is the phase's load-bearing guarantee — *no entry can exist having
been received but never assessed*. It holds because persistence, validation,
exception derivation and audit all commit together or not at all, and because the
Phase 1 deferred coupling triggers refuse the COMMIT if any audit entry is
missing. A "forgot to audit" bug does not produce an unaudited change; it
produces a failed transaction and a `500 RECEIPT_FAILED` telling the specialist
nothing was saved.
Output: the service, and a db-tier spec proving the committed result on both
outcomes.

Two constraints from STATE.md that this plan must not violate:
- **`server/src/db/tx.ts` is the SOLE `BEGIN`/`COMMIT`/`ROLLBACK` site (R-L2).**
  This service calls `withTransaction(pool, fn)` and issues no
  transaction-control statement of its own. `server/test/architecture` asserts
  exactly one module contains a `BEGIN`.
- **There must be no `UPDATE cargo_entries` statement anywhere in `server/src`.**
  `receipt_outcome` is written with its final value in the single INSERT
  (deviation D-3). The FRD's own step 10 ("set receipt_outcome") is deliberately
  unexecutable under `cargoexec_app`'s grant, and validating before the insert is
  what keeps entry immutability *stronger* than the FRD specified.
</objective>

Create `server/src/services/receipt.service.ts`. **Implement TechArch §1.5 steps
6–18 exactly in this order** — each step maps to a requirement and reordering any
of them breaks one:

```
 6  BEGIN                                       ← withTransaction, NOT here
 7  SELECT now() AS received_at, nextval('case_reference_seq')   ─ tx-stable
 8  validationEngine.evaluate(CanonicalEntryRecord, received_at)
       → { outcome, findings[], rule_set_version, rules_evaluated_count }
 9  INSERT cargo_entries (…values…, received_at, case_reference,
       receipt_outcome = outcome==='FAIL' ? 'EXCEPTION_OPENED'
                                          : 'VALIDATED_CLEAN')  RETURNING id
       └─ 23505 on entry_number ⇒ ROLLBACK, SELECT existing case_reference,
          respond 409 ENTRY_NUMBER_DUPLICATE (F3 FR-3.9)
10  SELECT id FROM cargo_entries WHERE id=$1 FOR UPDATE      ─ case anchor lock
11  INSERT cargo_entry_field_origins  (one row per provided field, 'HUMAN')
12  auditWriter.append(tx, ENTRY_RECEIVED)     seq 1  actor SPECIALIST
13  INSERT validation_results (+ validation_findings, ascending rule_id)
14  auditWriter.append(tx, VALIDATION_COMPLETED) seq 2  actor SYSTEM (on behalf of)
15  if FAIL:  INSERT exceptions (state OPEN, receipt_position from sequence)
              INSERT recommendations (status PENDING)   ← no audit entry (FR-5.12)
              auditWriter.append(tx, EXCEPTION_OPENED)  seq 3  actor SYSTEM
16  COMMIT  ─ deferred triggers now verify: audit coupling (a,b,c), hash chain,
              HITL (insert path: state OPEN ⇒ no decision required)
              any violation ⇒ ROLLBACK ⇒ 500 RECEIPT_FAILED, "nothing was saved"
17  after commit only: worker.dispatch(exceptionId)  ─ fire-and-forget, logged,
              never awaited, failure cannot affect the committed receipt
18  201 { entry, case_reference, receipt_outcome, validation, exception, next }
```

Signature and shape:

```typescript
export interface ReceiptPrincipal {
  readonly id: string;
  readonly display_name: string;
}

/** Raised for the 409 path. Carries the reference of the case that already owns
 *  the entry number, so the specialist can navigate to it (F3 FR-3.9). */
export class EntryNumberDuplicateError extends Error {
  readonly entry_number: string;
  readonly case_reference: string | null;
}

export async function receiveEntry(
  deps: {
    pool: Pool;
    principal: ReceiptPrincipal;
    requestId?: string;
    /** Post-commit AI dispatch. Injected so the request path can pass a no-op
     *  and Phase 5 can pass the real worker. NEVER awaited (FR-3.14). */
    dispatchRecommendation?: (exceptionId: string) => void;
  },
  submitted: CanonicalEntryRecord,
  provided: readonly EntryFieldName[],
): Promise<ReceiptResponse>
```

`submitted` is already canonical — trimmed, empty-equivalents as `null` — and
`provided` is the list of fields that were present and non-empty after trim. The
route (plan 03-06) owns that normalisation, because it is where the raw body
lives; this service takes the canonical record so it is testable without HTTP.

Implementation notes, each load-bearing:

- **One `withTransaction` call.** Everything from step 7 to step 15 is inside the
  callback. Nothing is retried: `AUDIT_SEQUENCE_CONFLICT` is surfaced to the
  caller, never silently retried (F13 §Error States).

- **Step 8 before step 9 (deviation D-3).** Evaluate the canonical record, then
  insert once with the final `receipt_outcome`. The evaluated content is
  byte-identical to the recorded content, and `RIV-132` sees the same
  `received_at` that is stored. Pass `received_at` straight from step 7 into
  `evaluate` — do not read a clock.

- **`arrival_date` precondition.** `insertEntry` binds `$18::date`, and
  `'2026-02-30'::date` raises `22008`. Before the insert, if
  `submitted.arrival_date` is non-null and
  `isCalendarDate(submitted.arrival_date)` is false, pass `null` for the
  **stored** date while passing the **submitted string** to `evaluate`. That is
  exactly what the FRD requires: a mistyped date is stored as `NULL` and reported
  as `RIV-131`, never as a `422` or a `500` (F3 §Validation). Build the insert
  payload as a shallow copy with `arrival_date` nulled — never mutate
  `submitted`, which the audit entry also reads.

- **Step 9's 23505.** Catch the unique violation on
  `uq_cargo_entries_entry_number` inside the transaction callback and rethrow it
  as `EntryNumberDuplicateError`. The transaction has already rolled back by the
  time `withTransaction` rethrows, so look up the existing `case_reference`
  **after** that, on the pool, via `findCaseReferenceByEntryNumber` — the dead
  transaction cannot serve a query. Distinguish the constraint by
  `err.constraint === 'uq_cargo_entries_entry_number'` (or the message
  containing that name), not by SQLSTATE alone, so a different unique violation
  in the same transaction is not misreported as a duplicate entry number.
  Deliberately **not** a validation rule and therefore never an exception:
  uniqueness depends on database state and would break determinism (F4 FR-4.4).

- **Step 10, the case-anchor lock.** `lockCaseAnchor(tx, entryId)` before the
  first `append`. `append()` assigns `case_sequence` under this lock; it needs
  table UPDATE privilege, which migration 0011 grants for exactly this reason.
  Take it once — all three appends in this transaction run under the same lock.

- **Step 11, provenance.** `insertFieldOrigins(tx, entryId, provided)`. An
  entirely empty entry legitimately gets zero rows (F3 FR-3.8) — that is the
  primary demonstration path, not an error.

- **Steps 12/14/15, the three audit entries.** Use `append(tx, …)` from
  `services/audit/writer.ts` — the single chokepoint. It cannot open a
  transaction and takes the open `PoolClient` as its first argument. Payloads,
  from TechArch §3.6 (copy this mapping exactly):

  | Action | Actor | `before_state` → `after_state` | Value rows |
  |---|---|---|---|
  | `ENTRY_RECEIVED` | `SPECIALIST` | `null` → `RECEIVED` | one per **provided** field; `after_value` = submitted value, `after_origin = 'HUMAN'` |
  | `VALIDATION_COMPLETED` | `SYSTEM` (records the requesting specialist) | `RECEIVED` → `VALIDATED_CLEAN` \| `EXCEPTION_OPENED` | one per finding; `field_name` = finding's primary field, `after_value` = failure code + message |
  | `EXCEPTION_OPENED` | `SYSTEM` | `null` → `OPEN` | one per finding (the stated basis) |

  Concretely: actor is `{ type: 'SPECIALIST', specialist_id: principal.id }` for
  step 12 and `{ type: 'SYSTEM', on_behalf_of_specialist_id: principal.id }` for
  steps 14 and 15. `case_id` is the entry id for all three; step 15 also passes
  `exception_id`. Pass `request_id` through from `deps` so an audit entry
  correlates with the server log. Pass **no** `reason` — the writer's
  `REASON_FORBIDDEN` set contains all three of these actions. For
  `VALIDATION_COMPLETED` on a clean pass there are zero findings and therefore
  zero value rows; that is correct and the writer accepts it.

  Note that the writer refuses secret-shaped field NAMES and VALUES. All
  fourteen entry field names are safe, and a finding's `after_value` is a failure
  code plus a plain-language message — but a specialist could type a
  bearer-token-shaped string into `goods_description`, which the writer would
  refuse (`AUDIT_WRITE_FORBIDDEN_CONTENT`) and which would correctly abort the
  receipt with `500 RECEIPT_FAILED`. Do not add a bypass; add a comment
  recording that this is intended behaviour, and cover it in Task 2 case 14.

- **Step 13, the validation result.** `insertValidationResult` then
  `insertFindings` with the engine's finding array **in the order the engine
  returned it** (ascending `rule_id`). Set `rules_evaluated_count` and
  `findings_count` from the evaluation — `validation_results_counts_chk` requires
  `rules_evaluated_count >= findings_count` and pins the PASS/FAIL ↔
  `findings_count` relationship, so passing the engine's own numbers is what
  keeps that CHECK satisfied. A clean pass writes a `PASS` row with zero
  findings — never no row (F4 FR-4.11).

- **Step 15, the derivation.** Only when `outcome === 'FAIL'`. Before inserting,
  assert defensively that `findings.length >= 1`; a `FAIL` with zero findings is
  an engine contradiction and must abort the transaction with the internal code
  `EXCEPTION_WITHOUT_BASIS` (F5 §Error States), not insert an exception with no
  basis. `insertException` passes only `entry_id` and `validation_result_id`;
  `insertPendingRecommendation` follows; then the `EXCEPTION_OPENED` append. The
  `PENDING` recommendation writes **no** audit entry of its own (FR-5.12).

- **Step 17, post-commit dispatch.** After `withTransaction` resolves, and only
  then, call `deps.dispatchRecommendation?.(exception.id)` for the FAIL path.
  Never `await` it; wrap it in a try/catch that logs and swallows, because AI
  provider failure MUST NOT affect receipt success (FR-3.14, NFR-9). Phase 5 owns
  the worker; this phase only provides the seam, and `deps.dispatchRecommendation`
  is optional so the request path can omit it entirely. Do **not** import
  anything from `server/src/ai/` — that directory does not exist yet and
  importing it would put Phase 5 work in Phase 3.

- **Step 18, the response.** Build a `ReceiptResponse` (plan 03-01's contract
  type): `entry` with `values` = the submitted canonical record (as stored,
  including the nulled invalid date — so the response reflects the record, not
  the request), `field_origins` = `{ [f]: 'HUMAN' }` for each provided field,
  `created_by` = `{ id, display_name }` from the principal; `case_reference`;
  `receipt_outcome`; `validation` = `{ outcome, rule_set_version, evaluated_at,
  findings }` using the `evaluated_at` **returned by `insertValidationResult`**
  (the database's `now()`, not a clock read); `exception` = the `ExceptionRef` or
  `null`; and `next` = `{ case_url: outcome === 'FAIL' ? `/cases/${case_reference}` : null,
  queue_url: '/queue' }`.

- **R-L5.** This module is the only one that writes `cargo_entries`,
  `cargo_entry_field_origins`, `validation_results`, `validation_findings` and
  the `exceptions` insert. It contains **no** function that writes
  `exceptions.state`, `closed_at` or `decision_id` — `decision.service.ts`
  (Phase 6) is the sole writer of those (R-L4, F5 FR-5.7). Say so in the header,
  and export nothing but `receiveEntry`, `EntryNumberDuplicateError` and
  `ReceiptPrincipal`.

- **No bypass of any kind.** `receiveEntry` takes no flag, mode, option or
  `skipValidation` argument, and there is no second entry point. Validation is
  unconditional and non-bypassable (F3 FR-3.4); plan 03-04's
  `validation.spec.ts` already fails the build on any such identifier.

`server/test/helpers/testdb.ts`, a real pool on **`cargoexec_app`**, and a real
specialist created through `server/test/helpers/identityFixtures.ts`. Unlike

for real. That is the point: a receipt that commits is a receipt whose audit
coupling was verified by the database.

Cases:

**The clean path (`VALIDATED_CLEAN`):**
1. A fully rule-satisfying entry returns `receipt_outcome: 'VALIDATED_CLEAN'`,
   `exception: null`, `validation.outcome: 'PASS'`, `validation.findings: []`,
   and `next.case_url === null` with `next.queue_url === '/queue'`.
2. After commit: exactly one `cargo_entries` row with
   `receipt_outcome = 'VALIDATED_CLEAN'`, `created_by` = the specialist,
   `case_reference` matching `^CE-\d{4}-\d{6}$`; exactly one `validation_results`
   row with `outcome = 'PASS'`, `findings_count = 0`,
   `rule_set_version = 'RIV-2026.09'`; **zero** `validation_findings` rows;
   **zero** `exceptions` rows; **zero** `recommendations` rows.
3. Exactly **two** `audit_entries` rows for the case, `case_sequence` 1 and 2,
   actions `ENTRY_RECEIVED` then `VALIDATION_COMPLETED`, with
   `after_state` `'RECEIVED'` then `'VALIDATED_CLEAN'`. The
   `VALIDATION_COMPLETED` entry has zero `audit_entry_values` rows.
4. `verify_audit_chain(case_id)` reports the chain verified.

**The exception path (`EXCEPTION_OPENED`):**
5. An entry with **every field null** returns `receipt_outcome:
   'EXCEPTION_OPENED'`, `validation.outcome: 'FAIL'` with exactly the thirteen
   presence findings in ascending `rule_id`, an `exception` with `state: 'OPEN'`
   and a positive `receipt_position`, and `next.case_url ===
   '/cases/' + case_reference` (F6's "Open case {ref}" target).
6. After commit: one `cargo_entries` row with `receipt_outcome =
   'EXCEPTION_OPENED'`; one `validation_results` row with `outcome = 'FAIL'` and
   `findings_count = 13`; thirteen `validation_findings` rows readable in
   ascending `rule_id` and matching the response's findings field-for-field;
   one `exceptions` row with `state = 'OPEN'`, `validation_outcome = 'FAIL'`,
   `closed_at IS NULL`, `decision_id IS NULL`, and `validation_result_id`
   pointing at that result; one `recommendations` row with `status = 'PENDING'`,
   `generated_at IS NULL`, `failed_at IS NULL`; **zero** `decisions` rows.
7. Exactly **three** `audit_entries` rows, `case_sequence` 1/2/3, actions
   `ENTRY_RECEIVED` / `VALIDATION_COMPLETED` / `EXCEPTION_OPENED`, with actor
   types `SPECIALIST` / `SYSTEM` / `SYSTEM` and — for both `SYSTEM` entries —
   `actor_specialist_id` equal to the submitting specialist (§3.6: `SYSTEM`
   records the requesting specialist). The `EXCEPTION_OPENED` entry has thirteen
   `audit_entry_values` rows, one per finding.
8. `verify_audit_chain(case_id)` reports the chain verified.

**Provenance (F3 FR-3.5, FR-3.8):**
9. An entry with three fields provided and eleven absent creates exactly three
   `cargo_entry_field_origins` rows, all `origin = 'HUMAN'`, naming exactly those
   three fields.
10. An entry with all fields null creates **zero** field-origin rows and still
    commits.
11. Values are stored as typed: submit `entry_number: 'abc12345678'` (lowercase)
    and assert the stored column, the response `entry.values.entry_number`, and
    the `ENTRY_RECEIVED` audit value row all read `'abc12345678'` — the receipt
    never uppercases, strips hyphens or reformats (F3 §The Entry Field Set,
    F6 acceptance 6, JRN-01 US-3.2). Note that lowercase also *fails* `RIV-011`,
    which is correct and expected — assert both facts in the same case.

**Determinism through the committed path (NFR-11):**
12. Receive the **same content twice** (differing only in `entry_number`, which
    must be unique) and assert the two responses' `validation.findings` arrays
    are identical in ids, field names, failure codes, messages **and order**.
    This is NFR-11 proven end to end, not just at the engine boundary.

**The 409 and the atomicity guarantee:**
13. A second receipt reusing an existing `entry_number` throws
    `EntryNumberDuplicateError` carrying the **existing** entry's
    `case_reference`, and leaves the database unchanged: the `cargo_entries` row
    count is the same before and after, and no new `validation_results`,
    `exceptions`, `recommendations` or `audit_entries` row exists (F3 FR-3.9,
    acceptance 6). Also assert the `case_reference_seq` gap is acceptable — the
    next successful receipt gets a higher reference and nothing is renumbered
    (F5 FR-5.8 for `receipt_position`, same principle).
14. A `goods_description` shaped like a bearer token (e.g.
    `'Bearer abcdefghijklmnop'`) is refused by the audit writer's forbidden-content
    guard, the transaction aborts, and **nothing** is saved: zero new
    `cargo_entries`, `validation_results` and `audit_entries` rows. This is
    intended behaviour, not a bug — record it as such in the test name.

**Receipt position (F5 FR-5.8):**
15. Three sequential failing entries receive strictly increasing
    `receipt_position` values (F5 acceptance 2).

**Immutability of the record (F3 FR-3.6, F4 FR-4.12):**
16. After a committed receipt, `UPDATE cargo_entries SET goods_description = …`
    executed directly as `cargoexec_app` is not exercised here — plan 01's
    `immutability.spec.ts` already owns the privilege-level framing. Instead
    assert the **application-level** guarantee this phase adds: a second
