# Security Audit — Phase 3: Receive, Validate, Except

**Mode:** verify (8 plans, each carrying a `<threat_model>` STRIDE register)
**Audited:** 2026-09-15
**Verdict:** SECURED
**Confirmed HIGH/CRITICAL findings (open):** 0

## Summary

Phase 3 ships the receipt pipeline: `POST /api/entries`, `GET /api/entries/{id}`, the F4 validation engine (RIV-2026.09, 31 rules), the F5 exception-derivation transaction, the `requireApiAuth` gate, and the shared USWDS form primitives. Across 8 plans the threat registers name 51 threats (T-03-01 .. T-03-51). Every mitigation claim was checked against the code at HEAD (not the plan's description of it) and, where a permanent test exists, the test was read and the full architecture/db/api suite was executed (148 arch + 160 db + 104 api = 412 tests, all green).

Two structural claims called out by the auditor's brief were independently re-verified rather than taken on faith:

1. **Single-write-path claim (no `UPDATE exceptions` anywhere in `server/src`, criterion 4).** Confirmed genuinely true at HEAD by direct grep (`receiptPaths.spec.ts` assertion 4, itself re-run: PASS) and by reading every write function in `db/repositories/exceptions.ts` (only `insertException` / `insertPendingRecommendation`, no update/delete function exists at all — not merely privilege-revoked, syntactically absent). The composite FK (`exceptions_basis_fk` → `validation_results(id, outcome)`, `outcome` CHECK-pinned to `'FAIL'`) makes a passing basis unstorable as a `23503`, independent of any trigger, and is proven from `cargoexec_app` (not the schema owner) in `exceptionBasis.spec.ts` case 1. **However** the HITL trigger (`exceptions_require_human_decision`, migration 0009) only fires `IF NEW.state <> 'OPEN'` — an `UPDATE exceptions SET validation_result_id = …` or `SET receipt_position = …` that leaves `state = 'OPEN'` is NOT refused at the database (verified directly: cases 6 and 11 of `exceptionBasis.spec.ts` execute the UPDATE as `cargoexec_app` and it succeeds, rolled back only by the test's own `ROLLBACK`, not by a DB refusal). This is the pre-existing STATE.md finding; it is **not exploitable today** because (a) `cargoexec_app` — the role a compromised server process would hold — is the only role capable of reaching this table, (b) no `UPDATE exceptions` statement of any kind exists anywhere in `server/src` (confirmed by grep and by the passing architecture test), and (c) there is no SQL-injection point anywhere in the receipt path (every repository is static-SQL, `$n`-bind-only — see below) by which an attacker could smuggle an arbitrary UPDATE through the application. The gap is a genuine DB-layer weakness carried entirely by application-code discipline, correctly disclosed by the phase itself as an accepted, documented risk rather than a silently-assumed one. Recorded below as an **accepted risk**, not a finding, because a "finding" implies a currently reachable attack path and none exists — reaching it requires either a SQL-injection primitive elsewhere (none found) or Phase 6 introducing a second write path (guarded structurally by `receiptPaths.spec.ts` assertion 4's allowlist, which is currently empty).

2. **`requireApiAuth` ordering.** Confirmed in code, not just in the comment: `app.ts` line order is `sessionMiddleware` → `requireApiAuth` → `csrfMiddleware` → routes (lines 93/102/105/110). `guard.spec.ts`'s case 6 (read, not re-derived) fails if a refactor moves the gate after CSRF. `requireApiAuth.ts` reads only `req.principal`, sourced solely from the `cargoexec_sid` cookie by `session.middleware.ts` — no header, body or query value is consulted, closing T-03-11/T-03-12 as claimed. **Both hold as claimed.**

No new threat class outside the 8 registers was found in the diff. SQL injection, XSS, CSRF, IDOR, secret leakage and DoS surfaces were all independently probed and refuted per threat below.

## Confirmed Findings (open, survived adversarial refutation)

**None.** Every HIGH/CRITICAL candidate identified during the retroactive sweep was refuted:

- *Candidate: HITL trigger gap enables silent exception re-basing.* Refuted as an exploitable finding — see Summary §1 and the ACCEPTED RISK row above. Requires either a second write path (structurally blocked and tested) or a SQL-injection primitive (none exists anywhere in the receipt path — every query is static text with `$n` binds, confirmed file-by-file).
- *Candidate: numeric byte-verbatim storage "reformatting" as a data-integrity gap.* Refuted as a security issue. This is a genuine, low-severity data-SHAPE quirk (`quantity numeric(14,3)` re-formats `'100'` → `'100.000'` on the `::text` read path in `loadEntryDetail`, entries.ts:230) — not an injection, not a precision loss, not an authorization or provenance issue. The POST response echoes the submitted text from the in-memory canonical record (byte-identical); only a subsequent GET re-reads the column and observes column-scale formatting. `entries.spec.ts` case 20 and `receipt.spec.ts` deliberately submit numerics already at column scale to keep the byte-for-byte assertion honest — documented, not concealed. No attacker-controlled path turns this into tampering: the value stored is still the exact value the specialist typed, merely displayed at fixed decimal scale.
- *Candidate: `insertException`'s absence of an owning-service check allows any caller to author an exception.* Refuted — `receiptPaths.spec.ts` assertion 2 (PASS) proves `receipt.service.ts` is the SOLE caller of `insertException` anywhere in `server/src`, and the composite FK independently makes a PASS-basis exception unstorable even from a compromised call site.
- *Candidate: `.strict()` zod schema could be bypassed by a non-JSON content-type smuggling extra keys.* Refuted — `app.ts`'s `express.json({type:'application/json'})` leaves non-JSON bodies unparsed, and the route's own explicit `req.is('application/json')===false` check (entries.ts:118-120) throws 415 before the body ever reaches the schema.

## Resolved Findings

None — no threat register entry in this phase's 8 plans was recorded as an open gap that a *later* plan then closed. The single documented gap (HITL trigger scope) was disclosed at the time it was discovered (03-07) and remains disclosed, unresolved by design (immutability is carried architecturally, not at the DB) — it is carried forward as an accepted risk, not resolved.
