<objective>
Evidence the phase's two *(no screen)* success criteria the way Phase 1 evidenced
its refusals: by test, from the application role, with a positive control on
every negative.

- **Criterion 4** — an exception exists only where a validation failure exists;
  no API shape, screen affordance or application-role SQL path can author one
  directly; and every open case carries its findings as its stated basis with an
  immutable receipt position.
- **Criterion 5** — when any part of receipt fails, nothing at all is saved: no
  entry without its assessment, no exception without its entry, no orphan audit
  entry — proven by forcing a failure mid-transaction and finding the database
  unchanged.

Purpose: these two criteria are the reason the phase exists. Criterion 4 is also
this phase's contribution to PRD R-2 — *scope pressure is the named project risk,
and every phase carries at least one criterion asserting an exclusion is
structural*. "There is no way to open an exception by hand" is not a convention
here; it is three independent mechanisms (a composite FK, a single write path, an
absent route) each asserted by a test that fails the build if it is weakened.
Output: two db-tier specs and one architecture spec. **No production code
changes in this plan.**

Note on ordering: this plan runs in the same wave as plan 03-09, which creates
`web/src/screens/NewEntry.tsx`. The UI assertions here are **absence**
assertions, so they hold whether or not that file exists yet, and the post-wave
regression gate re-runs them once it does. Do not make an assertion that requires
the screen to exist.
</objective>

  <name>Task 1: Criterion 4 — the SQL-path proof that an exception cannot exist without a failing basis</name>
  <files>server/test/db/exceptionBasis.spec.ts</files>
  <action>
Create `server/test/db/exceptionBasis.spec.ts` — db tier, per-suite database,
every statement issued as **`cargoexec_app`** (the role the application actually
runs as; a proof from the owner role would prove nothing about the deployed
posture). Follow the house style of `server/test/db/coupling.spec.ts` and
`hitl.spec.ts`: each refusal asserted by **SQLSTATE + constraint name**, each
with a **positive control** in the same file.

**The basis cannot be a passing validation:**
1. `INSERT INTO exceptions (entry_id, validation_result_id)` referencing a
   `PASS` `validation_results` row is refused with SQLSTATE `23503` on
   constraint `exceptions_basis_fk` (F5 acceptance 3, F0 FR-0.11). The composite
   foreign key `(validation_result_id, validation_outcome)` →
   `validation_results (id, outcome)` with `validation_outcome` CHECK-pinned to
   `'FAIL'` makes it unstorable — **no trigger is involved**, and assert that
   too: the error is a foreign-key violation, not a `P0001` raise.
2. Positive control: the same INSERT against a `FAIL` result succeeds.
3. Explicitly supplying `validation_outcome = 'PASS'` is refused by
   `exceptions_basis_is_failure_chk` (SQLSTATE `23514`) — so the CHECK is not
   merely a default that a caller could override.
4. Supplying a `validation_result_id` that does not exist at all is refused by
   the same composite FK (`23503`).

**The basis cannot be absent or forged after the fact:**
5. `validation_result_id` is `NOT NULL`: omitting it is refused (`23502`).
6. `UPDATE exceptions SET validation_result_id = <another FAIL result>` as
   `cargoexec_app` — the role does hold UPDATE on `exceptions` (migration 0008
   grants it for the F11 closure path), so this is a real risk and must be
   tested. It is refused at COMMIT by the Phase 1 HITL trigger
   (`HITL_VIOLATION`/`P0001`) because the row's state change has no matching
   `decisions` row. Assert the SQLSTATE and the message prefix. If the HITL
   trigger is scoped to `state`/`closed_at`/`decision_id` only and this UPDATE
   would therefore succeed, **do not weaken the assertion** — record it in the
   SUMMARY as a finding with the exact trigger behaviour, assert the actual
   behaviour, and note that basis immutability rests on the single write path
   (Task 3) plus the absence of any `UPDATE exceptions` in `server/src` outside
   Phase 6's decision service. Read `0009_invariant_triggers.sql` to determine
   which it is before writing the assertion.
7. `validation_findings` has no update or delete path at the application level
   (F4 FR-4.12, F5 FR-5.5): `grep` is Task 3's job, but assert here that a
   second `INSERT INTO validation_findings` with the same
   `(validation_result_id, rule_id)` is refused by
   `uq_validation_findings_rule` (`23505`) — findings cannot be quietly
   duplicated or re-worded into existence. Positive control: a different
   `rule_id` on the same result succeeds.

**One exception per entry, and no second basis:**
8. A second `INSERT INTO exceptions` for the same `entry_id` is refused by
   `uq_exceptions_entry` (`23505`) — an entry can never accumulate a second
   exception, because it is validated exactly once (F5 FR-5.3).
9. `uq_validation_results_entry` refuses a second `validation_results` row for
   the same entry (`23505`) — exactly one result per entry, so the basis is
   singular (F4 FR-4.11).

**The receipt position is immutable and never renumbered (F5 FR-5.8):**
10. Three exceptions created through `receiveEntry` (three failing entries) have
    strictly increasing `receipt_position` values, `NOT NULL` and unique.
11. `UPDATE exceptions SET receipt_position = …` as `cargoexec_app`: assert the
    actual behaviour against the migration (as in case 6) — either the HITL
    trigger refuses it at COMMIT, or it succeeds at the database and immutability
    rests on the application-level absence asserted in Task 3. Whichever it is,
    assert it explicitly with the SQLSTATE or the successful-but-guarded framing,
    and state which mechanism carries the guarantee. Do not leave it untested.
12. A **rolled-back** receipt leaves a sequence gap: capture
    `currval`/`last_value` of `exception_receipt_position_seq`, force a receipt
    to fail after the exception insert (drive `receiveEntry` with a poisoned
    input — see Task 2's mechanism, or simply run the insert inside a
    `BEGIN`…`ROLLBACK`), then create a successful failing receipt and assert its
    `receipt_position` is **greater than** the rolled-back one, with a gap. Then
    assert the queue order of the surrounding cases is unaffected: read
    `SELECT id FROM exceptions WHERE state='OPEN' ORDER BY receipt_position ASC`
    and confirm the two surviving cases are in creation order. Gaps are
    acceptable and MUST NOT be compacted, renumbered or reused — renumbering
    would rewrite queue history (F5 acceptance 8).

**No prioritisation surface (F5 FR-5.9, F5 acceptance 6):**
13. Read `information_schema.columns` for `exceptions` and assert the column set
    contains **none** of `priority`, `severity`, `risk_score`, `due_at`, any
    `sla_%`, `assigned_to`, `claimed_by`, `escalated_at`, `rank`, `weight`,
    `score`. Assert the full column set equals the nine columns of migration
    0004 (`id`, `entry_id`, `validation_result_id`, `validation_outcome`,
    `state`, `receipt_position`, `opened_at`, `closed_at`, `decision_id`) — a
    tenth column is then a deliberate, failing change. Receipt order is the
    whole ordering model.
14. Assert `exceptions_state_chk` admits exactly `OPEN`, `RESOLVED`, `REJECTED`
    by attempting `IN_PROGRESS`, `ON_HOLD`, `ESCALATED`, `CLAIMED`, `SNOOZED`,
    `PENDING_REVIEW` and `REOPENED` — each refused with `23514` on that
    constraint (F5 FR-5.6). Positive control: `'OPEN'` succeeds.

  <name>Task 2: Criterion 5 — force a failure at every receipt step and find the database unchanged</name>
  <files>server/test/db/receiptAtomicity.spec.ts</files>
  <action>
Create `server/test/db/receiptAtomicity.spec.ts` — db tier, per-suite database,
`cargoexec_app`. This is criterion 5's evidence and it must be a **census**, not
a spot check: after each forced failure, count rows in **every** table the
receipt touches and assert each count is identical to the pre-call value.

Build one helper and use it everywhere:

```typescript
/** Row counts for every table a receipt can touch. Compared before/after. */
async function census(pool) {
  // cargo_entries, cargo_entry_field_origins, validation_results,
  // validation_findings, exceptions, recommendations,
  // audit_entries, audit_entry_values
}
```

**The failure-injection mechanism.** Do not mock the repositories — that would
test a mock. Use real, causal failures so the test proves the transaction
boundary rather than a stub's behaviour. Available levers, in preference order:

- **Poisoned content that the audit writer refuses.** A `goods_description`
  shaped like a bearer token (`'Bearer abcdefghijklmnop'`) or containing an
  `sk-…` key makes `append()` raise `AUDIT_WRITE_FORBIDDEN_CONTENT` at step 12 —
  *after* the `cargo_entries` INSERT has already happened. This is the single
  best lever: it fails mid-transaction, after a write, with no mocking at all.
- **A duplicate `entry_number`.** Fails at step 9, before any audit entry.
- **Dropping a coupling trigger's counterpart.** In a **throwaway copy** of the
  database only (the `chain.spec.ts` precedent confines `DROP TRIGGER` to
  throwaway copies), disable the writer's insert so the coupling trigger fires
  at COMMIT. Prefer not to need this.
- **A `statement_timeout`.** `withTransaction` accepts
  `statementTimeoutMs`; a receipt driven with a 1 ms timeout aborts
  mid-transaction. Only use this if `receiveEntry` exposes the option; do not
  add production code to make it testable — if the seam does not exist, use the
  levers above.
- **An over-long value that the DDL CHECK refuses.** Pass a
  `CanonicalEntryRecord` directly to `receiveEntry` (bypassing the route's
  structural schema, which is legitimate here because this is a service-level
  test) with a `goods_description` of 2001 characters. `cargo_entries_len_chk`
  refuses at the INSERT.

**Cases:**
1. **Failure after the entry INSERT, before any audit entry** — poisoned
   `goods_description`. `receiveEntry` rejects; the census is **identical** to
   the pre-call census on all eight tables. Specifically: **zero** new
   `cargo_entries` rows (F3 acceptance 3 — *"Forcing a failure in the audit
   writer during receipt leaves zero `cargo_entries` rows for that
   submission"*), zero `validation_results`, zero `audit_entries`.
2. **Failure at the entry INSERT** — duplicate `entry_number`. Census identical.
3. **Failure at the entry INSERT** — over-length `goods_description` refused by
   `cargo_entries_len_chk`. Census identical; assert the error is a `23514`, so
   the test is failing for the reason it claims.
4. **No entry without its assessment.** Assert the invariant directly as a
   database query after a full suite of successes and failures:
   `SELECT count(*) FROM cargo_entries e LEFT JOIN validation_results v ON
   v.entry_id = e.id WHERE v.id IS NULL` is **0**. There is no entry in the
   database that was received but never assessed.
5. **No exception without its entry.** `SELECT count(*) FROM exceptions x LEFT
   JOIN cargo_entries e ON e.id = x.entry_id WHERE e.id IS NULL` is **0**.
   (The FK makes it unstorable; assert it anyway — the criterion names it.)
6. **No orphan audit entry.** `SELECT count(*) FROM audit_entries a LEFT JOIN
   cargo_entries e ON e.id = a.case_id WHERE e.id IS NULL` is **0**, and
   `SELECT count(*) FROM audit_entry_values v LEFT JOIN audit_entries a ON
   a.id = v.audit_entry_id WHERE a.id IS NULL` is **0**.
7. **No exception without a failing basis, across the whole database.**
   `SELECT count(*) FROM exceptions x JOIN validation_results v ON
   v.id = x.validation_result_id WHERE v.outcome <> 'FAIL'` is **0**, and
   `SELECT count(*) FROM exceptions x JOIN validation_results v ON
   v.id = x.validation_result_id WHERE v.findings_count = 0` is **0** — every
   open case carries findings as its stated basis (criterion 4's second half).
8. **Every exception's basis belongs to its own entry.**
   `SELECT count(*) FROM exceptions x JOIN validation_results v ON
   v.id = x.validation_result_id WHERE v.entry_id <> x.entry_id` is **0** — an
   exception cannot borrow another entry's failure as its basis.
9. **Every committed entry has its audit pair.** For every
   `cargo_entries` row: exactly one `ENTRY_RECEIVED` and exactly one
   `VALIDATION_COMPLETED` audit entry; and for every `exceptions` row, exactly
   one `EXCEPTION_OPENED`. Assert as three `GROUP BY … HAVING count(*) <> 1`
   queries returning zero rows (NFR-6: a state change without its audit entry,
   or an audit entry without its change, is prevented by transactional coupling,
   not convention).
10. **Positive control for the whole suite.** A clean receipt and a failing
    receipt both commit successfully in the same database, and the census
    *increases* by exactly the expected amounts (clean: +1 entry, +1 result, +0
    findings, +0 exceptions, +0 recommendations, +2 audit entries; failing:
    +1 entry, +1 result, +13 findings, +1 exception, +1 recommendation,
    +3 audit entries). Without this, cases 1–3 would also pass against a
    receipt service that never saved anything.
11. **The audit chain survives the failures.** After the mixed sequence of
    successes and forced failures, `verify_audit_chain(case_id)` reports verified
    for every committed case, and `case_sequence` is contiguous from 1 with no
    gap and no duplicate per case — a rolled-back receipt must not consume a
    case sequence number for a case that exists.
12. **The response tells the truth.** For case 1, assert the error surfaced to
    the caller is the one `errorMapper` would translate to
    `500 RECEIPT_FAILED` — i.e. an `AuditWriteError` / internal invariant code,
    not a partial success. (The HTTP-level assertion belongs to plan 03-06's
    api spec; here assert the service-level error identity.)
