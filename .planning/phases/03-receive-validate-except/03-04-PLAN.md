<objective>
Build the evaluation mechanism over plan 03-02's rule data: `evaluate(record,
receivedAt)` with declared gating, no short-circuiting, ascending-`rule_id`
ordering and a two-value outcome; the registry integrity self-check that refuses
boot on `RULE_SET_INVALID`; and the tests that prove determinism (NFR-11) rather
than asserting it in prose.

Purpose: this is the half of F4 that is **not** an assumption. Rule content is
open to CBP refinement; the mechanism — deterministic, complete, per-rule
findings in a stable order, carried onto the exception as its stated basis — is
fixed. Keeping it in `engine.ts` with all content in `rules.ts` / `domain.ts` is
what makes a rule revision a data change plus a `rule_set_version` bump.
Output: `engine.ts`, `selfCheck.ts`, `index.ts` (the directory's public surface),
a boot self-check in `server/src/index.ts`, two unit specs, and one permanent
architecture spec.

**There is no validation endpoint and no re-validate path.** F4 FR-4.2 is
explicit: no `POST /api/validate`, no re-validate action, no scheduled
re-evaluation, no UI control that re-runs validation on a stored entry, and no
request parameter, header, body flag, environment variable or configuration
switch that skips, defers, weakens or re-runs it (F3 FR-3.4). The architecture
spec in Task 3 makes that absence a build constraint.
</objective>

Create `server/src/services/validation/engine.ts`. Same purity constraint as the
rest of the directory (R-L10): no clock, no pool, no repository value, no
network, no randomness — only type imports plus the sibling modules.

```typescript
/**
 * The evaluation mechanism (F4 §Evaluation Semantics).
 *
 * Rule CONTENT is an inherited [ASSUMPTION] in rules.ts / domain.ts, open to CBP
 * refinement. This module is the part that is NOT an assumption, and it must
 * keep working unchanged across a rule-set revision:
 *   FR-4.3  every applicable rule is evaluated; evaluation NEVER short-circuits
 *   FR-4.5  a format rule is skipped when its presence rule failed
 *   FR-4.6  a domain rule is skipped when its format rule failed
 *   FR-4.7  conditional applicability is asked of the rule, not inferred here
 *   FR-4.8  findings are emitted in ascending rule_id
 *   FR-4.9  no severity, weight, score, priority or ranking — of a finding or of
 *           the outcome
 *   FR-4.10 outcome is PASS with zero findings or FAIL with one or more
 *   FR-4.4  determinism: the only inputs are the record and its own received_at
 */
export function evaluate(
  record: CanonicalEntryRecord,
  receivedAt: string,
): ValidationEvaluation
```

Algorithm — write it exactly this way, because each step maps to a requirement:

1. Iterate `RULES` in registry order (which plan 03-02 guarantees is ascending
   `rule_id`). Do **not** sort here and do **not** rely on the array order for
   gating — gating is read from each rule's declared `requires_passed`.
2. Maintain a `Set<RuleId>` of rules that produced a finding (`failed`) and a
   counter of rules actually evaluated.
3. For each rule:
   - **Gating (FR-4.5/4.6):** if any id in `rule.requires_passed` is in `failed`,
     skip the rule entirely — no finding, and it does **not** count toward
     `rules_evaluated_count`. Because `requires_passed` may name a rule that was
     itself skipped, treat "skipped" as "not failed": a rule whose gate was
     itself skipped is also skipped, which follows transitively from the
     declared chain (`RIV-032` requires `RIV-030` and `RIV-031`; if `RIV-030`
     failed, `RIV-031` is skipped and `RIV-032` is skipped by its own
     `RIV-030` dependency — verify the declared chains make this unambiguous and
     do not add implicit transitivity logic).
   - **Applicability (FR-4.7):** if `rule.applicable(record) === false`, skip —
     again no finding and no increment.
   - Otherwise increment `rules_evaluated_count` and call
     `rule.satisfied(record, receivedAt)`.
   - If not satisfied: resolve `primary_field` (call it when it is a function),
     resolve `message` (call it when it is a function), and push
     `{ rule_id, field_name, failure_code, message }`.
4. `outcome` is `findings.length === 0 ? 'PASS' : 'FAIL'`.
5. Return `{ outcome, rule_set_version: RULE_SET_VERSION, rules_evaluated_count,
   findings }` with `findings` frozen. `evaluated_at` is **not** produced here —
   it is the database's `now()` on the `validation_results` row, inside the
   receipt transaction (a clock read here would break FR-4.4).

**Never short-circuit.** There is no early `return` once a finding appears, no
`break`, and no "stop after N". R-10 in the PRD is exactly this: the specialist
must see every unsatisfied rule in one pass, so a second submission is not
needed to discover the second problem.

**Engine-failure handling.** Wrap each rule's `applicable` / `satisfied` /
`message` / `primary_field` call so a throwing predicate becomes a
`ValidationEngineError` carrying the internal code
`'VALIDATION_ENGINE_FAILURE'` (added to `INTERNAL_INVARIANT_CODES` by plan
03-01) and the offending `rule_id`. Also raise it when a resolved `field_name`
is not a member of `ENTRY_FIELDS` (F4 §Error States row 3). Do **not** catch and
continue: a malfunctioning evaluator must abort the receipt transaction so the
specialist is told nothing was saved, rather than receive a silently incomplete
finding list. Export the error class so the receipt service and `errorMapper`
can recognise it; `errorMapper`'s existing fallback already maps an unknown
internal failure to a generic `500 RECEIPT_FAILED`, which is the required
behaviour — confirm that path rather than adding a new mapper row.

Then create `server/src/services/validation/index.ts` as the directory's public
surface, re-exporting `evaluate`, `ValidationEngineError`, `RULE_SET_VERSION`,
`assertRuleRegistryValid` and the types. Callers outside the directory import
from `services/validation/index.js` only — they must not reach into `rules.ts`
or `domain.ts`, so a rule-set revision cannot ripple outward. Say that in the
header.
