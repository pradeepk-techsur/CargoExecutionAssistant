<objective>
Extend the two shared web primitives the cargo entry form needs: the form
pattern gains a select, a textarea with a character count, a date input and a
fieldset wrapper; the typed API client gains `createEntry` and `getEntry`.

Purpose: STATE.md is explicit — *"shared `ErrorSummary.tsx` + `UswdsForm.tsx` +
`LiveRegions.tsx` + `useScreenFocus.ts` already implement the inherited USWDS
error-summary + focus-management + live-region pattern. **Reuse them — do not
write a second pattern.**"* The entry form needs three control types Phase 2
never rendered, and the honest way to add them is inside the one pattern, with
the same label/hint/error/`aria-describedby`/`aria-invalid` contract, so the
per-screen accessibility review certifies one implementation rather than two.
The client half matters for a different reason: the CSRF token lives only in a
module variable in `client.ts` and is re-stored inside `getSession()`/`signIn()`.
**Any new state-changing POST from the web client must go through that client or
a reload + POST will 403.**
Output: four new exports in `UswdsForm.tsx`, two new methods on `api`.

No screen is built in this plan — plan 03-09 assembles them. Keeping the
primitives separate means the screen plan spends its context on the screen.
</objective>

  <files>web/src/components/UswdsForm.tsx</files>
  <action>
Extend `web/src/components/UswdsForm.tsx`. **Do not create a second components
file and do not re-implement the label/hint/error wiring** — factor the shared
bits out of `Field` into a small internal helper (`useFieldIds(id, hint,
invalid, errorText)` returning `{ hintId, errorId, describedBy }`, plus a
`FormGroup` wrapper rendering
`usa-form-group[--error]` + `usa-label` + hint + `usa-error-message`) and have
all four controls use it. `Field`'s rendered output must be **byte-identical**
to today's after the refactor — `e2e/sign-in.spec.ts` and
`server/test/architecture/navigation.spec.ts` both render it, and Phase 2's
signed `docs/a11y/sign-in.md` certifies that markup.

**`SelectField`** — USWDS select (Screen-01 interactive elements):
```tsx
<div className="usa-form-group">
  <label className="usa-label" htmlFor={id}>{label}{required && <> <abbr title="required" className="usa-hint--required">*</abbr></>}</label>
  {hint && <span className="usa-hint" id={hintId}>{hint}</span>}
  {invalid && errorText && <span className="usa-error-message" id={errorId} role="alert">{errorText}</span>}
  <select className="usa-select" id={id} name={id} value={value} aria-describedby={describedBy} aria-invalid={invalid || undefined} onChange={…}>
    <option value="">{placeholder ?? '- Select -'}</option>
    {options.map(o => <option key={o.value} value={o.value}>{o.label}</option>)}
  </select>
</div>
```
The empty default option is required and load-bearing: *nothing is pre-chosen on
the specialist's behalf* (FR-6.6). Its label defaults to `'- Select -'` exactly
as the mockup shows. Note in a comment that the option list is supplied by the
caller from the F4 domain code lists and that this component holds no list of
its own.

**`TextAreaField`** — USWDS textarea plus a character count:
- `<textarea className="usa-textarea" id maxLength={maxLength} rows={rows ?? 5} …>`
  with the same label/hint/error wiring. `maxLength` caps input at the F3
  structural limit so a `422` for over-length is not reachable through normal
  typing, while the server check remains authoritative (F6 §Validation).
- Render the counter **in React**, not via USWDS JS. Markup:
  `<span className="usa-hint usa-character-count__message" id={`${id}-info`}
  aria-live="polite">{remaining} characters allowed</span>`, and include
  `${id}-info` in the control's `aria-describedby`. **Why not USWDS JS:** the
  `usa-character-count` behaviour is initialised by
  `/assets/js/uswds.min.js` at document load, and this component mounts later
  from React — the same reason the date picker below needs explicit
  initialisation. A React-rendered counter is deterministic, needs no init, and
  produces the same announced text. Debounce is unnecessary; `aria-live="polite"`
  on a value that changes per keystroke is what USWDS itself does, and
  `AnnounceProvider`'s two global regions are untouched by this field-scoped one.
- Follow USWDS wording: *"{n} characters allowed"* while under the limit and
  *"{n} characters over limit"* if `maxLength` is ever exceeded (it cannot be,
  with `maxLength` set, but render the branch so the copy is right).

**`DateField`** — USWDS date input with an explicit `YYYY-MM-DD` hint (FR-6.6):
- Render the `usa-date-picker` markup:
  ```tsx
  <div className="usa-date-picker" data-default-value="" ref={wrapperRef}>
    <input className="usa-input" id={id} name={id} type="text" value={value}
           aria-describedby={describedBy} aria-invalid={invalid || undefined}
           onChange={…} />
  </div>
  ```
- On mount, attempt explicit initialisation of the USWDS behaviour:
  `(window as { uswds?: { components?: { 'usa-date-picker'?: { on(el: Element): void } } } }).uswds?.components?.['usa-date-picker']?.on(wrapperRef.current)`
  inside a `useEffect`, guarded in a `try/catch` that swallows. Read the exact
  accessor shape from the installed `@uswds/uswds` build before writing it, and
  if the global does not expose an imperative `on(...)`, **skip initialisation
  entirely** and render a plain `usa-input` with the hint.
- ⚠️ **The text input alone MUST be sufficient to complete the task** (Screen-01
  §Interactive elements). The calendar is a progressive enhancement: if USWDS JS
  is absent or its init fails, typing `YYYY-MM-DD` still works, the value still
  submits, and no error appears. Do **not** make the calendar a dependency of
  submission, and do **not** let USWDS's wrapper rewrite the value — the client
  never reformats a date (FR-6.5). If explicit init proves to fight React's
  controlled input (USWDS's date picker inserts a hidden external input and may
  write to the visible one), prefer the plain `usa-input` + hint form and record
  the deviation in the SUMMARY with its reason. Correct, keyboard-operable,
  as-typed behaviour beats the calendar widget.
- `type="text"`, never `type="date"`: a native date input coerces to the
  browser's locale format, which would break "values submitted as typed".

**`Fieldset`** — the group wrapper the four Screen-01 fieldsets need:
```tsx
<fieldset className="usa-fieldset" id={id} aria-describedby={describedBy}>
  <legend className="usa-legend">{legend}</legend>
  {statement && <p className="usa-hint" id={`${id}-statement`}>{statement}</p>}
  {errorTexts?.length ? (
    <div className="usa-error-message" id={`${id}-error`} role="alert">
      {errorTexts.map((t, i) => <p key={i}>{t}</p>)}
    </div>
  ) : null}
  {children}
</fieldset>
```
`describedBy` joins `${id}-statement` (when a statement exists) and
`${id}-error` (when error texts exist), in that order. This is the mechanism
behind FR-6.10's sole exception: `RIV-070` and `RIV-073` each carry a single
`field_name`, but **both render on the Transport fieldset**, inside the
fieldset's error slot and associated via `aria-describedby` on the
`<fieldset>`, because the finding concerns the pair rather than either field
alone. Say exactly that in the component's comment so the next reader does not
"fix" it into a per-field binding. The fieldset must also be focusable as a
summary-link target, so add `tabIndex={-1}`.

**Two constraints that are build gates:**
- **No raw hex and no raw `px`** anywhere in `web/src/**/*.tsx` —
  `server/test/architecture/absence.spec.ts` fails the build on either. Use
  USWDS classes and tokens only; add no inline `style` attribute.
- **No `dangerouslySetInnerHTML`** — `headers.spec.ts` fails the build on it.
  Every message is a React text child, escaped by default.

Also keep `UswdsForm`'s `noValidate` exactly as it is: native constraint
validation must never pre-empt the server, and the form must be submittable in
any state including entirely empty (FR-6.4). Do not add a `required` gate, do
not add `onInvalid`, do not call `checkValidity()`.

Note on `required`: `Field` currently sets the DOM `required` attribute as well
as the visible `*`. Keep that (Screen-01 §Accessibility asks for *"USWDS

inert for submission because the form is `noValidate`, and it is what a screen
reader announces. Mirror it in `SelectField`, `TextAreaField` and `DateField`.

<task type="auto">
  <name>Task 2: api.createEntry and api.getEntry on the single typed client</name>
  <files>web/src/api/client.ts</files>
  <action>
Add two methods to the `api` object in `web/src/api/client.ts`. They go
**through the existing `request()` primitive** — that is the whole point:

```typescript
  /**
   * Receive one manually authored entry (F3). Goes through request() so the
   * in-memory CSRF token stored by getSession()/signIn() is attached — the
   * mandatory client half of 02-04's rotate-on-GET CSRF. A POST that bypassed
   * this client would send no X-CSRF-Token after a page reload and 403.
   *
   * A required-information failure is NOT an error here: it is a 201 with
   * receipt_outcome 'EXCEPTION_OPENED' and findings, so it resolves normally
   * and the screen reads the outcome off the response (F3 FR-3.10).
   */
  async createEntry(body: EntryCreateRequest): Promise<ReceiptResponse> {
    return request<ReceiptResponse>('POST', '/api/entries', {
      body,
      expectBody: true,
    });
  },

  /** Retrieve one entry with its derived state (F3 FR-3.11). */
  async getEntry(entryId: string): Promise<EntryDetailResponse> {
    return request<EntryDetailResponse>('GET', `/api/entries/${encodeURIComponent(entryId)}`, {
      expectBody: true,
    });
  },
```

Import the three types from `@cargoexec/contract` — `web` imports types from
`contract` and never duplicates a DTO shape locally (R-L9).

Behaviours that must NOT be added, each for a stated reason:

- **No retry, of any kind.** `request()` already throws
  `ApiClientError({ status: 0, code: 'NETWORK' })` on a transport failure with
  no retry, because a mutating request whose outcome is unknown must not be
  silently re-sent — a timeout may have created an entry, and receipt is not
  idempotent (F3 FR-3.16, F6 FR-6.9). Do not add a retry, a backoff or an
  `AbortController` re-issue.
- **No idempotency key.** The endpoint accepts none; double-submission
  prevention is client-side and in-flight-scoped (plan 03-09's busy state).
- **No client-side validation or coercion.** `createEntry` sends the body it is
  given, untouched. It must not uppercase a code, strip a hyphen, reformat a
  date, round a number, or drop a field it considers empty-equivalent beyond
  sending it as an empty string (FR-6.5). Trimming is the screen's job (one
  place), and the server treats `''`, whitespace-only and absent identically.
- **No 401 special-casing.** `request()`'s global handler already discards
  in-memory state and navigates to `/sign-in?next=<path>&reason=expired` on a
  mid-session 401, which is exactly FR-6.16's *"preserve the typed values in
  memory, navigate to `/sign-in?next=/entries/new`, and after re-authentication
  return to an empty form"* — the full-document navigation is what discards the
  values, and the screen must NOT silently re-submit after re-authentication.
  Do not pass `isSignIn: true`.

Update the file header's note about phases 3 and 6: it already says *"including
for every POST that phases 3 and 6 add after a reload"* — make it concrete by
naming `createEntry` as the first such POST, so the next author sees the rule
was actually applied rather than merely anticipated.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| server→browser (db→render) | Server-authored finding messages and stored entry values arriving in the SPA and being rendered by these components. |
| browser→API | The SPA's outbound state-changing request, which must carry the CSRF token and must not be replayed. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-03-46 | Tampering | `web/src/components/UswdsForm.tsx` — XSS via a server-authored error message or a specialist-typed `{value}` interpolation | mitigate | Every message is rendered as a React text child (`{errorText}`, `{t}`), escaped by default; no component uses `dangerouslySetInnerHTML` and `server/test/architecture/headers.spec.ts` already fails the build on it anywhere under `web/src`. | T-03-47 | Elevation of privilege | `web/src/api/client.ts::createEntry` — a cross-site forged entry submission | mitigate | `createEntry` goes through the shared `request()` primitive, which attaches `x-csrf-token` from the module variable re-stored inside `getSession()`/`signIn()` and sends `credentials: 'same-origin'`. A bypassing `fetch` would simply 403. |
| T-03-48 | Tampering | `web/src/api/client.ts::createEntry` — a duplicated entry from a replayed request | mitigate | `request()` performs no retry on any path and `createEntry` adds none, because receipt is not idempotent and a timeout may already have created an entry (F3 FR-3.16). | T-03-49 | Information disclosure | `web/src/api/client.ts` — the CSRF token or session state leaking to persistent storage | mitigate | The token remains in a module variable and never touches `localStorage` / `sessionStorage` / `indexedDB`; these two methods add no storage call. Owned by the route and the session middleware. |
| T-03-51 | Denial of service | `web/src/components/UswdsForm.tsx::TextAreaField` character counter | accept | The counter recomputes a string length per keystroke on a field capped at `maxLength` (2000), and the `aria-live="polite"` region is field-scoped. Bounded, local work; residual risk accepted. |
