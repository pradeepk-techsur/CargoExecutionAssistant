# Security Report — Phase 6: The Human Decision and the Record That Explains It

**Mode:** verify
**Audited:** 2026-09-16
**Verdict:** SECURED
**Confirmed HIGH/CRITICAL:** 0

## Summary
This audit verified all 16 pre-declared STRIDE threats (T-06-01 through T-06-16) across the five plans of Phase 6 (F11 decision API, F13 audit-read API, F12 decision UI, F14 audit-trail UI, and the whole-loop milestone gate) by reading the actual on-disk implementation — not the plan prose — and, where practical, executing the real test suites. Every declared mitigation was found genuinely present and reachable: the decision body schema is `.strict()` with no `decided_by`/`actor`/`origin` slot (confirmed by a passing 422 test); every SQL statement in the write path is parameterised, with no string concatenation; the `SELECT … FOR UPDATE` + `UNIQUE(exception_id)` combination was proven to serialize concurrent decisions (test 6, one 201 + one 409, executed live); neither `DecisionPanel.tsx` nor `AuditTrailRegion.tsx` contains `dangerouslySetInnerHTML` (grep, corroborated by the project-wide `headers.spec.ts` scan, 153/153 architecture tests green); the AI-actor `whoText()` branch returns before ever reading `entry.actor`; and the confirmation panel is built exclusively from a dedicated `response` state variable populated only inside the POST success handler, gated by a `busy` flag plus a client-minted `Idempotency-Key` backed by a server-side `UNIQUE(exception_id, idempotency_key)` index. One noteworthy finding surfaced during the audit trail (not a new vulnerability, but worth recording): 06-01's own SUMMARY documents that the executor discovered and fixed a real pre-existing CSRF-bypass gap (parameterized paths were compared as literal strings against `req.path`, silently skipping CSRF enforcement on every future parameterized mutation) before this route shipped — verified fixed via a regex-based path-pattern matcher, confirmed correct with a live regex probe including path-traversal and malformed-segment rejection. No HIGH/CRITICAL issues survive adversarial refutation; ship as-is.

## Resolved findings
### CSRF-bypass on parameterised state-changing routes
- **Status:** Fixed during 06-01 (commit `6a14bf3`), verified present in current code
- **Prior finding:** `csrfMiddleware` built its implemented-state-changing set from `API_ROUTE_TABLE` route PATTERNS and compared them as plain strings against the concrete `req.path`. A parameterised path (`/api/exceptions/:exceptionId/decision`) never equals a concrete path (`/api/exceptions/<uuid>/decision`), so CSRF enforcement was silently skipped for the first parameterised mutation route this project ever shipped — `POST /api/exceptions/{id}/decision`. This was caught by the plan's own regression suite (decision.spec test 2 returned 201 instead of 403) rather than by this audit, but is recorded here because it is exactly the class of "mitigation claimed but not actually reachable" this audit looks for.
- **Fix applied:** `server/src/http/csrf.middleware.ts:47-64` — each implemented state-changing route pattern is compiled to an anchored regex (`:param` → `[^/]+`) and tested against the concrete `req.path`.
- **Verification:** This audit independently re-derived and executed the regex logic in a standalone node script against the uuid form, the case-reference form, and adversarial inputs (`../../decision`, extra path segments) — all behaved correctly (match the two legitimate forms, reject the others). `decision.spec.ts` test 2 (missing/bad CSRF token ⇒ 403) was executed live in this audit and passed. Full architecture suite (153/153) and API suite (34/34 for decision+audit) re-run live and green.
