<objective>
Build the F11 decision API end to end: the contract types, the write half of
the decisions repository (currently read-only), the transactional
`decision.service.ts` that computes per-value provenance and closes a case
through exactly one audit entry, and the `POST
/api/exceptions/{exceptionId}/decision` route — wired into the route table as
its ninth (of ten) row.

Purpose: this is the structural guarantee the whole phase and the whole
product exist to prove — a cargo exception is never resolved without an
accountable human decision, and this is the ONLY code path in the entire
codebase permitted to write that decision.
Output: `decision.service.ts`, `decisions.ts` write functions, the decision
route, and `server/test/api/decision.spec.ts` — the permanent regression
asset proving all ten F11 acceptance criteria.
</objective>

```ts
export interface DecisionPrincipal { readonly id: string; readonly display_name: string; }

export async function recordDecision(
  deps: { pool: Pool; principal: DecisionPrincipal; requestId?: string },
  exceptionId: string,               // ALREADY RESOLVED to a uuid by the route
  body: DecisionCreateRequest,
  idempotencyKey: string | null,
): Promise<DecisionRecordResponse> {
  const { pool, principal, requestId } = deps;

  // FR-11.11 — the idempotency pre-check runs OUTSIDE the transaction, BEFORE
  // BEGIN (FRD process step 3, literally before step 4 "Transaction BEGIN").
  if (idempotencyKey !== null) {
    const existing = await loadDecisionByIdempotencyKey(pool, exceptionId, idempotencyKey);
    if (existing !== null) {
      const matches = decisionMatchesReplay(existing, body); // compares decision_type,
        // reason (trimmed), resolution_values as field_name/value pairs against the
        // STORED decision_values rows, and recommendation_id if supplied — ALL must
        // match for a legitimate replay.
      if (!matches) throw new IdempotencyKeyReusedError();
      return assembleReplayResponse(pool, existing); // idempotent_replay: true,
        // writes NOTHING — loads the existing decision_values + its audit_entry_id
        // (SELECT id FROM audit_entries WHERE decision_id = $1) and returns the
        // exact same shape a fresh 201 would have produced.
    }
  }

  return withTransaction(pool, (tx) => runDecision(tx, principal, requestId ?? null, exceptionId, body, idempotencyKey));
}
```

**Inside `runDecision` (all under the transaction; every branch that throws
leaves ZERO rows — no catch-and-partial-write anywhere):**

1. `SELECT id, entry_id, state FROM exceptions WHERE id = $1 FOR UPDATE` —
   serialises concurrent decisions on this case (FR-11.10, FR-11.12 acceptance
   4). Not found is an internal invariant breach here (the route already
   resolved the identifier) — throw a plain `Error` prefixed
   `DECISION_READ_INVARIANT` so it falls to the generic 500 path, never a
   client-facing 404.
2. If `state !== 'OPEN'`: load the existing decision via
   `loadDecisionByException(tx, exceptionId)` (already exists, read-only) and
   throw `ExceptionAlreadyDecidedError({decision_type, decided_by_display_name,
   decided_at})` — the route turns this into the exact Y2 message "This case
   was already {resolved/rejected} by {name} on {date}."
3. Load the recommendation: `loadRecommendationByException(tx, exceptionId)`
   (existing). It is NEVER null (F5 FR-5.12 guarantees a PENDING placeholder at
   minimum) — if it somehow is, throw the same internal invariant error as
   step 1. `recommendationId = recommendation.id` — ALWAYS set on the decision
   row (see Task 1's note); there is no "no recommendation" branch to handle.
4. If `body.recommendation_id` is supplied and `!== recommendation.id`: throw
   `RecommendationMismatchError()` (FR-11.16).
5. Branch on `body.decision_type`:

   **`APPROVE`** (FR-11.3, FR-11.6):
   - `recommendation.status !== 'AVAILABLE'` → throw
     `RecommendationNotAvailableError()`.
   - `body.resolution_values !== undefined` → throw
     `ResolutionValuesNotAllowedError()` (client must not supply values).
   - Load `loadRecommendationValues(tx, recommendation.id)` (existing) and copy
     EVERY proposed value verbatim: `value = proposed_value`, `origin='AI'`,
     `prior_value = proposed_value`, `prior_origin='AI'`,
     `changed_from_proposal=false`.
   - `resultingState = 'RESOLVED'`. `reason = body.reason ?? null` (optional;
     if present, 10–2000 chars trimmed — same length check as EDIT_APPROVE/
     REJECT, else `ReasonRequiredError` naming "too short" specifically — see
     the shared `validateReason` helper below).

   **`EDIT_APPROVE`** (FR-11.4, FR-11.7, FR-11.8):
   - `validateReason(body.reason, required: true)` — throw
     `ReasonRequiredError()` if absent/blank/<10 chars after trim, or >2000.
   - `body.resolution_values === undefined || .length === 0` → throw
     `ResolutionValuesNotAllowedError()` is WRONG here — this is the
     "required but missing" case, which the route's zod layer should already
     catch structurally (see Task 3). If it somehow reaches the service empty,
     treat as `ResolutionValuesIncompleteError({missing: ['(at least one field)'], unexpected: []})`.
   - Reject any DUPLICATE `field_name` in `resolution_values` — throw a plain
     validation error the route maps to `422 REQUEST_MALFORMED` (structural,
     not a decision-specific code).
   - **If `recommendation.status === 'AVAILABLE'`** (has a real proposal):
     load `loadRecommendationValues(tx, recommendation.id)`. The submitted
     field-name SET must equal the proposed field-name SET EXACTLY — compute
     `missing` (proposed fields absent from submission) and `unexpected`
     (submitted fields absent from the proposal); if either is non-empty throw
     `ResolutionValuesIncompleteError({missing, unexpected})` (FR-11.7). For
     each submitted value, find its matching proposed value and apply the
     TRIM-THEN-BYTE-COMPARE rule (FR-11.8, TechArch §3.5.3):
     `submitted.trim() === proposed.proposed_value.trim()` → `origin='AI'`,
     `changed_from_proposal=false`; else → `origin='HUMAN'`,
     `changed_from_proposal=true`. `prior_value = proposed.proposed_value`,
     `prior_origin='AI'` always in this branch (the exact-set-match guarantees
     a proposal exists for every field).
   - **Else** (`PENDING`/`UNAVAILABLE` — "direct resolution", FR-11.2's own
     term): every `field_name` MUST be a member of `ENTRY_FIELDS` (the 14-field
     set — the route's zod schema already constrains this, but re-check
     defensively), at least one field required. For each: `origin='HUMAN'`,
     `changed_from_proposal=true`. `prior_value`/`prior_origin`: load
     `loadEntryDetail(tx, exception.entry_id)` (existing) once, and for each
     field take `entry.values[field_name]` as `prior_value` (`prior_origin =
     'HUMAN'` if non-null, else `null` — an entry value is always HUMAN
     origin by construction, F3).
   - `resultingState = 'RESOLVED'`.

   **`REJECT`** (FR-11.5):
   - `validateReason(body.reason, required: true)` — same rule as EDIT_APPROVE.
   - `body.resolution_values !== undefined` → throw
     `ResolutionValuesNotAllowedError()`.
   - ZERO `decision_values` rows written (nothing is adopted).
   - Compute the AUDIT entry's value rows separately from `decision_values`
     (TechArch §3.6 row `RECOMMENDATION_REJECTED`): if
     `recommendation.status === 'AVAILABLE'`, one audit value row per proposed
     value with `before_value = proposed_value`, `before_origin='AI'`,
     `after_value=null`, `after_origin=null`; otherwise zero audit value rows
     (nothing was proposed to decline).
   - `resultingState = 'REJECTED'`.

6. `lockCaseAnchor(tx, exception.entry_id)` (existing — reuses the SAME
   case-anchor lock `append()` also takes defensively; taking it once here
   mirrors `receipt.service.ts`'s own step 10).
7. `insertDecision(tx, {...})` — `recommendation_id = recommendation.id`
   ALWAYS (see step 3), `idempotency_key = idempotencyKey`.
8. `insertDecisionValues(tx, decision.id, resolutionValues)` — empty array for
   REJECT.
9. `UPDATE exceptions SET state=$1, closed_at=now(), decision_id=$2 WHERE
   id=$3` — this is the ONE `UPDATE exceptions` statement this service is
   EVER permitted (receiptPaths.spec's allowlist, Task 3 of this plan, names
   this exact file). Do not import or call anything from `exceptions.ts` that
   writes `state`/`closed_at`/`decision_id` — there is no such function to

10. `append(tx, {...})` — EXACTLY ONE call (FR-11.13):
    `action_type` = `APPROVE→'RECOMMENDATION_APPROVED'`,
    `EDIT_APPROVE→'RECOMMENDATION_EDITED_AND_APPROVED'`,
    `REJECT→'RECOMMENDATION_REJECTED'`; `actor: {type:'SPECIALIST',
    specialist_id: principal.id}`; `case_id: exception.entry_id`;
    `exception_id`, `recommendation_id: recommendation.id`, `decision_id:

    `reason` (the writer's own `REASON_REQUIRED`/`REASON_FORBIDDEN` sets

    ENTRY_RECEIVED-etc-forbid-reason — APPROVE is in NEITHER set, so it
    accepts an optional reason with no writer-level objection); `values`: for
    APPROVE/EDIT_APPROVE, one row per resolution value (`before_value:
