<objective>
Prove phase success criteria 2, 3 and 4 by deliberately mis-writing transactions and watching
the database refuse them — at `COMMIT` for the deferred triggers, at the statement for the
`CHECK`s and foreign keys.

Purpose: the coupling and HITL guarantees are only meaningful if a half-written transaction
genuinely cannot commit. The only way to know that is to write one on purpose, from a direct
SQL session holding full application privileges, and assert the rejection. This is RTM
TEST-DB-04 through TEST-DB-12 and TEST-DB-18 — nine of the eighteen assertions of the
governance suite.

Output: three spec files under `server/test/db/`, run by `npm run test:db`.
</objective>

<suite_conventions>
- One fresh database per file: `createTestDatabase()` in `beforeAll`, `dropTestDatabase()` in
  `afterAll`. Each test builds its own `GovernedCase` so a failed transaction in one test
  cannot leave another test depending on rolled-back state.
- **Connect as `cargoexec_app`** for these suites unless a test needs another role. The point
  of criterion 3 is that the refusal holds "even from a direct SQL session with full
  application privileges" — so use exactly those privileges, not the owner's.
- Assert the **refusal layer** every time, by SQLSTATE and message:
  - deferred constraint triggers → `P0001`, message begins `HITL_VIOLATION:` or
    `AUDIT_COUPLING_VIOLATION:`
  - `CHECK` → `23514` plus the constraint name
  - `UNIQUE` → `23505` plus the index name
  - foreign key → `23503` plus the constraint name
  A bare `expect(...).rejects.toThrow()` is not acceptable: it would pass if the table did
  not exist.
- For every deferred-trigger test, additionally assert **where** the failure happened: the
  individual `INSERT`/`UPDATE` statements must all succeed and only the `COMMIT` must throw.
  That distinction is phase success criterion 2's phrasing — "fails at `COMMIT` rather than
  committing half of itself" — and it is the difference between a deferred constraint trigger
  and an immediate one. Structure the test by issuing the statements explicitly and awaiting
  each, then awaiting `COMMIT` inside its own `expect(...).rejects`.
- After every refused transaction, assert the database is unchanged: the exception is still
  `OPEN`, zero rows were added to the table under test, and `verify_audit_chain` is still true.
- Never disable a trigger, never `SET CONSTRAINTS ALL IMMEDIATE` to "make the error arrive
  earlier", never use the owner or superuser to sidestep a privilege.
</suite_conventions>

**TEST-DB-04 — an exception cannot leave `OPEN` without a matching human decision.**

Using a `GovernedCase` and a raw `cargoexec_app` client (explicit `BEGIN` … `COMMIT`, not

1. `BEGIN`
2. `UPDATE exceptions SET state = 'RESOLVED', closed_at = now(), decision_id = $fakeUuid
   WHERE id = $1` — expect this to fail on `exceptions_decision_fk` (`23503`), because
   `decision_id` must reference a real `decisions` row. Roll back. This is the *first* of the
   layers and worth asserting separately.

   `UPDATE exceptions SET state='RESOLVED', closed_at=now(), decision_id=$thatDecisionId`.

   `HITL_VIOLATION` (`P0001`). Assert every prior statement succeeded.

   `decision_type='REJECT'`/`resulting_state='REJECTED'`, then set the exception to
   `'RESOLVED'`. `d.resulting_state <> NEW.state`, so expect `COMMIT` to raise
   `HITL_VIOLATION`.
5. The positive control, so the suite proves a *precise* refusal rather than a broken table:
   a transaction that inserts a matching `decisions` row (with `decided_by` = a real
   specialist, a `recommendation_id` for `APPROVE`), writes its `RECOMMENDATION_APPROVED`
   audit entry through `append`, and sets the exception to `RESOLVED` with `closed_at` and
   `decision_id` **commits successfully**. Without this control, a suite that accidentally
   broke all writes would look like a pass.
6. After each refused transaction, re-read the exception and assert `state='OPEN'`,
   `closed_at IS NULL`, `decision_id IS NULL`.

Add one assertion that names the crux explicitly: attempt `INSERT INTO decisions (...,

`decisions_decided_by_fkey` — the AI has no row in `specialists`, so a machine-authored

|----------|-------------|
| direct-SQL-session→governed record | A client holding full `cargoexec_app` privileges deliberately writing a half-transaction, exactly the adversary phase success criteria 2 and 3 describe |
| application-defect→database | A future service that forgets to audit, forgets a decision row, or writes a value with no origin |
| AI-attribution→resolution | A path by which a machine-originated value could be recorded as human, or a resolution recorded with no named human |
