<objective>
Prove the negative. For each way history could be rewritten, attempt it and assert the
database refused — **including as `cargoexec_owner`**, which is the case privilege revocation
does not cover and the case phase success criterion 1 names explicitly.

Purpose: "we never call UPDATE" is not evidence. "UPDATE was attempted and the database
rejected it, as the schema owner, and the row is byte-identical afterwards" is. This suite is
the SM-7 mechanism: 100% of mutation attempts rejected, including attempts made directly
against the database.

Output: `server/test/db/immutability.spec.ts`, covering RTM TEST-DB-01, 02, 03, 16 and 17.
</objective>

<suite_conventions>
- One fresh database per file: `createTestDatabase()` in `beforeAll`, `dropTestDatabase()` in
  `afterAll`. Teardown **drops**; `TRUNCATE` is impossible on the audit tables, which is
  itself part of what this suite proves (TechArch §8.2).
- Connect as all three roles from `TestDatabase.appUrl`, `aiUrl` and `ownerUrl`. Several
  assertions are specifically about what the **owner** also cannot do — a suite that only
  tests the app role would pass against a completely unprotected audit store.
- Every refusal assertion must check the **error text or SQLSTATE**, not merely that
  something threw. A `relation does not exist` would otherwise pass as "refused".
  - Trigger refusals: message contains `AUDIT_IMMUTABLE`, SQLSTATE `P0001`.
  - Privilege refusals: SQLSTATE `42501` (`insufficient_privilege`).
  Assert one or the other explicitly per case, and say in the assertion message which layer
  is expected to have refused.
- Never disable a trigger, never `SET session_replication_role`, never connect as the
  Postgres superuser to make an assertion pass. If a test cannot be written without doing
  that, the test is telling you something true.
</suite_conventions>

**TEST-DB-01 — `UPDATE` refused for `cargoexec_app`, `cargoexec_ai` and `cargoexec_owner`.**
For each of the three roles, run each of these and assert refusal:
- `UPDATE audit_entries SET action_type = 'X'` (no `WHERE` — the statement-level trigger
  must fire even before row selection)
- `UPDATE audit_entries SET action_type = 'RECOMMENDATION_APPROVED' WHERE id = $1` targeting
  a real entry
- `UPDATE audit_entries SET reason = 'rewritten' WHERE case_id = $1`
- `UPDATE audit_entry_values SET after_value = 'rewritten' WHERE audit_entry_id = $1`
- `UPDATE audit_entries SET action_type = 'X' WHERE false` — zero matching rows, and it must
  **still** be refused, which is the difference between a row trigger and a statement trigger
For `cargoexec_app` and `cargoexec_ai` the expected refusal may be the privilege layer
(`42501`) *or* the trigger (`P0001` / `AUDIT_IMMUTABLE`) depending on which the server
evaluates first — accept either, and assert explicitly that for `cargoexec_owner` it is the
**trigger** (`AUDIT_IMMUTABLE`, `P0001`), because the owner holds the privilege and only the
trigger can stop it. That distinction is the whole point of FR-0.5.

**TEST-DB-02 — `DELETE` and `TRUNCATE` refused for all three roles.**
For each role:
- `DELETE FROM audit_entry_values` (unqualified)
- `DELETE FROM audit_entry_values WHERE audit_entry_id = $1`
- `DELETE FROM audit_entries WHERE case_id = $1`
- `TRUNCATE audit_entries`
- `TRUNCATE audit_entry_values`
- `TRUNCATE audit_entries, audit_entry_values CASCADE`
Same layer expectation as above; for `cargoexec_owner`, assert `AUDIT_IMMUTABLE`.

**TEST-DB-03 — `INSERT … ON CONFLICT DO UPDATE` refused.**
As `cargoexec_owner` (so privilege is not the reason), attempt:
```sql
INSERT INTO audit_entries (id, case_id, case_sequence, action_type, actor_type,
  actor_specialist_id, after_state, prev_entry_hash, entry_hash)
VALUES ($1, $2, 1, 'ENTRY_RECEIVED', 'SPECIALIST', $3, 'RECEIVED', $4, $5)
ON CONFLICT (case_id, case_sequence) DO UPDATE SET action_type = 'X'
```
against the existing sequence-1 entry, and assert it fails with `AUDIT_IMMUTABLE` — the
`DO UPDATE` branch fires the `BEFORE UPDATE` row trigger. Do the same for
`audit_entry_values` with `ON CONFLICT (audit_entry_id, field_name) DO UPDATE`.
Also attempt `ON CONFLICT DO NOTHING` on a conflicting row and assert it is **allowed** (it
performs no update) — this distinguishes "upsert is blocked" from "insert is broken", and
guards against a future change that accidentally blocks legitimate inserts.

**After-state assertion, applied once at the end of each describe block:** re-read every
audit row and value row for the case and assert the snapshot is byte-identical to the
"before" capture — same `action_type`, same `reason`, same `occurred_at`, same
`entry_hash`, same row count. A refusal that nonetheless left a partial change would be a
worse failure than an accepted update.

Finally assert `verify_audit_chain(case_id)` still returns `chain_verified = true` with
`entry_count = 3` after all attempts.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| owner/superuser→audit store | A direct SQL session with full DDL privilege attempting to rewrite, delete or truncate history |
| app-role→entry of record | The request-path pool attempting to overwrite a submitted cargo entry rather than recording a correction |
| ai-worker→resolution tables | The recommendation worker's pool attempting to write a decision or close an exception |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-46 | Tampering | audit history rewritten by the schema owner | mitigate | `server/test/db/immutability.spec.ts` attempts every `UPDATE`/`DELETE`/`TRUNCATE` variant as `cargoexec_owner` and asserts `AUDIT_IMMUTABLE` with SQLSTATE `P0001` specifically — proving the trigger from `0009_invariant_triggers.sql`, not a privilege, did the refusing |
| T-01-47 | Tampering | history rewritten via an upsert convenience path | mitigate | The `ON CONFLICT DO UPDATE` cases in the same spec assert the `BEFORE UPDATE` row trigger fires on the update branch, closing the path an ORM's `save()` would take |
| T-01-48 | Tampering | the entry of record overwritten instead of corrected | mitigate | The TEST-DB-16 block asserts `cargoexec_app` receives `42501` on `UPDATE cargo_entries` and re-reads the row byte-identically, including internal whitespace and case, so a correction cannot masquerade as the original submission |
| T-01-49 | Elevation of privilege | the AI worker resolving a case | mitigate | The TEST-DB-17 block asserts `42501` on `INSERT INTO decisions`, on `SELECT FROM decisions/specialists/sessions`, and on `UPDATE exceptions` for `cargoexec_ai`, then asserts the exception is still `OPEN` with no decision row |
