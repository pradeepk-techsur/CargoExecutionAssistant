<objective>
Build the single chokepoint through which all history is written: `append(tx, entry)`.
Plus the transaction helper it requires, the two connection pools, and the case fixture
builder that every database suite in wave 6 depends on.

Purpose: the database refuses an unaudited change (plan 01-05) — but something must actually
write the audit entries, and F13 requires that something to be **one module with one
operation**, unable to open its own transaction, unable to update or delete, and unable to
accept a timestamp or an actor from a client. That module is what makes the deferred coupling
triggers satisfiable in the first place, and it is what plans 01-08 through 01-10 use to
construct the records they then try to tamper with.

Output: `db/tx.ts`, `db/pool.app.ts`, `db/pool.ai.ts`, `services/audit/writer.ts`, a case
fixture builder, and the writer's own integration suite.
</objective>

<single_writer_rule>
`server/src/services/audit/writer.ts` is the **only** module under `server/src/` permitted to
**write** `audit_entries` or `audit_entry_values` — i.e. to contain `INSERT INTO audit_entr`
(rule R-L3). Read-only modules may `SELECT` from them: plan 01-10 adds
`server/src/services/auditRead.service.ts`, which names both tables in queries and is
deliberately within the rule. Do **not** create `server/src/db/repositories/audit.ts`. The writer holds its own hand-written
parameterised SQL. Test helpers under `server/test/` are outside this rule and may query the
tables to make assertions.

`server/src/db/tx.ts` is the **only** module permitted to issue `BEGIN`, `COMMIT` or
`ROLLBACK` (rule R-L2; TEST-ARCH-07 asserts it).
</single_writer_rule>

<no_orm_rule>
Hand-written parameterised SQL only. Every value is a `$n` placeholder — no template-literal
interpolation of any value anywhere in `server/src/`. Do not add `prisma`, `typeorm`,
`sequelize`, `knex`, `drizzle-orm` or `mikro-orm`: an ORM's dirty-flush is precisely the
mechanism that would emit an `UPDATE` against an append-only table (PRD R-4, TechArch §6.3).
</no_orm_rule>

```ts
export async function withTransaction<T>(
  pool: Pool,
  fn: (tx: PoolClient) => Promise<T>,
): Promise<T> {
  const client = await pool.connect();
  try {
    await client.query('BEGIN');
    await client.query("SET LOCAL statement_timeout = '10s'");
    const result = await fn(client);
    await client.query('COMMIT');
    return result;
  } catch (err) {
    try { await client.query('ROLLBACK'); } catch { /* connection already gone */ }
    throw err;
  } finally {
    client.release();
  }
}
```
Requirements:
- `SET LOCAL statement_timeout = '10s'` for request-path transactions (TechArch §8.8).
  Accept an options argument `{ statementTimeoutMs }` so a longer-running fixture or
  concurrency test can raise it, defaulting to 10000.
- The error from `fn` must **propagate unchanged** after the rollback — never swallowed,
  never wrapped in a generic message. `AUDIT_COUPLING_VIOLATION` and friends are raised at
  `COMMIT`, so a caller must be able to read the original `error.message` and `error.code`.
- Add `export async function withTransactionExpectingFailure` **only if** a wave-6 plan needs
  it — otherwise do not; the suites can use try/catch around `withTransaction`.
- Do not add a retry loop. `AUDIT_SEQUENCE_CONFLICT` is surfaced to the caller, never
  silently retried (F13 §Error States).

  <action>
Implement `append(tx, entry)` exactly to F13 and TechArch §1A.3. Its signature and types are
given in this plan's `integration_contracts.provides` — implement them literally.

**Interface (FR-13.2).** Exactly one exported operation plus its types. There is **no**
`update`, `delete`, `upsert`, `merge`, `redact`, `correct`, `anonymise`, `backfill`, `purge`
or `truncate` function — not exported, and not present as a private helper either. Put a
file-header comment saying so.

**Transactional coupling (FR-13.3).** `tx: PoolClient` is the first parameter and is
required. The module must not import `getAppPool`, `getAiPool`, or `withTransaction`, and
must never call `BEGIN`. If a caller passes something without a `.query` method, throw
`AUDIT_WRITE_INVALID`.

**Validation, in this order, all raising before any SQL is issued:**
1. `action_type` is one of the eight (`ENTRY_RECEIVED`, `VALIDATION_COMPLETED`,
   `EXCEPTION_OPENED`, `RECOMMENDATION_GENERATED`, `RECOMMENDATION_UNAVAILABLE`,
   `RECOMMENDATION_APPROVED`, `RECOMMENDATION_EDITED_AND_APPROVED`,
   `RECOMMENDATION_REJECTED`) — else `AUDIT_WRITE_INVALID`.
2. Actor pairing (FR-13.7): `SPECIALIST` ⇒ `specialist_id` present; `AI` ⇒ no id;
   `SYSTEM` ⇒ `on_behalf_of_specialist_id` present and written into
   `actor_specialist_id`. Anything else ⇒ `AUDIT_WRITE_INVALID`.
3. `after_state` non-empty. `before_state` may be `null` only for the creation actions
   `ENTRY_RECEIVED` and `EXCEPTION_OPENED`.
4. `reason` is required (non-blank, `btrim` length ≥ 10) for
   `RECOMMENDATION_EDITED_AND_APPROVED` and `RECOMMENDATION_REJECTED`; and must be `null`
   or absent for `ENTRY_RECEIVED`, `VALIDATION_COMPLETED`, `EXCEPTION_OPENED`,
   `RECOMMENDATION_GENERATED` and `RECOMMENDATION_UNAVAILABLE`. Else `AUDIT_WRITE_INVALID`.
   (`RECOMMENDATION_APPROVED` may carry one or not — the database's
   `ae_reason_only_on_decisions_chk` permits it.)
5. Every `field_name` is a member of `ENTRY_FIELDS` from `@cargoexec/contract`. Anything
   else ⇒ `AUDIT_WRITE_INVALID`.
6. **Secrets denylist (FR-13.12).** Reject and raise `AUDIT_WRITE_FORBIDDEN_CONTENT` if a
   `field_name` matches `/password|passwd|token|secret|api[_-]?key|authorization|cookie|csrf|credential/i`,
   or if a `before_value`/`after_value` matches a secret shape:
   `/^Bearer\s+\S+/i`, `/\bsk-[A-Za-z0-9_-]{16,}\b/`, or a JWT
   `/^[A-Za-z0-9_-]{8,}\.[A-Za-z0-9_-]{8,}\.[A-Za-z0-9_-]{8,}$/`.
   Raise — do **not** silently drop the value. The transaction must abort.
7. Each value row has at least one of `before_value` / `after_value` non-null, and an origin
   on each side that has a value (the database enforces this too; fail early with a clear
   message).

**Timestamp authority (FR-13.8).** `occurred_at` is **not** a parameter of `append`. Obtain
it inside the transaction with `SELECT now() AS occurred_at` (the transaction timestamp is
stable across the transaction) and use that single value both for the hash payload and as the
explicit `occurred_at` column value in the `INSERT`. Explain in a comment why the value is
read back rather than left to the column default: the hash must cover the same timestamp the
row stores, and an audit row cannot be updated afterwards to reconcile them.

**Sequence assignment (FR-13.5).** The caller holds the case-anchor lock. Inside `append`:
```sql
SELECT id FROM cargo_entries WHERE id = $1 FOR UPDATE
```
Take the lock defensively here as well — it is idempotent when the caller already holds it,
and it guarantees the invariant even if a caller forgets. If the row does not exist, raise
`AUDIT_WRITE_INVALID` ("case_id does not exist"). Then:
```sql
SELECT coalesce(max(case_sequence), 0) + 1 AS next_sequence FROM audit_entries WHERE case_id = $1
```
`UNIQUE (case_id, case_sequence)` is the backstop; map a `23505` on that constraint to
`AUDIT_SEQUENCE_CONFLICT` and rethrow. Never retry.

**Hash chain (FR-13.6).** `prev_entry_hash` is `ZERO_HASH` when `case_sequence === 1`,
otherwise:
```sql
SELECT entry_hash FROM audit_entries WHERE case_id = $1 AND case_sequence = $2
```
for `case_sequence - 1`. Compute `entry_hash = computeEntryHash(payload, prevEntryHash)`
using `server/src/db/canonical.ts`, with `changed` derived per value row as
`before_value !== after_value` (strict comparison of the verbatim strings — no trimming, no
case folding; FR-13.11).

**Writes.** One parameterised `INSERT INTO audit_entries (...) VALUES ($1…$16) RETURNING id`,
then, if there are value rows, one parameterised multi-row
`INSERT INTO audit_entry_values (audit_entry_id, field_name, before_value, before_origin,
after_value, after_origin, changed) VALUES …`. Never `ON CONFLICT` — the immutability trigger
rejects the `DO UPDATE` branch and there is no legitimate conflict. Return the new
`audit_entry_id` (FR-13.16 callers need it).

**Failure is loud (FR-13.16).** No `try`/`catch` that swallows. No fallback file. No queue.
No logging-and-continuing. The only permitted catch maps the `23505` unique violation to
`AUDIT_SEQUENCE_CONFLICT` and immediately rethrows.

Raise errors as a small `AuditWriteError extends Error` carrying `code:
InternalInvariantCode` from `@cargoexec/contract`, so the API layer of a later phase can map
them to the generic `500 RECEIPT_FAILED` / `DECISION_FAILED` without ever leaking the internal
code to a client.
