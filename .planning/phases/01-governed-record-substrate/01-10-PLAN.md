<objective>
Close phase success criterion 5: a removed, altered or reordered audit entry is detectable
from the per-case sequence and hash chain, and **the verifier reports the break rather than
repairing it**.

Three things make that true and all three are tested here: sequence assignment under the
case-anchor lock survives concurrency (no gap, no duplicate); a forged `prev_entry_hash`
cannot be committed even from a direct SQL session; and a genuinely excised entry — which
requires dropping the immutability triggers in a *copy* of the database, because it is
otherwise impossible — is detected by `verify_audit_chain`, which returns `false` and the
divergent sequence and changes nothing.

This plan also ships the read half of F13 (FR-13.15): a strictly read-only service returning
one case's trail with its `chain_verified` result, which F14 consumes in phase 6.

Output: `server/src/services/auditRead.service.ts` and `server/test/db/chain.spec.ts`.
</objective>

<read_path_rule>
`readCaseTrail` is **strictly read-only and strictly per-case** (FR-13.15, FR-13.18). It must
not expose a bulk read, a cross-case query, a download, a report, a streaming feed, a
`format` option, or a limit/offset over multiple cases. It takes exactly one `caseId` and
returns exactly that case's entries. Do not add a "list all cases" convenience — the trail is
read per case, in the UI, and nowhere else.

It must also not write: no `INSERT`, no `UPDATE`, no `DELETE`, and no repair of any kind.
When `chain_verified` is `false` it returns that fact with the divergent sequence and the
entries as stored. The UI surfaces the result and offers no repair action (F14, Y2 §8).
</read_path_rule>

the actor type already carries that, and inventing a display name for the machine would blur
exactly the distinction the product exists to preserve.

```sql
SELECT audit_entry_id, field_name, before_value, before_origin,
       after_value, after_origin, changed
  FROM audit_entry_values
 WHERE audit_entry_id = ANY($1::uuid[])
 ORDER BY audit_entry_id, field_name ASC
```
Group them onto their entries in memory. Order by `field_name` so a rendered trail is stable
and matches the order the hash covers.

**TEST-DB-13 — two concurrent audit writes to one case.**
Open **two** separate `cargoexec_app` clients (distinct connections, not two calls on one
client — the serialisation under test is row-level locking, which a single connection cannot
exercise). In each, `BEGIN`, then call `append` for the same `case_id` with a valid action.
Start both, await both, `COMMIT` both. Assert:
- Both succeed.
- The case now has audit entries with contiguous `case_sequence` values and **no gap and no
  duplicate** — for a fixture case already holding 1–3, the two new entries are 4 and 5.
- Each new entry's `prev_entry_hash` equals the previous entry's `entry_hash`.
- `global_sequence` is strictly increasing across all five.
- `verify_audit_chain` returns `chain_verified = true`, `entry_count = 5`.
Structure it so the second `append` genuinely waits on the first's `SELECT … FOR UPDATE`:
issue the first `append` and await it, then issue the second `append` *before* committing the
first, and assert the second promise is still pending (e.g. race it against a short timer)
until the first commits. That is the observation that proves the anchor lock serialises
writers rather than that the test happened to run sequentially. Raise the transaction
`statementTimeoutMs` for this test so the deliberate wait does not trip the 10 s default.

Also assert the backstop: with the lock deliberately bypassed (two clients each computing
`case_sequence` before either inserts — achievable by reading `max(case_sequence)` manually in
both before calling a raw insert), one transaction fails with `23505` on
`uq_audit_entries_case_sequence`, surfaced by the writer as `AUDIT_SEQUENCE_CONFLICT`, and it
is **not** retried silently.

**TEST-DB-14 — a tampered `prev_entry_hash` is refused at `COMMIT`.**
As `cargoexec_app`, with a raw client and explicit `BEGIN`:
- Insert a well-formed `audit_entries` row for an existing case at `case_sequence = n+1`, but
  with `prev_entry_hash` set to 32 arbitrary bytes that are **not** the previous entry's
  `entry_hash`. Assert the `INSERT` **succeeds** and the `COMMIT` raises `AUDIT_CHAIN_BROKEN`
  (`P0001`) — the refusal is deferred, which is the property under test.
- Insert at `case_sequence = 1` for a fresh case with a non-zero `prev_entry_hash` → `COMMIT`
  raises `AUDIT_CHAIN_BROKEN`.
- Insert at `case_sequence = n+2`, skipping `n+1` → the trigger's lookup finds no previous
  entry, `expected IS NULL`, and `COMMIT` raises `AUDIT_CHAIN_BROKEN`.
- Positive control: a correctly linked entry written through `append` commits.
- After each refusal, assert the case's entry count and `verify_audit_chain` result are
  unchanged.
Note in a comment that this is why the chain is verified by a **deferred constraint trigger**
rather than only in application code: a broken link cannot be committed even from a direct
SQL session (TechArch §1.4(1)).

**Step 3 — excise in the copy.** Connect to the copy as `cargoexec_owner` and:
```sql
DROP TRIGGER trg_audit_entries_immutable ON audit_entries;
DROP TRIGGER trg_audit_entries_immutable_row ON audit_entries;
DROP TRIGGER trg_audit_entry_values_immutable ON audit_entry_values;
DROP TRIGGER trg_audit_entry_values_immutable_row ON audit_entry_values;

DELETE FROM audit_entries WHERE id = $middleEntryId;
```

precedent. The verify step for this task greps every *other* spec file for `DROP TRIGGER` and
