<objective>
Close phase success criterion 5: a removed, altered or reordered audit entry is detectable
from the per-case sequence and hash chain, and **the verifier reports the break rather than
repairing it**.

Three things make that true and all three are tested here: sequence assignment under the
case-anchor lock survives concurrency (no gap, no duplicate); a forged `prev_entry_hash`
cannot be committed even from a direct SQL session; and genuinely tampered history — which
requires dropping the immutability triggers in *copies* of the database, because it is
otherwise impossible — is detected, with the verifier returning `false` and the divergent
sequence and changing nothing.

Tampering is tested as **four independent copies of the pristine fixture**, one per tamper,
never cumulatively against a single copy: an excision at sequence 3 already makes the walk
diverge at sequence 4, which would mask a later alteration at sequence 2 behind the identical
result and leave the alteration and reordering assertions proving nothing. The excision,
alteration and reordering copies each assert the exact
`(chain_verified, first_divergence_sequence, entry_count)` triple, so the three are mutually
distinguishable. The fourth copy covers **content substitution**, which `verify_audit_chain`
cannot see at all — it checks linkage, never recomputing `entry_hash` from row content — and
which is instead caught by recomputing the entry digest with `computeEntryHash` over the
stored row. Linkage and recomputation together are what make TechArch §2.12's claim true.

This plan also ships the read half of F13 (FR-13.15): a strictly read-only service returning
one case's trail with its `chain_verified` result, which F14 consumes in phase 6.

Output: `server/src/services/auditRead.service.ts` and `server/test/db/chain.spec.ts`.
</objective>

<read_path_rule>
`readCaseTrail` is **strictly read-only and strictly per-case** (FR-13.15, FR-13.18). It must
not expose a bulk read, a cross-case query, a download, a report, a streaming feed, a
`format` option, or a limit/offset over multiple cases. It takes exactly one `caseId` and
returns exactly that case's entries. Do not add a "list all cases" convenience — the trail is
read per case, in the UI, and nowhere else.

It must also not write: no `INSERT`, no `UPDATE`, no `DELETE`, and no repair of any kind.
When `chain_verified` is `false` it returns that fact with the divergent sequence and the
entries as stored. The UI surfaces the result and offers no repair action (F14, Y2 §8).
</read_path_rule>

middle entry cannot be removed at all — which is the first thing the test must prove.

Build a case with at least five audit entries (the three-entry fixture plus two more through
`append`). Then:

**Step 1 — prove excision is impossible in place.** As `cargoexec_owner`, attempt
`DELETE FROM audit_entries WHERE case_id = $1 AND case_sequence = 3` and assert it fails with
`AUDIT_IMMUTABLE`. Record in a comment that the only way to obtain a tampered database for
this test is to build one deliberately, which is itself the evidence.

**Step 2 — snapshot the pristine fixture, and prove writer↔verifier parity.** Before any
tampering, read all five entries ordered by `case_sequence` together with their
`audit_entry_values` rows and keep them in memory as `pristine`. Every expected value below is
**computed from `pristine`**, never hard-coded.

While the fixture is still pristine, assert the parity positive control: for each entry,
`computeEntryHash` (from `server/src/db/canonical.ts`) recomputed over the stored row and its
stored value rows equals the stored `entry_hash`. This proves the writer and the independent
recomputation agree on canonicalisation, and it is the control that makes the divergences in
Step 7 meaningful rather than an artefact of a mismatched hash function.

**Step 3 — make four independent copies from the pristine test database.** Close every pool
and client against the test database. Then, as `cargoexec_owner` connected to the `postgres`
maintenance database, for each of the four copy names in turn:
```sql
SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname = $1 AND pid <> pg_backend_pid();
CREATE DATABASE "<copy_name>" TEMPLATE "<test_db_name>" OWNER cargoexec_owner;
```
The `pg_terminate_backend` pass runs **before every one** of the four `CREATE DATABASE`
statements — `CREATE DATABASE … TEMPLATE` fails outright if the template has any active
connection, and each statement can leave one behind. Create all four copies **before** opening
a pool against any of them. `copy_name` is generated and regex-validated exactly as
`testdb.ts` does.

Each copy is tampered **exactly once, from pristine**. This is the whole point of making four:
tampering cumulatively against a single copy masks later tampers behind earlier ones. Excising
`case_sequence = 3` makes the walk diverge at sequence 4, and a subsequent "alter entry 2, expect
divergence at entry 3" assertion is then **vacuous** — entry 3 no longer exists, the verifier
returns the same `(false, 4, 3)` it already returned for the excision, and a naive
`chain_verified === false` check passes while proving nothing. State this in a comment so the
four-copy structure is not later "simplified" back into one.

In every copy, tampering first requires dropping the immutability guards:
```sql
DROP TRIGGER trg_audit_entries_immutable ON audit_entries;
DROP TRIGGER trg_audit_entries_immutable_row ON audit_entries;
DROP TRIGGER trg_audit_entry_values_immutable ON audit_entry_values;
DROP TRIGGER trg_audit_entry_values_immutable_row ON audit_entry_values;
```
This is the **only** place in the entire phase where a guard may be dropped, and it is done in
throwaway copies to manufacture the tampered artefacts the verifier must detect. Add a
prominent comment saying so, naming this test, so a future reader does not take it as a
precedent. The verify step for this task greps every *other* spec and helper file for
`DROP TRIGGER` and fails if one appears.

**Step 4 — copy A, excision.** Delete the middle entry and its values:
```sql
DELETE FROM audit_entry_values WHERE audit_entry_id = $middleEntryId;
DELETE FROM audit_entries WHERE id = $middleEntryId;
```
Assert `verify_audit_chain(case_id)` returns exactly `(chain_verified = false,
first_divergence_sequence = 4, entry_count = 3)`, deriving both numbers from `pristine` (the
sequence *following* the excised one, and the excised one's walk position). State the reasoning
in a comment: rows 1, 2, 4, 5 remain; walk position n=1 matches stored sequence 1 with
`prev_entry_hash = ZERO_HASH`; n=2 matches stored sequence 2 with `prev_entry_hash = hash1`;
at n=3 the next row carries stored `case_sequence = 4`, and `4 <> 3` diverges.
`first_divergence_sequence` is the offending row's **stored** sequence, `entry_count` is the
**walk position reached**, not the surviving row count.

**Step 5 — copy B, alteration.** In a *pristine* copy, alter a stored hash:
```sql
UPDATE audit_entries SET entry_hash = <32 bytes differing from the stored value> WHERE case_id = $1 AND case_sequence = 2;
```
Assert `verify_audit_chain` returns exactly `(false, 3, 3)`. Reasoning, in a comment: n=1 is
intact; at n=2 the row's own stored sequence is 2 and its `prev_entry_hash` still matches
entry 1's untouched `entry_hash`, so n=2 passes; at n=3 the row's `prev_entry_hash` still holds
entry 2's **original** hash, which no longer equals entry 2's now-altered stored `entry_hash`,
so the link breaks. Assert the full triple, not merely `chain_verified === false`: copy A also
returns `chain_verified = false` with `entry_count = 3`, and only `first_divergence_sequence`
(3 here versus 4 there) distinguishes an alteration from an excision.

**Step 6 — copy C, reordering.** In a *pristine* copy, swap two entries' `case_sequence` values,
routing through a temporary out-of-range value to dodge `uq_audit_entries_case_sequence`:
sequence 2 → temporary, 3 → 2, temporary → 3. Assert `verify_audit_chain` returns exactly
`(false, 2, 2)`. Reasoning, in a comment: ordering by `case_sequence` now yields entry 1,
entry 3, entry 2, entry 4, entry 5; at n=2 the row is original entry 3, whose stored sequence is
2 and therefore matches the walk position, but whose `prev_entry_hash` is entry 2's hash while
the walk expects entry 1's hash — so reordering is caught by the **linkage** check, not the
sequence check.

**Step 7 — copy D, content substitution, and the honest limit of linkage-only verification.**
`verify_audit_chain` checks linkage only: stored `case_sequence` against walk position, and
`prev_entry_hash` against the previous row's `entry_hash`. It **never recomputes `entry_hash`
from row content**. So the realistic tamper — rewriting what an entry says, leaving the chain
columns untouched — is invisible to it. Assert both halves of that:

- In a *pristine* copy, `UPDATE audit_entries SET reason = <different text> WHERE case_id = $1
  AND case_sequence = <the decision entry's sequence>` — rewriting why a decision was made.
- Assert `verify_audit_chain` returns exactly `(chain_verified = true,
  first_divergence_sequence IS NULL, entry_count = 5)`. This is the true result. Assert it
  explicitly rather than omitting it: the boundary is documented by test, not by hope.
- Then recompute that entry's digest with `computeEntryHash` over the **stored** row and its
  **stored** `audit_entry_values` rows, and assert the recomputed digest **differs** from the
  stored `entry_hash`. This is what actually detects substitution.
- Repeat for a value row: alter one `audit_entry_values` stored value in the same copy and
  assert recomputation diverges there too, since value rows participate in the entry hash.

Add a comment stating the division of labour plainly, because TechArch §2.12 claims "any
excision, substitution, or reordering within a case breaks verification" and only both
mechanisms together make that true: **linkage** (`verify_audit_chain`) catches excision and
reordering; **recomputation** (`computeEntryHash`) catches substitution. Any later phase that
exposes a verification endpoint must run both.

**Step 8 — assert no repair, in every copy.** In each of the four copies, immediately re-read
every `audit_entries` row and assert it is byte-identical to the post-tamper snapshot taken
before verification: same `case_sequence` values (no renumbering), same `prev_entry_hash` and

annotation anywhere. Run `verify_audit_chain` a second time in each copy and assert it returns
the identical triple — a verifier that healed on first read would return `true` the second time.

exported function to call — assert the module's export list contains only `readCaseTrail` and
its types).

**Step 10 — teardown.** In `afterAll`, terminate backends against each of the four copies and
