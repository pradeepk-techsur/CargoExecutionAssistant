Implement `server/src/db/canonical.ts` exactly to the TechArch §2.12 specification.

**Canonical JSON** (used for hashing and for value comparison):
- object keys sorted lexicographically by UTF-16 code unit; no insignificant whitespace
- `timestamptz` as RFC 3339 UTC with microsecond precision (`2026-09-11T14:32:07.512000Z`)
- SQL `NULL` as JSON `null`
- decimals as unquoted fixed-scale numbers at the column's scale (`quantity` → 3 dp,
  `declared_value_usd` → 2 dp)
- strings verbatim, NFC-unnormalised — the record shows exactly what was typed

Implementation notes:
- Do **not** use `JSON.stringify` with a replacer and hope the key order is right. Write an
  explicit recursive serialiser: `null` → `null`; `boolean`/`number` → their JSON token;
  `string` → `JSON.stringify(s)` (correct escaping, no normalisation); `Date` → the
  microsecond RFC 3339 string, quoted; a tagged decimal → its unquoted fixed-scale token;
  arrays → `[` + elements + `]` preserving the caller's order; objects → keys sorted with
  `keys.sort()` (V8's default sort on strings is UTF-16 code unit order — that is exactly
  what is required) then `{"k":v,...}`.
- Microsecond timestamp: take `date.toISOString()` (which yields millisecond precision),
  strip the trailing `Z`, pad the fractional part to six digits with `'0'`, re-append `Z`.
  Reject a non-UTC representation — always format from the epoch value.
- Represent a fixed-scale decimal with a tiny branded type so it cannot be confused with a
  plain number: `export type CanonicalDecimal = { __decimal: string }` and
  `export function fixedScale(value: string | number, scale: number): CanonicalDecimal`
  producing `value.toFixed(scale)` semantics from a string to avoid float drift (use a
  string-based fixed formatter, not `Number.prototype.toFixed`, for values arriving from
  `pg` as strings — `pg` returns `numeric` as a string precisely so precision survives).
- `undefined` is a programming error here: throw rather than emit an omitted key, so a
  missing field surfaces loudly instead of silently changing a hash.

**Entry hash** — copy the shape from TechArch §2.12 exactly:
```
entry_hash = SHA-256(
    canonical_json({
      case_id, case_sequence, action_type, actor_type, actor_specialist_id,
      occurred_at, exception_id, recommendation_id, decision_id,
      before_state, after_state, reason, request_id,
      values: [ {field_name, before_value, before_origin,
                 after_value, after_origin, changed} ]   -- sorted by field_name
    })
 ‖ prev_entry_hash )                                      -- ‖ = byte concatenation
```
So `computeEntryHash(entry, prevEntryHash)`:
1. Assert `prevEntryHash` is a 32-byte `Buffer`; throw otherwise.
2. Build the object with exactly those thirteen scalar keys plus `values`. Do not add
   `id`, do not add `global_sequence`, do not add `entry_hash`, do not add `prev_entry_hash`
   — they are not part of the hashed payload.
3. Sort `values` by `field_name` using a plain `<` comparison; each value row carries
   exactly the six keys `field_name, before_value, before_origin, after_value, after_origin, changed`.
4. `Buffer.concat([Buffer.from(canonicalJson(payload), 'utf8'), prevEntryHash])`, then
   `createHash('sha256').update(...).digest()` → a 32-byte `Buffer`.
5. `export const ZERO_HASH = Buffer.alloc(32);` — freeze it or return a copy from a getter
   so a caller cannot mutate the shared buffer. Prefer `Object.freeze` on a module-level
   constant plus a defensive `Buffer.from(ZERO_HASH)` at every use site inside this module.

Also export `sha256(input: Buffer | string): Buffer`.

Finally: run the suite, read the actual hash from the fixed-vector test failure, paste it
into `server/test/unit/canonical.spec.ts` as the expected hex constant, and re-run until
green. That constant is now a regression anchor — if a later change alters it, the chain of
every previously written audit entry has silently changed meaning, which is exactly what the
test exists to catch. Add a comment in the spec saying so.

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| caller→hash computation | Audit-entry field values reaching the serialiser; a serialisation that varies with input shape would make the tamper-evidence claim false |
| module→module | `canonical.ts` is shared by the audit writer and (in parity) by the SQL verifier, so a divergence between them silently disables chain verification |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-01-11 | Tampering | `computeEntryHash` value-row ordering | mitigate | `computeEntryHash` in `server/src/db/canonical.ts` sorts `values` by `field_name` with a plain `<` comparison before serialising, so a caller cannot change an entry's hash — or hide a row — by reordering the array |
| T-01-12 | Repudiation | `canonicalJson` key ordering | mitigate | Keys are sorted by UTF-16 code unit via `keys.sort()`, never `localeCompare`, so the hash is reproducible across locales and processes; the cross-process assertion in `server/test/unit/canonical.spec.ts` proves it |
| T-01-13 | Tampering | `ZERO_HASH` shared buffer | mitigate | `ZERO_HASH` is a module-level frozen constant and every internal use copies via `Buffer.from`, so a caller mutating the returned buffer cannot poison the genesis link of every subsequent case |
| T-01-14 | Repudiation | float drift in decimal serialisation | mitigate | `fixedScale` formats from the string `pg` returns for `numeric`, never through `Number.prototype.toFixed` on a parsed float, so a `declared_value_usd` hashes identically on write and on verification |
| T-01-15 | Tampering | silent `undefined` in the hashed payload | mitigate | `canonicalJson` throws on `undefined` rather than omitting the key, so a missing field fails loudly instead of producing a different-but-plausible hash |
