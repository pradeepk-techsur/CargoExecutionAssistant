<objective>

governance guarantees are expressed against, a forward-only migration runner that connects
as `cargoexec_owner`, and a test harness that creates a fresh database per suite and

five phase success criteria can be proved. This plan ships that and stops.

Output: root workspace configuration, `docker-compose.yml` + role init script, the migration
runner, the test-database lifecycle helper, and the two shared `contract/` constants the
audit writer will need.

`db/init/00-roles.sh` — runs once, on a fresh volume, as the superuser. This is the

instruction. Make it executable (`chmod +x`).
```sh
#!/bin/bash
set -euo pipefail

psql -v ON_ERROR_STOP=1 --username "$POSTGRES_USER" --dbname "$POSTGRES_DB" <<-EOSQL
  -- pgcrypto is created here as superuser as well as in migration 0001, so
  -- gen_random_uuid() is available regardless of which role migrates first.
  CREATE EXTENSION IF NOT EXISTS pgcrypto;

  -- Three DATABASE roles. None of them is an application role: CargoExec has
  -- exactly one application role, 'cargo specialist', which is not represented
  -- in the database privilege system at all (FRD Y0 §Roles, F1 FR-1.1).
  CREATE ROLE cargoexec_owner LOGIN PASSWORD '${CARGOEXEC_OWNER_PASSWORD}' CREATEDB;
  CREATE ROLE cargoexec_app   LOGIN PASSWORD '${CARGOEXEC_APP_PASSWORD}';
  CREATE ROLE cargoexec_ai    LOGIN PASSWORD '${CARGOEXEC_AI_PASSWORD}';

  -- The owner owns the schema and is used ONLY by the migration runner.
  ALTER DATABASE ${POSTGRES_DB} OWNER TO cargoexec_owner;
  ALTER SCHEMA public OWNER TO cargoexec_owner;

  -- Neither runtime role may create objects.
  REVOKE CREATE ON SCHEMA public FROM PUBLIC;
EOSQL
```
`CREATEDB` on the owner exists so the test harness can create and drop per-suite databases
without a superuser connection (TechArch §8.2).

Do NOT grant anything else here. Every table grant and revocation belongs to migration
0008 (plan 01-05), because FR-0.17 requires privileges to land in the same migration set as
the tables they protect.

**`server/scripts/migrate.mjs`** — one runner used by both the compose `migrate` service and
the test harness, so tests migrate exactly as deployment does.

```js
import runnerDefault, { runner as runnerNamed } from 'node-pg-migrate';

// node-pg-migrate 7.x exports the runner as the default; accept the named export
// too so a packaging change surfaces as a clear error rather than a crash.
const runner = typeof runnerDefault === 'function' ? runnerDefault : runnerNamed;
if (typeof runner !== 'function') {
  throw new Error('node-pg-migrate runner export not found');
}

export async function runMigrations({ databaseUrl, dir = 'server/migrations', log = () => {} }) {
  if (!databaseUrl) throw new Error('runMigrations: databaseUrl is required');
  await runner({
    databaseUrl,
    dir,
    migrationsTable: 'schema_migrations',
    direction: 'up',
    count: Infinity,
    singleTransaction: false, // each migration file gets its own transaction
    log,
  });
}

if (import.meta.url === `file://${process.argv[1]}`) {
  await runMigrations({
    databaseUrl: process.env.DATABASE_URL_OWNER,
    log: (m) => console.log(m),
  });
  console.log('migrations applied');
}
```
Notes the executor must honour:
- `migrationsTable: 'schema_migrations'` is required by TechArch §2.13; do not accept
  node-pg-migrate's default `pgmigrations`.
- `singleTransaction: false` with node-pg-migrate's per-migration transaction gives
  FR-Y0.1's "each wrapped in a transaction" while letting a later file fail independently.
- There is **no down-migration path in v1**. Do not add one, do not add a `down` script,
  and do not write `-- Down Migration` sections in any migration file.
- If the installed `node-pg-migrate@7.9.0` rejects an option name, run
  `node -e "import('node-pg-migrate').then(m=>console.log(Object.keys(m)))"` and adapt the
  call — but keep the exported `runMigrations` signature and the `schema_migrations` table
  name unchanged, because plan 01-02 onwards depend on both.

`createTestDatabase()`:
1. Read `PGHOST`/`PGPORT` and the four passwords from `process.env`, defaulting to the
   `.env.example` values so a bare `npm run test:db` works after `docker compose up -d db`.
2. `name = 'cargoexec_test_' + randomBytes(6).toString('hex')`.
3. Connect to the `postgres` maintenance database **as `cargoexec_owner`** (it holds
   `CREATEDB`) and run `CREATE DATABASE "<name>"`. Database names are generated, never
   client-supplied, and are additionally validated against `/^cargoexec_test_[0-9a-f]{12}$/`
   before interpolation, because `CREATE DATABASE` cannot take a bind parameter.
4. `await runMigrations({ databaseUrl: ownerUrl })`.
5. Return the five connection strings.

`dropTestDatabase(db)`:
1. Connect to `postgres` as `cargoexec_owner`.
2. `SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname = $1 AND pid <> pg_backend_pid()`.
3. `DROP DATABASE IF EXISTS "<name>"` (same regex guard).

Add a file-level comment stating why teardown drops rather than truncates: `TRUNCATE` on the
audit tables is rejected by an unconditional trigger for every role including the owner, so
teardown-by-truncate is not an option — the append-only guarantee constrains the harness
itself (TechArch §8.2). **Never add a `TRUNCATE` to this helper.**

Also export `connect(url)` returning a connected `pg.Client`, and `withClient(url, fn)` that
always closes, so later suites do not each reinvent connection handling.
