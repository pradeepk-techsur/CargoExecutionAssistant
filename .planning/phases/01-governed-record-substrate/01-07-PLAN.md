product whose scope discipline is a stated success metric (SM-14), absence must be verified,
not remembered. `npm run test:arch` is the mechanism by which PRD §10's exclusion list
becomes a build constraint rather than an intention.

tempted to add a `priority` column, a filter, an export, a second role, or "a quick axe check
in CI". This suite fails the build when that happens. It also closes FR-Y0.5, which requires
a schema test asserting the absent-column list, the privilege set, and the eight-action
correspondence.

Run against a **freshly migrated** database via `createTestDatabase`/`dropTestDatabase`, so
the assertions are about the migration set rather than about whatever the dev database

**1. Forbidden column names (TechArch §2.14 item 1).** Define `FORBIDDEN_COLUMNS` as exactly
these twenty-five names, copied verbatim:
```
assigned_to, assignee_id, claimed_by, priority, severity, severity_rank, risk_score,
age_days, due_at, sla_due_at, sla_status, role, is_supervisor, permission, permissions,
scope, tenant_id, exported_at, export_format, source_system, ingestion_batch_id, is_seed,
hts_code, tariff_rate, duty_amount
```
Query:
```sql
SELECT table_name, column_name FROM information_schema.columns
 WHERE table_schema = 'public' AND column_name = ANY($1)
```
and assert the result is empty. On failure the message must name the table and column so the
scope leak is obvious.

**2. Exactly thirteen application tables (TechArch §2.14 item 2).** Define
`APPLICATION_TABLES` as: `specialists`, `sessions`, `cargo_entries`,
`cargo_entry_field_origins`, `validation_results`, `validation_findings`, `exceptions`,
`recommendations`, `recommendation_values`, `decisions`, `decision_values`, `audit_entries`,
`audit_entry_values`. Query `information_schema.tables` for
`table_schema = 'public' AND table_type = 'BASE TABLE'`, subtract `schema_migrations`, and
assert the remaining set **equals** `APPLICATION_TABLES` — both directions, so an added table
and a missing table each fail.

**3. Forbidden object names (TechArch §2.14 item 9).** Assert that no table, view,
materialised view, or function name in schema `public` matches
`/export|report|dashboard|metric|seed|fixture|ingest|assign|priorit/i`. Query `pg_class`
(relkinds `r`, `v`, `m`, `p`) and `pg_proc` filtered to the `public` namespace. Note that
`verify_audit_chain`, `audit_reject_mutation`, `audit_check_chain`,
`exceptions_require_human_decision`, `require_audit_entry` and the five `*_require_audit`
functions must all pass this filter — they do; if a future name does not, that is the signal.

**4. The eight audit actions (FR-Y0.5, TechArch §2.14 item 7).** Define `AUDIT_ACTIONS` as
the eight transitions of FRD `00-header` §0.6:
```
ENTRY_RECEIVED, VALIDATION_COMPLETED, EXCEPTION_OPENED,
RECOMMENDATION_GENERATED, RECOMMENDATION_UNAVAILABLE,
RECOMMENDATION_APPROVED, RECOMMENDATION_EDITED_AND_APPROVED,
RECOMMENDATION_REJECTED
```
Read `pg_get_constraintdef(oid)` for `ae_action_chk`, extract the quoted literals with a
regex, and assert the extracted set **equals** `AUDIT_ACTIONS` — so a ninth action added
without a corresponding transition fails, and so does a removed one.

**5. No delete path (TechArch §2.2).** Assert that no foreign key in schema `public` declares
`ON DELETE CASCADE` or `ON DELETE SET NULL` (`pg_constraint.confdeltype <> 'a'`), because a
cascade would be an indirect deletion route through a table on which `DELETE` is granted to
nobody.

**6. No audit-table scope leakage.** Assert that `audit_entries` and `audit_entry_values`
carry no column matching `/failure_reason|redact|correct|retention|archive|purge|delete|export/i`
— clarification C-1 forbids `failure_reason` here specifically, and the rest are the
capabilities F13 FR-13.14 and FR-13.18 rule out.

  <feature_dependencies>Implements: F0 FR-0.4, FR-Y0.3, FR-Y0.5; TechArch §2.14 items 3–6 and A-1 · Depends on: Task 2 · Enables: the behavioural counterpart in plan 01-08</feature_dependencies>

This suite asserts what the schema **declares**; plan 01-08 asserts what the database
**does**. Both are required: a declaration test catches a migration that silently widened a
grant, and a behavioural test catches a trigger that was dropped. Say so in a file comment,
and cross-reference plan 01-08's spec file by name.

Against a freshly migrated database, read `information_schema.table_privileges` and assert:

1. **`cargoexec_app` cannot mutate the audit store** (§2.14 item 3): no `UPDATE`, `DELETE` or
   `TRUNCATE` grant for `cargoexec_app` on `audit_entries` or `audit_entry_values`; and it
   **does** hold `SELECT` and `INSERT` on both, so the assertion distinguishes "correctly
   revoked" from "never granted anything and therefore broken".
2. **`cargoexec_app` cannot update the entry of record** (§2.14 item 4, deviation D-3): no
   `UPDATE` grant on `cargo_entries`.
3. **`cargoexec_ai` is structurally incapable of resolving a case** (§2.14 item 5, addition
   A-1): zero privilege rows of any `privilege_type` for `cargoexec_ai` on `decisions` or
   `decision_values`; no `UPDATE` on `exceptions`; and zero rows on `specialists` or
   `sessions`. Positively assert it **does** hold `SELECT` on `cargo_entries`,
   `validation_results`, `validation_findings`, `exceptions`, `recommendations`,
   `recommendation_values`; `INSERT`+`UPDATE` on `recommendations`; `INSERT` on
   `recommendation_values`; `SELECT`+`INSERT` on both audit tables.
4. **`DELETE` and `TRUNCATE` are granted to no role on any table** (§2.14 item 6): query for
   `privilege_type IN ('DELETE','TRUNCATE')` across all of schema `public` for every grantee
   including `PUBLIC`, and assert the result is empty.
5. **Neither runtime role holds DDL**: `has_schema_privilege('cargoexec_app', 'public',
   'CREATE')` and the same for `cargoexec_ai` both return false; `has_schema_privilege(...,
   'USAGE')` returns true for both (otherwise the grants in item 3 would be unreachable and
   the whole suite would be asserting a fiction).
6. **The full `cargoexec_app` matrix matches FR-Y0.3 exactly.** Build the expected
   `{table → sorted privilege list}` map from FR-Y0.3 and compare set-for-set, so a widened
   grant in a future migration fails here rather than being discovered in production.

Use `createTestDatabase`/`dropTestDatabase` in `beforeAll`/`afterAll`. Note that role grants
in `information_schema.table_privileges` are per-database, so the fresh test database
exercises migration 0008 itself rather than inheriting anything from the dev database.
