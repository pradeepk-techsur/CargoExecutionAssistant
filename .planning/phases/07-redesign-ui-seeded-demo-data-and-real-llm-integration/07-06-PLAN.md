  `DatePickerInput` accepts and submits the typed value as-is with no
  locale coercion (`type="text"` semantics), not a native `<input
  type="date">`.
- **Fieldset** → Carbon has no dedicated `Fieldset` wrapper component; keep
  the native `<fieldset>`/`<legend>` (required, semantic, standards-based
  HTML — not itself a "bespoke control"), styled with Carbon's typography/
  spacing tokens, preserving the exact `aria-describedby` join order
  (statement id, then fieldset-level error id) and the `tabIndex={-1}`
  focus-target behaviour the error-summary link activation relies on
  (FR-6.10's RIV-070/RIV-073 cross-field exception).

**ProvenanceBadge.tsx.** Rebuild on Carbon's `Tag` component from
`@carbon/react` plus `@carbon/icons-react` icons. Preserve the FOUR
redundant carriers Pattern 1 requires (never colour alone):
1. **Text label** — unchanged: "AI-suggested" / "Specialist-entered" /
   "Specialist-modified".
2. **Icon** — a DISTINCT icon per origin, not the same glyph recoloured.
   Use `@carbon/icons-react`'s `Settings` (or `SettingsAdjust`) for AI and
   `User` for HUMAN — confirm both exist in the installed icon package

   (Carbon's icon components accept this directly, or wrap in a `<span
   aria-hidden="true">` if the icon component itself does not forward the
   attribute — verify).
3. **Shape/border distinction** — Carbon's `Tag` does not natively vary
   border style by type, so add ONE small, explicitly-documented CSS rule
   (in this file's own scoped styling, or a tiny addition to `app.scss`
   under a `.cargoexec-provenance-badge` class) giving the AI variant a
   dashed 2px border and the HUMAN variant a solid 2px border, preserving
   the EXACT distinction Pattern 1 names. Document this as a Carbon-
   conformant composition addition in the register, not a bespoke widget —
   it is a styling refinement of a registered Carbon component, not a new
   interactive control.
4. **Token colour** — use two visually-distinct Carbon `Tag` `type` values
   (e.g. `type="purple"` for AI, `type="gray"` for HUMAN — pick a pair that
   the installed Carbon version documents as meeting AA contrast; verify,
   do not guess) — never re-use one colour for both variants.

Preserve the exact `modified` prop behaviour (label swaps to "Specialist-
modified" for a HUMAN value that was AI-proposed and changed, same icon/
colour pair as plain HUMAN — only the text differs, per FR-12.6). The
exported signature `ProvenanceBadge(props: { origin: 'AI' | 'HUMAN';
modified?: boolean })` stays unchanged.

**Document the AttributedValue gap honestly, do not silently claim
otherwise.** TechArch §1A.4 describes an `AttributedValue` component as
"the only component permitted to render a case value," type-enforcing that
a value cannot render without an `Attributed<T>` origin. This component
does NOT exist in the codebase today — every screen renders a value inline
(e.g. `entry.values.foo`) adjacent to a `ProvenanceBadge`, with the
guarantee held by code-review convention, not by the type system. This
plan does not invent that wrapper component now (that is new scope this
redesign phase was not asked to add) — it adds a short, explicit comment
at the top of `ProvenanceBadge.tsx` recording this exact discrepancy
(TechArch describes `AttributedValue`; it was never built; the actual,
currently-shipped guarantee is "every value that has an origin is rendered
with an adjacent `ProvenanceBadge`, verified per screen by review, never by
the type system") so a future reader is not misled into thinking a
stronger guarantee exists than actually does.
