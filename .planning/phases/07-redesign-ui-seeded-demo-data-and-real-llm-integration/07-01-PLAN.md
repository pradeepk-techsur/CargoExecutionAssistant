<objective>
Implement F15: a hand-authored, idempotent, stage-resumable seed script
(`server/src/cli/seed-demo-case.ts`) that pre-loads exactly one demonstration
cargo case, already carried through the full governed loop (received →
validated-failed → exception → AI recommendation → `EDIT_APPROVE` decision with
mixed AI/HUMAN provenance → full audit trail) — by calling the SAME service
functions the running application uses for a live request, never a migration
and never a direct `INSERT`. Add the narrow, named architecture-test exception
that lets this one file exist without weakening the existing seeds/fixtures
directory ban or the migration-INSERT ban.

Purpose: so every later-loop scenario (recommendation review, decision, audit
trail) is demonstrable on demand without hand-typing an entry and its
validation failure live first (PRD §10 #7, superseded).
Output: `server/src/cli/seed-demo-case.ts`, a `seed:demo-case` npm script, two
narrowly-extended architecture tests, and `docs/seed-demo-case.md` (the FR-15.9
fixture-labelling runbook).
</objective>

**Reserved fixed constants** (module-level, hard-coded — FR-15.11 forbids any
parameterisation that would make this a general fixture factory):
```
DEMO_SPECIALIST_EMAIL        = 'demo.specialist@cbp.example.gov'
DEMO_SPECIALIST_DISPLAY_NAME = 'Demo Specialist (Seeded)'
DEMO_SPECIALIST_PASSWORD     = 'cargoexec-demo-specialist-seed'   // 30 chars, satisfies the 12-256 range
DEMO_ENTRY_NUMBER            = 'DEMO-0000001'
DEMO_GOODS_DESCRIPTION       = 'Assorted retail merchandise for demonstration purposes'
DEMO_DECISION_REASON         = 'Corrected the carrier code after confirming it against the demonstration manifest.'

The fixture entry supplies ONLY `entry_number` and `goods_description`
(`provided: EntryFieldName[] = ['entry_number', 'goods_description']`); all
other 12 fields of the `CanonicalEntryRecord` are `null`. This is a genuinely
incomplete entry (mirrors the existing "goods_description only" pattern
receipt.spec.ts already exercises) and WILL fail multiple `RIV-0x0` presence
rules through F4's real evaluation — the failure is real, never asserted.

**Imports** — only ever the APP pool. Do NOT import `db/pool.ai.js`/`getAiPool`
anywhere in this file: `aiCapability.spec.ts` test 3 asserts the importer set
of `pool.ai.js` is EXACTLY `{server/src/index.ts}`, and that test is NOT one of
the two named for a Phase 7 update. Instead, pass the SAME app pool as both
`aiPool` and `appPool` in `GenerationJobDeps` when calling `runGenerationJob`.
This is deliberate and safe, not a shortcut: the two-pool split
(`cargoexec_app` vs. `cargoexec_ai`) exists ONLY to keep the asynchronous,
network-facing worker from holding write privilege it should never need (A-1);
an operator-invoked CLI already runs at a higher trust level than that async
path, and `cargoexec_app`'s privileges are a strict superset of
`cargoexec_ai`'s for every read this job performs — so no guarantee is
weakened by reusing it. Document this reasoning in the file's header comment,
naming `aiCapability.spec.ts` test 3 explicitly so a future reader does not
"fix" it by adding a `pool.ai.js` import.

Construct the AI provider the same way `server/src/index.ts` does — do NOT
import or modify `index.ts`; duplicate the small ternary locally (a shared
factory module is not worth introducing for a single six-line ternary with two

```
const provider =

**Stage-by-stage logic** (`main(): Promise<number>`), each stage checked BEFORE
writing (FR-15.3 — never a single all-or-nothing precondition):

1. **Specialist** — `findSpecialistByEmail(appPool, DEMO_SPECIALIST_EMAIL)`
   (import from `../db/repositories/specialists.js`). If absent, call
   `createSpecialist(ownerUrlFromEnv(), { email: DEMO_SPECIALIST_EMAIL,
   display_name: DEMO_SPECIALIST_DISPLAY_NAME, password: DEMO_SPECIALIST_PASSWORD
   })` (imported from `./create-specialist.js`; read `DATABASE_URL_OWNER` from
   `process.env` the same way that module's own `ownerUrlFromEnv` does — either
   import that helper if it is exported, or inline the same two-line read/throw).
   Log `created` vs. `reused`. Keep the resolved `specialistId` +
   `DEMO_SPECIALIST_DISPLAY_NAME` for later stages.

2. **Entry + exception** — `findCaseReferenceByEntryNumber(appPool,
   DEMO_ENTRY_NUMBER)` (from `../db/repositories/entries.js`).
   - If `null`: build the `CanonicalEntryRecord` (14 keys, 12 `null`), call
     `receiveEntry({ pool: appPool, principal: { id: specialistId, display_name:
     DEMO_SPECIALIST_DISPLAY_NAME } }, submitted, provided)` — `requestId` and
     `dispatchRecommendation` both OMITTED (undefined), so receipt does NOT
     fire the async worker; this script drives the recommendation stage itself,
     explicitly, in the next step, so there is exactly one path to it. If the
     response's `exception` is `null` (the fixture validated clean — a
     script-authoring bug, not a runtime condition), throw a fatal
     `DEMO_FIXTURE_INVALID` error naming the stage. Otherwise capture
     `exceptionId = response.exception.id`. Log `created`.
   - If a case reference already exists: `resolveCaseIdentifier(appPool,
     'CASE_REF', caseReference)` (from `../db/repositories/exceptions.js`). A
     `FOUND` result gives `exceptionId` directly. An `ENTRY_PASSED_VALIDATION`
     result is a fatal invariant error (the reserved entry number must always
     resolve to the seeded exception) — throw and exit non-zero naming the
     stage. Log `already present`.

3. **Recommendation** — `loadRecommendationByException(appPool, exceptionId)`
   (from `../db/repositories/recommendations.js`).
   - If `status === 'PENDING'`: `await runGenerationJob({ aiPool: appPool,
     appPool, provider, modelId: config.aiModelId, promptVersion:
     config.promptVersion }, exceptionId)` (awaited — this in-process call IS
     the same function the real worker invokes per job; the script simply calls
     it directly and synchronously instead of through `ai/worker.ts`'s queue,
     which is correct for a single-exception CLI). Re-load the recommendation
     afterward.
   - If the (possibly just-updated) status is `AVAILABLE`: log `created`/
     `already present` accordingly and continue.
   - If the status is `UNAVAILABLE` (whether just reached or already terminal
     from a prior run): F9 FR-9.14 forbids any automatic retry after a terminal
     outcome — do NOT call `runGenerationJob` again. Log the `failure_reason`,
     exit non-zero naming the `recommendation` stage, and state that a re-run
     after the provider is reachable will resume from here (FRD §Error States).
   - If it is still `PENDING` after the call (should not happen given F9's
     synchronous terminal-write contract, but defend anyway): exit non-zero
     naming the stage.

4. **Decision** — `loadDecisionByException(appPool, exceptionId)` (from
   `../db/repositories/decisions.js`). If non-null: log `already present`,
   done. If null: `loadRecommendationValues(appPool, recommendationId)` (from
   `../db/repositories/recommendations.js`) to read the AI's proposed values.
   Build `resolution_values`: for the FIRST proposed value, set `value =
   proposed_value + ' (specialist-verified)'` (guaranteed to differ after
   trim, so `decision.service.ts`'s trim-then-byte-compare re-stamps it
   `HUMAN`); for every OTHER proposed value, set `value = proposed_value`
   unchanged (retaining `AI` origin). Call `recordDecision({ pool: appPool,
   principal: { id: specialistId, display_name: DEMO_SPECIALIST_DISPLAY_NAME }
   }, exceptionId, { decision_type: 'EDIT_APPROVE', reason:
   DEMO_DECISION_REASON, resolution_values }, null)`. Log `created`.

5. **Summary** — log one final line: case reference, `DEMO_SPECIALIST_EMAIL`,
   and a count of this case's audit entries (a simple `SELECT count(*) FROM
   audit_entries WHERE case_id = $1` against `appPool` is acceptable here —
   read-only, not a second write path). Call `closeAppPool()`. Return `0`.

Wrap the whole `main()` body in a try/catch: on any thrown error, write
`seed-demo-case: failed at stage <name>: <message>` to stderr and return `1`
(never `0`) — never swallow an error into a false success. Run when invoked
directly (`import.meta.url === \`file://${process.argv[1]}\``), mirroring
`create-specialist.ts`'s own bottom-of-file pattern exactly, calling
`process.exit(code)`.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator CLI → service layer | `seed-demo-case.ts` runs in-process with the same `cargoexec_app` database credentials the request path uses, but with NO HTTP request, NO session, and NO CSRF boundary in front of it — trust here is "whoever can run a shell command against this deployment", not "whoever is signed in" |
| fixture data → governed record | The seeded case's rows are read back and rendered by F10/F14 exactly like any organic case; nothing distinguishes them structurally (by design, FR-15.9), so any weakness in labelling is a documentation-only risk, never a data-level one |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-01 | Elevation of privilege | `server/src/cli/seed-demo-case.ts` | mitigate | `main()` accepts zero arguments and performs no argv parsing beyond direct invocation (FR-15.11) — no `--count`, `--email`, or batch flag exists, so it cannot become a general fixture factory. The new `absence.spec.ts`/`validation.spec.ts` assertions (Task 2) additionally fail the build if a second seed-named file ever appears. |
| T-07-02 | Tampering | `server/src/cli/seed-demo-case.ts` | mitigate | The script imports ONLY `receiveEntry`, `runGenerationJob`, `recordDecision`, and `createSpecialist` — no repository INSERT/UPDATE function for a governed table is imported directly. `receiptPaths.spec.ts`'s existing "only caller of the insert functions is receipt.service.ts" assertion (unmodified) already fails the build if that ever changes. |
| T-07-03 | Information disclosure | `DEMO_SPECIALIST_PASSWORD` constant | mitigate | The password is fixed, non-secret, and labelled as fixture-only in `docs/seed-demo-case.md`; `createSpecialist`'s existing Argon2id hashing and its established "never echoed, never logged" behaviour (unchanged, reused as-is) apply identically to this call. |
| T-07-04 | Denial of service | Real-provider recommendation generation during seeding | accept | Running the seed script against a demonstration deployment configured for a real hosted LLM incurs one real generation call; documented in `docs/seed-demo-case.md` as expected, operator-triggered, and out of the automated test path (owner: the operator running the command). |
