<objective>
Change the Phase 7 deployment posture for F9 (FR-9.20): the demonstration/
production `docker-compose.yml` must no longer silently default
`AI_PROVIDER_URL` to the deterministic `fake:deterministic` provider. An
operator must set it explicitly — to a real HTTPS LLM endpoint for any
demonstration/production run, or to the literal `fake:deterministic` only as a
deliberate, documented override. No code in `server/src/ai/` changes: the
provider abstraction, the adapter, and the retry/timeout/schema-validation
logic are all already correct and untouched by this plan (TechArch §5.9).

Purpose: today, `docker compose up` with no `.env` silently boots a
demonstration deployment against the fake provider, which is exactly the
posture FR-9.20 forbids. This plan fixes the DEFAULT, not the architecture.
Output: `docker-compose.yml` and `.env.example` changes, plus
`docs/ai-provider-configuration.md`.
</objective>

  <action>
In `docker-compose.yml`'s `web` service `environment:` block, change:
```yaml
      AI_PROVIDER_URL:      ${AI_PROVIDER_URL:-fake:deterministic}
      AI_MODEL_ID:          ${AI_MODEL_ID:-demo-fake-model}
```
to:
```yaml
      AI_PROVIDER_URL: ${AI_PROVIDER_URL:?AI_PROVIDER_URL must be set explicitly: a real https:// LLM endpoint for a demonstration/production deployment (FR-9.20), or the literal fake:deterministic for local/test use only. There is deliberately no silent default.}
      AI_API_KEY:      ${AI_API_KEY:-}
      AI_MODEL_ID:     ${AI_MODEL_ID:-demo-fake-model}
```
Note `AI_API_KEY` is currently ABSENT from `docker-compose.yml` entirely —
`.env.example` already declares it but the compose file never passes it
through to the `web` service, so a real-provider deployment configured only
via compose would have no way to supply a key at all. Add it as shown (default
empty — `config.ts`'s own boot self-check already requires it only when
`AI_PROVIDER_URL` is a real `https://` URL, so an empty default is correct for
the fake posture and loud-failing for a misconfigured real one).

Rewrite the surrounding comment block (currently explaining the old
Phase-5-era posture) to state the Phase 7 posture plainly: this deployment
requires a real hosted LLM outside test configuration (FR-9.20); the fake
provider remains valid ONLY as an explicit override, e.g. `AI_PROVIDER_URL=
fake:deterministic docker compose up`, never the shipped default; `AI_API_KEY`
is required by `config.ts`'s existing self-check only for a real `https://`
provider. Cite FR-9.20 and TechArch §5.9 by name so a future reader finds the
source.

In `.env.example`, above the existing `AI_PROVIDER_URL=` / `AI_API_KEY=` /
`AI_MODEL_ID=` / `PROMPT_VERSION=` block, add a comment explaining the same
Phase 7 posture: these ship empty here (forcing the developer to choose
explicitly before `loadConfig()` will boot), and the same rule applies to any
demonstration/production deployment via `docker-compose.yml`'s new mandatory
`AI_PROVIDER_URL`. Do not change the empty values themselves — they are
already correct.

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| operator env config → app boot self-check | `AI_PROVIDER_URL`/`AI_API_KEY`/`AI_MODEL_ID` cross from operator-supplied configuration into `config.ts`'s startup validation |
| app → external LLM provider | Outbound HTTPS egress is the only network call the system makes (TechArch §5.2) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-07-05 | Information disclosure | `AI_API_KEY` passthrough in `docker-compose.yml` | mitigate | The key is passed only via `environment:` (never printed by `docker compose config` output in this form, never echoed by any task command here); `config.ts`'s existing self-check messages name only the offending KEY, never its value (§4.7, unchanged) |
| T-07-06 | Spoofing | Operator-supplied `AI_PROVIDER_URL` pointing at an attacker-controlled endpoint | accept | Validating provider identity beyond requiring an `https:` scheme (existing self-check, unchanged) is outside this deployment-posture plan's scope; owner: the deploying operator, who chooses the provider |
| T-07-07 | Elevation of privilege / silent misconfiguration | A production/demonstration deployment silently inheriting the fake provider (the FR-9.20 risk this plan exists to close) | mitigate | `docker-compose.yml`'s `${AI_PROVIDER_URL:?...}` mandatory-variable syntax (Task 1) — `docker compose config`/`up` refuses to proceed with no value, converting a silent misconfiguration into a loud, named failure |

</threat_model>
