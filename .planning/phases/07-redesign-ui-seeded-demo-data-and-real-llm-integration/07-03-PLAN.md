<objective>
Prepare — but do NOT perform — the F2 visual redesign. The user-supplied
replacement design (a `claude.ai/design/...` link) returned 403 during scoping
and remains inaccessible: no colour, token, component, or layout detail from it
is known. This plan therefore does INFRASTRUCTURE work only: (1) enumerate
every point in the current UI where USWDS is coupled in, so a future redesign
knows its exact blast radius, and (2) introduce a design-token abstraction seam
(CSS custom properties) that re-exposes the CURRENT USWDS theme's own values
under new, swappable names — so that when the real design becomes available,
applying it is a token/CSS override, not a per-component rewrite. Nothing
visual changes. No component is touched. No colour is invented.

Purpose: make load-bearing progress toward F2's Phase 7 redesign without
guessing at a design nobody has shown this project, while leaving today's
Section 508 / WCAG 2.1 AA conformance, CSP, and asset pipeline exactly as they
are.
Output: `docs/uswds-coupling-audit.md` (the inventory) and
`web/styles/_tokens.scss` (the seam), forwarded into the existing
`web/styles/app.scss` entry point.
</objective>


Document, exactly:
1. **Every `.tsx` file that references a USWDS class or the `uswds` JS module**
   — list each path individually (as of this writing: 18 of 21 files under
   `web/src`, spanning `web/src/components/`, `web/src/screens/`, and
   `web/src/shell/`; the 3 exceptions —
   `web/src/app/router.tsx`, `web/src/main.tsx`,
   `web/src/session/SessionProvider.tsx` — carry no markup and reference no
   USWDS class). For each listed file, one line naming what it couples to
   (e.g. "usa-table, usa-table-container--scrollable" for `Queue.tsx`) is
   sufficient — this is an inventory, not a redesign spec.
2. **`web/styles/app.scss`** as the single Sass entry point: the
   `@use "uswds-core" with (...)` theme-settings block, `@forward "uswds"`,
   and the fact it compiles (via `npm run build:css`) into
   `web/public/assets/uswds.css`, loaded as a linked `<link>` stylesheet (never
   a JS-injected `<style>` tag).
3. **`web/scripts/copy-uswds-assets.mjs`** as the asset self-hosting pipeline:
   copies USWDS's icon sprite, fonts, and compiled JS from `node_modules` into
   `web/public/assets` at build time, so nothing is fetched from a CDN at
   runtime (FR-2.3).
4. **The CSP constraint** (`server/src/http/headers.ts`): `style-src 'self'`
   with no `unsafe-inline` — state plainly that ANY replacement visual system
   must still compile to a single self-hosted stylesheet loaded via `<link>`;
   a design system whose runtime injects `<style>` tags or assumes a CDN font
   host is incompatible with this constraint as it stands (TechArch §1A.1b).
5. **`docs/uswds-conformance-register.md`** — note (do not yet rewrite) that
   this register maps every interactive control to a specific USWDS primitive
   by name, and will need a wholesale re-authoring once the replacement
   design's primitives are known (TechArch §1A.1b point 2) — flagged as
   required future output, not attempted here.
6. A closing section, in plain words: **this document changes nothing about
   what ships today.** No component was touched, no colour was invented, and
   the actual visual redesign remains blocked pending the (currently
   inaccessible) approved design. See `web/styles/_tokens.scss` (Task 2) for
   the one piece of forward-looking infrastructure this phase does add.

<task type="auto">
  <name>Task 2: Introduce the design-token abstraction seam (behaviour-preserving)</name>
  <files>web/styles/app.scss, web/styles/_tokens.scss</files>
  <action>
Create `web/styles/_tokens.scss`. Its purpose is narrow: expose a curated set
of CSS custom properties at `:root`, whose VALUES are computed from USWDS
core's OWN existing theme configuration — never a hand-typed hex/px guess —
so the properties are guaranteed identical to what the shell already renders
today. Before writing values, inspect the installed package's public Sass API
(`node_modules/@uswds/uswds/packages/uswds-core/src/scss/` — look for exported
functions such as a colour-token accessor and a spacing-unit accessor; USWDS
3.x's `uswds-core` module conventionally exposes both) to find the CORRECT
function names for this installed version; do not guess a function name that
turns out not to exist — a broken `npm run build:css` is not an acceptable
outcome of this task, so verify against the actual installed API. If, after
checking, no clean public accessor function exists for a given token
family, it is acceptable to instead reference the SAME `$theme-*`
settings-block variables `app.scss` already sets — this file `@use`s
`uswds-core` already, so those are already the project's own settled inputs,
just not yet re-exposed as custom properties.

Cover a SMALL, clearly-named set sufficient to prove the seam works — do not
attempt to enumerate the entire USWDS token system:
```
--cargoexec-color-primary
--cargoexec-color-primary-dark
--cargoexec-color-error
--cargoexec-color-base-ink
--cargoexec-space-1
--cargoexec-space-2
--cargoexec-space-3
--cargoexec-font-family-body
```
Nothing in `web/src/**/*.tsx` consumes these properties yet — that consumption
is future work, once a real design exists to apply. This task ships the SEAM,
not the usage.

Wire `_tokens.scss` into `web/styles/app.scss` immediately after the existing
`@use "uswds-core" with (...)` configuration block (Sass requires `@use`
statements before other rules; `_tokens.scss` itself will `@use "uswds-core"
as *;` — or the project's already-configured alias — to reach the same
configured instance, never re-configuring it a second time, which `app.scss`'s
own header comment already warns would deadlock). Add `@forward "tokens";` (or
`@use "tokens";` if the properties must land inside `app.scss`'s own compiled
output rather than a separately-forwarded partial — pick whichever the Sass
module system requires for the `:root` block to actually reach the compiled
`uswds.css`; verify by inspecting the build output, not by assumption).

Update `docs/uswds-coupling-audit.md`'s closing section (from Task 1) to note
that `web/styles/_tokens.scss` is now the named seam location, so this task's
diff should be additive to that file, not a rewrite of it.
  </action>
